# v0.140: サイドを取る順番の利用者の指定と、知らない再開先の決定の拒否

対象: v0.139 の追加検証（[prize-order-followup.md](prize-order-followup.md)）を踏まえた 2 件。

1. **サイドを取る順番（利用者の指定）**: 同じきぜつの処理で両方のプレイヤーがサイドを取るときは、いつも番のプレイヤーが先に取るプレイヤーを選び、選ばれたプレイヤーがまとめて
   取ってから、もう一方が取る（2 章）。v0.139 の「おもてのサイドがあるときだけ、1 枚ごとに次の人を選ぶ」を置きかえる
2. **知らない再開先の決定の拒否（両モード共通の不具合の修正）**: この版が扱えない再開先の決定を待つ状態（後の版の状態の写し・続けない前の版の決定）を、観測・コマンドの前に
   明示的な非対応（`UnsupportedError`・`UNSUPPORTED_DECISION`）で拒否する（3 章。追加検証の FU-D2）

保存形式は 34 のまま（4 章）。取ったサイドの位置の観測は変えていない（2.6 節）。HC1・ほかの裁定と規約・モードは変えていない（厳密モード・プレイ用モードは実装していない）。
カードの写し・採用の記録・研究の対応表・固定デッキ・過去の参照データ（`tests/fixtures/`）は変えていない（7.4 節）。

## 2. サイドを取る順番（利用者の指定）

### 2.1 指定の文と根拠の区別

この版の依頼（2026-11-03）の文を、利用者の指定の根拠として記録する。公式の裁定・エラッタ・kyuura の研究上の解決として扱わない。既存の利用者の指定と同じく、将来の厳密モード・
プレイ用モードの両方に共通する基礎集合の規約として記録する（[ruleset-mode-design.md](ruleset-mode-design.md) の AGR-MODE-BASELINE-USER。モードは実装していない）。

| ID | 指定の文（そのまま） |
|---|---|
| `USER-PRIZE-ORDER-ALWAYS-CHOSEN` | 両方のプレイヤーがサイドを取る場合は、表向き・うら向きや特殊能力の有無によらず、番のプレイヤーが先に取る人を選ぶ。 |
| `USER-PRIZE-ORDER-PER-PLAYER` | 先に選ばれたプレイヤーが必要な枚数を取り終え、その後、もう一方が必要な枚数を取る。1枚ごとの交互取得は認めない。 |

独自の規約の対象は、この 2 点（両方が取るときにいつも順番を選ぶこと・プレイヤーごとにまとめて取ること）だけ。

| 区分 | 内容 | 記録 |
|---|---|---|
| 公式資料（p.325 の一般規定） | 同じタイミングで複数のことがらが起こったときは、特に指示されていないかぎり、処理する順番を番のプレイヤーが決める（kyuura GR-2000-P325-SAME-TIMING。`checked: kyuura_image`） | 変えていない |
| 従来の導出（その当てはめ） | 同時のきぜつで両方がサイドを取ることへの当てはめ（v0.2f 2 章 #4 の SUPPORTED。明文はない） | 変えていない（導出のまま） |
| 今回の利用者の指定 | 上の 2 点。いつ・何を単位に順番を決めるかの公式の読みを決めたのではない | `decisions.USER_PRIZE_ORDER_RULES`・停止の方針の台帳の conventions（`CONV:USER-PRIZE-ORDER-*`） |
| 変えていない観測 | きぜつで取ったサイドの位置を相手・観戦者に見せないこと（2.6 節）。今回、公式の正しさを承認したとは記録しない | — |

### 2.2 仕様と実装

| 項目 | 内容 |
|---|---|
| 決定 | `decisions.PRIZE_FIRST`（`"prize_first"`。v0.139 の `prize_order` を置きかえた）。決めるのは番のプレイヤー（`state.current_player`）。選べるものは並びにいるプレイヤーの番号（`(0, 1)`）で 1 つ。段階は `Phase.DECISION`、再開先は `"prize_first"`、`context` は `remaining`（まだ取っていない並びのすべて）・`then`・`post_knockout` |
| 出す場面 | `flow.prize_first_needed`: 並び（`_after_knockouts` が作る。きぜつ 1 匹につき相手側のプレイヤー 1 枚。残りのサイドを超えない）に両方のプレイヤーがいて、まだ選んでいないとき。おもてのサイド・［おみとおし］・本人だけが知るサイドで条件を分けない。一方だけが取るなら出さない |
| 答えのあと | `flow._resume_prize_first`: 並びを「選んだプレイヤーの分すべて → もう一方の分すべて」にし（枚数は変えない）、選んだプレイヤーのサイドの決定を出す。選んだプレイヤーは続きの情報 `first`（サイドの決定の `context` の `"first"`）に持ち、取るたびに選び直さない |
| 主体の分離 | 順番を決めるのは番のプレイヤー、それぞれのサイドを選ぶのは取るプレイヤー本人（`take_prize` の決定。変えていない） |
| 情報 | 順番の決定の観測は、決めるプレイヤーに選べるもの（プレイヤーの番号）だけ、相手・観戦者に種類と数だけ。サイドの中身は含まない。取ったあとの観測は今までの公開の規則のまま（うらのカードは取ったプレイヤーだけ。取った位置・uid を新たに公開しない） |
| 判定 | 勝ち負け・サドン・デスは、すべて取り終えてから（v0.2f 2 章 #5 のまま。途中で 0 枚になったプレイヤーがいても判定しない） |
| ログ・乱数 | 順番の答えはログに書かない（ほかの決定と同じ。結果は `take_prize` の順番に表れる）。乱数は使わない |
| 不変条件 | `engine._prize_first_decision_problems`（決める人・選ぶ数・選べるもの・出す場面・`first` がないこと）。`engine._prize_first_marker_problems`（両方が取る並びのサイドの決定は `first` を持ち、そのプレイヤーの分が先にまとまっている） |
| 探索 | 選べるものは削っていない（両方のプレイヤー）。並びの組み合わせは 2 通りだけになる（v0.139 の 1 枚ごとの C(n, k) 通りより少ない。上限には関係しない） |
| 対戦の道具の方策 | `tests/helpers.py` の `trainer_policy_command` は、この決定に番のプレイヤーを選ぶ（v0.2f の正規化と同じ順番。旧バッチと比べられるように） |

### 2.3 v0.139 までの状態との関係（読み替えない）

v0.139 の決定 `prize_order` は意味が違う（1 枚ごとに次の人）ので、`prize_first` として読み替えない。`decisions.RETIRED_DECISIONS` に理由を書き、観測・コマンドの前に
`UnsupportedError`（`UNSUPPORTED_DECISION`）で拒否する（3 章の確かめ）。v0.138・v0.139 で両方がサイドを取る並びのサイドの決定（`first` がない）は、順番を選ばないまま進んだ状態で、
続けると黙って読み替えることになるので、決定への答えの前に `StateIntegrityError` で拒否する。残りが一方だけのサイドの決定（`first` がなくても並びは 1 人）は、どの版でも同じ意味なので
続けられる。どれも v0.139・v0.138 の木で作った状態の写しで確かめた（`OldVersionStateTest`）。

### 2.4 意図した差（基点との）

- 両方がサイドを取る場面ごとに、`take_prize` の前に `prize_first` の決定が 1 つ増える（どのサイドもうらでも）。決定の番号がずれ、サイドの決定の `context` に `first` が加わる
- 番のプレイヤーを先に選べば、カードの動き・ログの種類の並び・結果は基点と同じ（基点の並びも番のプレイヤーが先。`kernel.knocked_out` の順番）
- おもてのサイドがあり、1 匹ずつ 2 匹以上がきぜつして並びが 3 以上のとき、基点（v0.139）は 1 枚ごとに聞き直した。今は 1 回だけで、交互の並びはない
- 一方だけが取る場面・きぜつしない場面は変わらない

### 2.5 同等性の説明（合法な候補・取得順・決定時点の情報・最終結果を分ける）

| 観点 | 結果 | 確かめ方 |
|---|---|---|
| 合法な候補 | それぞれのサイドの決定で選べる位置は、自分のサイドの位置で、取る順番によらない | `OrderAndInformationTest.test_choice_depends_on_order`（候補が同じ） |
| 取得順 | 番のプレイヤーの選択で 2 通り（先のプレイヤーの分すべて → もう一方）。交互はない | `PerPlayerTest`（2 枚対 1 枚・2 枚対 2 枚） |
| 決定の時点の情報 | 取る順番で変わりうる（おもてのサイド・［おみとおし］で先に取られたカードが見える）。今は番のプレイヤーがその順番を選べる | `OrderAndInformationTest`（合法な操作の seed 2 と構築盤面） |
| 最終結果 | 同じ位置を取れば、順番によらず場・手札・サイド・乱数は同じ。見えた情報で選び方を変えれば、選択と結果は変わりうる | `PerPlayerTest.test_same_positions_give_the_same_board`・`OrderAndInformationTest` |

### 2.6 変えていないこと

- 取ったサイドの位置の観測（ログ `take_prize` に位置を書かない）。マチスの交渉（`trainer_take_prize`）の位置の公開との不統一は別件として残す
- 先攻・後攻、サイドの枚数、きぜつの処理、バトル場に出す順番（番でないプレイヤーから）、トレーナー・特殊能力でサイドを取る処理

## 3. 知らない再開先の決定の拒否（不具合の修正）

### 3.1 問題（修正の前の再現）

追加検証（[prize-order-followup.md](prize-order-followup.md) 4 章）で、v0.138 が v0.139 の `prize_order` の状態の写しを拒否せずに読み込み、答えると `RuntimeError`、観測で `ValueError` に
なることを確かめた。基点（v0.139 と同じエンジン）も同じ作りで、知らない再開先の決定を待つ状態に答えると `RuntimeError`（「決定の再開先 … を続ける処理がない（不変条件で拒否するはず。
エンジンの不具合）」）になる（`apply_command` は入力の状態を処理の前に確かめず、結果だけを確かめていた）。回帰テスト `UnsupportedDecisionTest` は基点で失敗する（5 章）。

### 3.2 変更

| 項目 | 内容 |
|---|---|
| 共通の確かめ | `decisions.unsupported_decision_error`（再開先が `DECISION_RESUMES` にない・前の版の決定 `RETIRED_DECISIONS` の名前なら `UnsupportedError`（`UNSUPPORTED_DECISION`）を返す）。`engine.supported_decision_error` が今の版の再開先の集合で呼ぶ |
| 入口 | コマンド: `engine._apply_once` が状態を複製する前に `_require_supported_decision`（どのコマンドでも。決定への答えを試してから内部エラーを捕まえる方式にしない）。観測: `observation.observe` が観測を作る前に同じ確かめ |
| 知っている再開先の壊れた状態 | 決定への答え（`ResolveDecision`・`TakePrize`・`PromoteActive`）の前に、決定の形の不変条件（`_decision_problems`）を確かめ、問題があれば `StateIntegrityError`（続けるのに要る情報が欠ける・合わない）。知らない再開先（`UnsupportedError`）と取り違えない |
| 理由の文 | 知らない再開先の文字列をそのまま書かない（状態の中の値で信頼できない）。前の版の決定は、決まった理由の文（`RETIRED_DECISIONS`）だけを書く |
| 状態・乱数・ログ | どの拒否でも、渡した状態・乱数・ログは変わらない |
| 変えていないこと | 一般の `RuntimeError`・`ValueError`・例外全体を `UnsupportedError` に変換しない。知っている再開先の正常な決定の処理。`check_invariants` は今までどおり問題の一覧を返す（例外にしない）。ゲーム状態全体の読み込みは加えていない |

### 3.3 範囲と限界

- 確かめるのは再開先（閉じた語彙）と前の版の決定の名前だけ。決定の種類はカードの実装が加える開いた語彙（試験の登録表の種類もある）なので、知っている再開先の下の知らない種類は、
  今までどおりそれぞれの確かめ（観測の `OPTION_MEANINGS` の `ValueError` など）のまま
- 書き出し（`state_to_dict`）は確かめを加えていない（書き出しは状態の値をそのまま書く。読む側が知らない種類を拒否する約束。4 章）
- 直せるのはこの版以降の扱いだけ。v0.139 以前は後の版の決定に答えると内部エラーになる（前の版のコードは変えない）
- pickle を安全な外部のデータ交換の形式として位置づけない（信頼できない写しを読み込まない。4 章）

## 4. 保存互換性

| 項目 | 内容 |
|---|---|
| 形式の番号 | 34 のまま。`prize_first` と `context` の `first` は、これまでと同じく種類の値と項目を加えただけ（`serialize.py` の説明に追記） |
| 既存の約束（明記した） | 形式の番号は書き出しの**形**の版で、決定の種類などの**値の語彙**の版ではない。読む側は、知らない形式に加えて知らない種類の値・項目を拒否する（同じ形式の番号でも、前の版の読む側が後の版の書き出しを読めるとは約束しない）。`serialize.py` のモジュールの説明と README に書いた |
| 書き出しと状態の写しの区別 | 書き出し（`state_to_dict`）は一方向で、エンジンに読み込む処理はない。状態の写し（pickle・deepcopy・clone）は別のもので、前の版の写しを後の版で読む向き（後方の互換）だけを考えてきた。後の版の写しを前の版で読む向きは約束しない。pickle は安全な外部のデータ交換の形式ではない |
| 既存の約束との矛盾 | 見つからなかった。ただし、v0.139 の `prize_order` を `prize_first` に改めたので、v0.139 の決定を待つ状態の写しはこの版で続けられない（明示的に拒否する。2.3 節）。v0.138・v0.139 の両方が取る途中のサイドの決定も続けられない（`StateIntegrityError`） |
| 旧版の制限 | v0.139 以前のエンジンは、この版の `prize_first` を待つ状態の写しに答えると内部エラー（v0.138 で確かめた `RuntimeError` と同じ作り）。前の版は直せない |
