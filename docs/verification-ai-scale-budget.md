### 2.2 メモリ（測定方法の限界）

- 値は、各局の `adapter.play` が返った直後（ファイルを書く前）に、バッチの道具が自分のプロセスについて `K32GetProcessMemoryInfo` で取ったものです。8 バッチとも同じ方法で、全局が measured でした。
- `PeakWorkingSetSize` はプロセスの開始からの累積の最大です。局ごとの固有のピークではないので、局ごとの分布としては扱いません。
- 各バッチのプロセスの最大は次のとおりです。
  - b1 170 MB、b2 345 MB、C1 193 MB、C2 348 MB（記録なし）
  - d1 244 MB、d2 227 MB、r1 798 MB、r2 370 MB（観測つき）
- 累積の最大が上がった局は、どのバッチでもそのバッチで証跡が最大の局でした（b2 の 11 局目・C2 の 14 局目・r1 の 3 局目は受理上限の局、r2 は 2 局目の 451 受理の局）。大きな局がメモリの上限を決めるという関係は記録と合いますが、局ごとに測ったものではありません。
- attempt の終わりの working set（その時点の値）は、大きな局のあと高いまま少しずつ下がりました。たとえば b2 は 11 局目のあと 255 MB で、99 局目は 155 MB です。99 局の範囲では、局が進むにつれて増え続ける様子は見られませんでした。それより多い局数では未確認です。
- r1 の約 798 MB は参考値です。実行の上限ではなく、マシンの空きメモリとの関係も未計測です。

## 3. 現行バッチの保持・保存・再開・上限の構造

`tools/verification_ai/batch.py`・`runner.py`・`observe.py`（`b8cd148` の木、`22a23a29` と同じ）を読みました。「事実」はコードに書いてあること、「推測」は実測していないことです。

### 3.1 実行中にメモリへ持つもの

- **事実（1 局のあいだ）**: runner は局が終わるまで、次をすべてメモリに持ちます。
  - `trace`（試みごとの記録）
  - `actor_logs`（主体ごとの要求と応答。行動する局面ごとに本人の観測 `view` を含む）
  - エンジンの完全な記録（`game.close()` の値）
  - 観測の記録が有効なら、`ObservationRecorder` の `rows` と 3 閲覧者分の閲覧用記録。閲覧用記録は、受理ごとに観測・新しいログを凍結した写しです。
- **事実（局の終わり）**: `EngineAdapter.play` は局の終わりに、上のすべてのファイルのバイト列を一度に作って `files` に入れます。そのあいだ `result` も生きています。
  - 書き込みが済むと `del output.files[:]` でバイト列を捨て、`result` は `play` の外へ出しません。
  - 局の途中でファイルへ少しずつ書くこと（ストリーミング）はしていません。
- **推測**: 1 局のピークは、局の大きさ（受理・観測の量）に比例して増えると見ています。2.2 節の一致と合う見方ですが、比率は測っていません。

### 3.2 観測の記録と通常の記録の重なり

- **事実**: 本人の観測は、`actors/<主体>.jsonl` に行動する局面ごとに入ります。観測の記録が有効なら、`observe/view-<主体>.json` にも開始と受理のたびに入ります。
  - 前者は行動する局面ごと、後者は受理ごとなので、同じ内容の全体の重複ではなく一部の重複です。
  - 観戦者の記録は `observe/view-spectator.json` だけにあります。対応表 `observe/rows.jsonl` は観測の sha256 とログの位置だけで、観測そのものは入りません。
  - ホストの完全な情報は `full_record.json` だけで、observe/ には入りません。
- **事実**: 保存のときに 2 つの記録を共有・参照する仕組みはありません。メモリでもディスクでも、それぞれのバイト列を持ちます。

### 3.3 次の局へ持ち越すもの

- **事実**: 局と局のあいだで持ち越すのは次のものだけです。
  - 計画（`plan`。全局の設定・デッキの記録を含む）
  - `scan` の状態
  - 台帳のオブジェクト
  - 証跡の量の整数
  - 実行した局の小さな要約の一覧（`report.ran`）
- **事実**: 観測の記録器は局ごとに作って捨てます。全局の観測をためません。
- **推測**: 大きな局のあとに working set が高いまま残るのは、Python のメモリの使い回しによるものと見ています。原因は確かめていません。

### 3.4 再開・集計で読むものとハッシュの照合

**事実（セッションの開始。`run_batch`）**: 次の順に読みます。

1. 台帳の全体
2. `plan.json` とその sha256、実装識別。実装識別には、道具の .py 全ファイルの sha256 とエンジンの識別が入ります。
3. 全局の `check_entry`。デッキの記録を作り直し、`deck_problems`・規約集合・方策の設定を照らします。
4. `scan`。完了マーカーのある attempt ごとに、マーカー・ファイル表・ディスクのファイルの一覧を照らし、表のすべてのファイルを sha256 で読み直します。

照合に失敗した局・計画にない局のディレクトリ・完了が 2 つある局があれば、`BatchRefused` で始めません。

**事実（集計）**: run の終わりに `aggregate` が同じ `load_plan`・`scan`（全完了局の全ファイルの再ハッシュ）を繰り返します。そのうえで、完了局ごとに `COMPLETE.json`・`result.json`・`judge.json` を読み、バッチのディレクトリ全体の大きさを数えます。集計だけの再実行も同じです。

**推測**: このため、1 回の run で完了局の証跡を少なくとも 2 回、全部読みます（開始の scan と終わりの集計）。再開ごとにさらに 1 回増えます。読む量は「その時点の完了局の証跡の合計」です。照合の時間は数百 MB 以上では未計測です。

### 3.5 上限を確かめる時点と、1 局の途中で超え得る範囲

**事実（時間）**

- 局を始める前に、`budget_seconds − 累積 < game_reserve_seconds（150）` なら止めます（`stopped_budget_time`）。
- 局の途中では、単局の上限 `Limits.seconds`（120 秒）を要求と要求のあいだで確かめます。エンジンの 1 回の呼び出しの途中では止めません。
- ほかの単局の上限は次のとおりです: operations 2000、accepted 1000、turns 200、同じ状態での拒否 16、選び直し 64。

**事実（証跡）**

- 局を始める前に、`evidence_max − 現在の量 < evidence_reserve（64 MiB）` なら止めます（`stopped_budget_evidence`）。
- 局のあとは、書く前に `現在の量 + その局の量 > evidence_max` を確かめます。超える場合は、その局のファイルを書きません。`INCOMPLETE.json`（`evidence_limit`）だけを残し、セッションを `stopped_evidence_limit` で止めます。このとき run の終了コードは 1 で、正常な停止の扱いではありません。

**事実（CLI）**: `plan` で変えられるのは `--max-games`・`--budget-seconds`・`--evidence-max-mb` だけです。`game_reserve_seconds`（150）・`evidence_reserve_bytes`（64 MiB）・`max_attempts_per_game`（3）・単局の上限は既定のままです。

**推測（時間）**: 最後に始まる局は、累積が `budget − 150` 以下の時点で始まります。その局と書き込み・照合が 150 秒以内に終われば、累積は予算を超えません。観測した最長の attempt は 45.4 秒です。単局の上限 120 秒とエンジンの 1 回の呼び出しの長さ次第では、超える可能性が残ります。集計の時間は累積に数えません。

**推測（証跡）**: 64 MiB の予備は、観測つきの受理上限の局（94.4 MB）より小さい値です。上限の近くでそのような局が出ると、時間を使ったうえで書かれずに `evidence_limit` で止まります。推奨案では見積もりと上限のあいだに余裕を取って、これを避けます（4.4 節）。

**事実（メモリ）**: メモリの上限はありません。`MemoryError` は対戦の結果に変えず、attempt を未完了のまま残して投げ直します。

### 3.6 150 秒の予備・累積時間と、分割実行・再開

- **事実**: 累積時間は、セッションごとの単調時計の経過の最大の合計です。再開で戻しません。
  - 開始の照合（2.3 節の 1.5〜1.9 秒）は累積に入ります。終わりの集計は入りません。
  - `session_end` のないセッション（異常終了）には、見込みとして 150 秒を足します。
- **推測（分割実行）**: `--stop-after-games` でセッションを分けると、セッションごとに開始の照合の時間が増えます。その照合で読む量は完了局の証跡の合計です。
- **推測（異常終了のあと）**: 150 秒が足されるので、予算の小さい計画では再開しても 1 局も始められないことがあります。たとえば 4.4 節の枠 B（420 秒）では、累積 120 秒を超えたあとに異常終了すると `120 + 150 > 270` になり、次の局は始まりません。

### 3.7 再実行の防止・停止の承認・ロック

- **事実（再実行の防止）**:
  - 照合に通った完了局は飛ばします。
  - 未完了の attempt は残したまま、次の番号の attempt で実行します。
  - attempt の数（未完了を含む）が 3 に達した局があると、`stopped_attempts_exhausted` で止まります。
  - 計画・識別・保存内容が合わなければ、黙って採用・再実行せずに拒否します。
- **事実（停止の承認）**: 停止方針で止めた局は、`--acknowledge-stop <局>` で台帳に書くまで再開を拒否します。
- **事実（ロック）**:
  - `LOCK` は `O_EXCL` で作ります。PID は記録するだけで、生死を調べて自動で外すことはしません。
  - 外すのは、自分のセッションの終わりか、`unlock --session` による利用者の操作だけです。
- この単位では、承認とロックの解除を自動化しません。推奨案にも入れていません。

### 3.8 reach の保護と時間

- reach の保護（目標を優先する最大 3 番）は、秘策でうらのカードを出したあとに始まります。始まる前は期限が進みません。
- r2 の g003・g004 は保護が始まらず、局の最後まで boundary のまま進みました。
- このため「最大 3 番」は、到達の試み全体の時間の上限ではありません。到達目的の局の時間・量は、通常の局と同じく単局の上限（120 秒・受理 1000 など）で決まります。

## 4. 次の実行計画（推奨案。現行の道具のまま実行できる）

### 4.1 方針

- 道具・エンジン・方策・判定規則・停止方針・既知停止の根拠は変えません。現行の `22a23a29` と同じ道具（TOOL_VERSION 8）で実行します。
- 枠を 2 つに分けます。観測の記録の有無で別の確定計画にし、1 プロセスずつ逐次に実行します。同時には走らせません。
- 合計は 42 局・900 秒・1792 MiB です（利用者の上限: 100 局・15 分・2 GiB）。100 局を埋めることは目標にしません。
- 上限に達したら、未着手を残して終わります。結果を見て seed を差し替える・局を足す・予算を延ばすことはしません。

### 4.4 予算の根拠（`estimate.json`）

見積もりは `(局数 − 1) × 典型 + 1 × 尾` です。典型は参照バッチの p90、尾は受理上限の局を含む観測した最大で、平均は使いません。「悲観」は全局が尾になる場合で、そのときは上限で止まり、未着手が残る想定です。

| 枠 | 典型の参照（時間・量） | 尾の参照（時間・量） | 時間の見積もり／窓（budget − 150） | 量の見積もり／窓（max − 64 MiB） | 悲観（時間・量） |
|---|---|---|---|---|---|
| A（30 局） | d1 の attempt p90 8.57 秒、r2 の observe/ を除く p90 17.7 MB | C2 の最大 26.72 秒・47.2 MB | 275.3 秒／330 秒 | 559 MB／738 MB | 801.6 秒・1415 MB（時間・量とも上限で止まる） |
| B（12 局） | r2 の attempt p90 16.70 秒・局の証跡 p90 37.3 MB | r1 の最大 45.44 秒・94.4 MB | 229.2 秒／270 秒 | 505 MB／1007 MB | 545.3 秒・1133 MB（時間・量とも上限で止まる） |

- **A の時間の参照**: d1 は同じ基のデッキ・同じ方式ですが、観測つきです。記録なしの枠 A には多めの側の値です。
- **A の量の参照**: d1 の p90 8.8 MB・b2 の 11.1 MB・C2 の 12.2 MB より大きい、r2 の値を使いました。
- **窓の余裕**: 見積もりは窓に対して、時間 A 55 秒・B 41 秒、量 A 約 179 MB・B 約 502 MB の余裕があります。
  - 典型の値だけで数えると、時間の窓の中で A は 39 局・B は 17 局まで始められます。
  - 典型の局が尾の局に置き換わると、1 局あたり A は約 29.5 MB、B は約 57.1 MB 増えます。量の余裕は、そのような局が A でさらに 6 局、B でさらに 8 局出ても足りる大きさです。
- **単局の上限**: 単局の上限（`runner.Limits` の既定）と 150 秒の予備は変えません。CLI では変えられません。
- **メモリ**: 枠 B では、r1 と同じ観測つきの受理上限の局が出ると、約 800 MB になる可能性があります（参考値）。上限は置きません。
- **時計の時間**: 累積に入らない集計（3.4 節）があるので、時計の上の所要時間は 900 秒を少し超えることがあります。集計の時間は未計測です。

### 4.6 実行の順と手順（次の実行の単位で行う）

1. 実行コミットを決めます。`tools/`・`kyuura_engine/` が `22a23a29` と同じことと、道具の識別 `dbca28bd…` を確かめます。

### 4.7 観測の記録の適用範囲と、確認できないこと

- 枠 A（記録なし）では、次を確かめられません。

- 枠 A で確かめられるのは、通常の記録（trace・actors・full_record）による判定・replay_run・終わり方・送信の範囲までです。
- 枠 B は観測の記録が必須ファイルです。欠け・矛盾は停止方針の `on_observation_problem: stop` で止まります。

### 9.2 実行の方法（1 局ずつ・局の間の容量確認）
