## 4. 受理・拒否の判断に使う情報と安全性の根拠

### 4.1 情報の区分

クイズ（v0.135・v0.136）では「正解・正解でないの両方の結果を確かめる」ことで答えに依存しない判断にしたが、山札の検索には「両方」に当たる有限の分岐がない（配分の可能性は
組み合わせの数だけある）。そこで、先に何を既知として判断できるかを分けた。

| 区分 | 内容 | この版の判断に使うか |
|---|---|---|
| 全員に公開されている情報 | 山札・サイド・手札の枚数、トラッシュ・場・スタジアム、おもてのサイド（ロケット団参上!）、山札のおもての枚数といちばん上（フラッシュ）、置いておくカードの枚数、公開のログ | 使う（山札の外の見えない枚数 C、おもてのサイドを除くこと） |
| 行為者だけが知っている情報 | 自分の手札、自分で並べたおもての山札のカード（`known_face_up`）、自分が所有するカードの集合（対戦開始時のデッキリストと、両者が見た所有者の変更。4.3 節） | 使う: 所有するカードの集合から見えるカードを除いたもの（本人に見えない自分のカードの集合）。使わない: おもての山札のカード（保守的。4.5 節） |
| 過去に見たことで知っている情報 | 前に山札をさがしたときに見た山札の中身、引いた・取ったサイド | 使わない（保守的。エンジンは見た情報の記録を持たない） |
| エンジン内部でしか分からない情報 | 山札とサイドの配分、山札の並び、乱数の状態、相手の手札・デッキリスト | 使わない |

### 4.2 下限の計算と前提

`effects.unseen_card_pool(state, player)` は、プレイヤーの「本人に見えない自分のカード」を 2 つに分ける。

- **山札のうら**: 山札から、フラッシュでおもてにしたカードを除いたもの
- **山札の外の見えないカード**: うらのサイド（おもてのサイドを除く）と、持ち主に見えない置いておくカード（くすぐりマシーンなど。`SetAsideCards.visible_to` に持ち主がいない）

`effects.deck_target_lower_bound(state, player, target)` は、2 つを合わせた中の目的のカードを K 枚、山札の外の見えないカードを C 枚として、max(0, K − C) を返す。

- 証明: 山札の外の見えないカードは C 枚しかないので、目的のカードのうち山札の外にあるのは多くて C 枚。残りの K − C 枚以上は山札のうらにある（鳩の巣の原理）。配分によらない
- 配分によらないこと: K は 2 つを合わせた集合だけ、C は公開の枚数（サイドの枚数 − おもてのサイド、置いておくカードの枚数）だけで決まる。どのカードが山札とサイドのどちらにあるかを読まない
- 実際の山札の候補の数とは別のもの: 実際の数は K − C 以上で、ちょうど等しいとは限らない（実際にはあっても下限が足りない場面を止める。5 章）。実際の候補の数を名前だけ変えたものではない
  （`LowerBoundTest.test_pigeonhole_bound` は、どの配分でも値が同じで、実際の数以下であることを確かめる）
- 必要な枚数: 選ばなくてよいと書かれていない検索は 1 枚、エネルギーアークはコインの枚数（2）。エネルギーアークは「おもて」の数（0〜2）によらず選べるよう、コインの前に 2 枚を確かめる
  （v0.80 からの「コインの結果で受け付けるかを変えない」をそのまま保つ）

下限が必要な枚数に足りなければ、既存のコード（ST1・FC1）のまま使う前に止める。理由の文は決まった文（`effects.DECK_TARGET_UNCONFIRMED_DETAIL`。実際の山札の枚数・カードの名前・位置を
書かない）。v0.136 までの FC1 の文が書いていた山札の枚数は書かない。

下限が足りれば山札に目的のカードが必要な枚数あるので、受け付けたあとの効果（`SearchDeckTrainer._search` など）が「使う前の確認の漏れ（エンジンの不具合）」の `RuntimeError` に
当たることはない。

### 4.3 持ち主が知っている集合（デッキリスト）について

K を求める集合（本人に見えない自分のカード）は、「自分が所有するカード」から「自分に見えるカード」を除いたものと同じ（カードは持ち主のゾーンにある。`check_invariants`）。

- 自分が所有するカード: 対戦開始時のデッキリスト（`new_game` に自分で渡した）と、所有者の変更（とりかえっこプリーズの交換。v0.130。交換した 2 枚は両者が手札を見て選んだもので、
  両者が知っている。観戦者は見ない）から決まる。延長戦の区間（v0.134）は所有者を最初のデッキにもどすので、デッキリストそのもの
- 自分に見えるカード: 自分の観測（手札・トラッシュ・場・スタジアム・使用中のトレーナー・見られる置いておくカード・おもてのサイド・自分で並べたおもての山札）

ただし、**デッキリストはエンジンの観測（`observe`）に入っていない**。エンジンの状態（`GameState.decklists`）にはあるが、プレイヤーに渡す観測・ログの写しには書かない。この版は
「持ち主は自分のデッキリストを知っている」（自分で渡した）ことを前提にした。比べる検査では、この前提を明示するため `twin_command_problems` に `owner_knowledge` を加え、比べる状態の
前提に「見る人が所有するカードの id の多重集合（`log_audit.owned_card_ids`）が同じ」を加えた。所有するカードの集合が違う状態（デッキリストが違う状態）は比べない（受理・拒否は
その集合に依存してよい、という前提を検査の側に書いた）。

- 公開の操作から再構成できるか: 持ち主は、デッキリストと自分の観測から再構成できる（`LowerBoundTest.test_pool_is_the_owned_cards_the_owner_cannot_see` は、合法な対戦の途中の状態で、
  見えない自分のカードの集合が「所有カード − 観測で見えるカード」と同じことを確かめる）。相手・観戦者は、デッキリストを知らないので再構成できない
- 「山札とサイドを合わせれば公開情報」とは扱っていない。合わせた集合は持ち主だけが知っている情報（行為者だけの情報）として扱う

### 4.4 受理・拒否を見られる相手・観戦者への影響

- **拒否**: 状態・乱数・ログを変えないので、相手・観戦者の観測・ログの写しには何も残らない（拒否はコマンドを送った人だけに返る）。送ったのが使ったプレイヤーなら、その人はもとから
  K・C を知っているので、新しく分かることはない
- **受理**: 使った事実（`play_trainer`）は公開。分類の時点の確かめでは、受理は「山札に目的のカードが必要な枚数ある」ことを相手・観戦者に伝えていた（選ばなくてよいと書かれていない
  検索では、そのあとの効果も同じことを示す）。この版の確かめでは、受理は「使ったプレイヤーの見えないカードのうち目的のカードが C + 必要な枚数以上ある」ことを伝える。どちらも使った
  プレイヤーの非公開の情報（デッキの構成）の 1 ビットで、相手は試せない（相手は使う宣言を送れず、拒否も見えない）。山札とサイドの配分は伝えない。ただし、この版のほうが伝える内容が
  強い（例: サイド 6 枚でボスのやりかたを使えば、見えない「わるい」進化カードが 7 枚以上あることが分かる）。これは**この修正で変わった、残る性質**として記録する（解消していない。
  受理の事実を相手・観戦者に伝えない方法はない。公開の情報だけで決めれば相手にも何も伝わらないが、その場合は実際にはほぼ使えなくなる）
- 錯乱ジムで相手が借りて使うとき（`borrow_unusable_reason`）は、借りたプレイヤーの K・C で確かめる。借りる答えの「選ぶと止める」印は観測に出ない（v0.57 からの扱いのまま）。借りた
  プレイヤーは自分の K・C を知っているので、新しく分かることはない

### 4.5 整合（所有者の変更・再交換・表向きのサイド・フラッシュ・カードの移動・延長戦）

| 場面 | 扱い |
|---|---|
| 所有者の変更（とりかえっこプリーズ） | 受け取ったカードは新しい所有者のゾーンに置く（v0.130）。新しい所有者の山札・サイドに入れば、その人の見えないカードとして数える（両者が交換のときに見たカードなので、持ち主は知っている。`OwnershipTest`）。再交換も同じ（もとの所有者へ自動でもどさない） |
| 表向きのサイド（ロケット団参上!） | 全員に見えるので、目的のカードでも K に数えず、C にも数えない（`test_face_up_prizes_are_neither_counted_nor_capacity`） |
| フラッシュ（おもての山札） | おもてのカードは K に数えない（保守的）。いちばん上より下のおもてのカードを手札へ移すと止まる FU3 があり、それしか候補がない場面で、受け付けたあとの続きの有無（`_trainer_dead_end`）が配分によることを避けるため。うらの山札だけで下限が足りる場面は今までどおり使える（`FaceUpDeckTest`） |
| 持ち主に見えない置いておくカード | C に数える（`test_hidden_set_aside_counts_as_capacity`） |
| カードの移動（引く・さがす・トラッシュ・山札にもどす） | 下限は確かめるときの状態だけで決まる（記録を持たない）。移動のあとは、その時点の集合と枚数で求め直す |
| 延長戦の区間（v0.134） | 今の区間の山札・サイド（1 枚）で求める。前の区間の記録は使わない（`SuddenDeathTest`） |
| 保存・復元（pickle・deepcopy・clone）・書き出し | 状態だけで決まるので、保存の前後で同じ（`PersistenceTest`）。書き出しの形式は変えていない |

## 5. 修正のあとも使える条件と、増えた制限

### 5.1 使える条件

| カード | 使える条件（ほかの使うための条件は今までどおり先に確かめる） |
|---|---|
| エネルギー転送 | 本人に見えない基本エネルギーカードの枚数 > サイドなど山札の外の見えない枚数 |
| ボスのやりかた | 本人に見えない「わるい」の進化カードの枚数 > 同上 |
| タケシの育て方 | 本人に見えない「タケシの」ポケモンの枚数 > 同上 |
| 遺跡の石版 | ベンチに空きがあり、本人に見えないアンノーン（たね）の枚数 > 同上 |
| エネルギーアーク | 本人に見えない基本エネルギーカードの枚数 ≥ 同上 + 2 |

例: 基本エネルギーカード 20 枚以上のデッキのエネルギー転送は、最初の番から使える（`LegalPathTest.test_rich_deck_accepts_from_the_first_turn`）。サイドが減るほど条件はゆるくなる。

### 5.2 増えた制限（情報漏れを防ぐための保守的な制限）

- 実際には山札に目的のカードがあっても、下限が足りなければ使う前に止める（`SafePathTest.test_over_rejection_when_the_target_is_actually_in_the_deck`）
- 遺跡の石版: アンノーンはデッキに合わせて 4 枚までなので、サイドが 4 枚以上ある間は使えない（見えないアンノーンが 4 枚でも、サイド 3 枚以下でないと下限が 1 にならない）
- ボスのやりかた・タケシの育て方: 目的のカードがサイドの枚数より少ないデッキでは、サイドが減るまで使えない（例: 道具のデッキ S53 は「わるい」の進化カード 2 枚なので、v0.53 の組では
  ボスのやりかたが使えなくなった。10 章の意図した差）
- エネルギーアーク: サイド 6 枚の間は見えない基本エネルギーカード 8 枚以上が要る
- これは**エンジンの制限**で、ST1・FC1 の研究上の論点を解決したのではない。止めるコードは既存の ST1・FC1 のまま（新しいコードは作っていない）

### 5.3 既存の動きとの違い
