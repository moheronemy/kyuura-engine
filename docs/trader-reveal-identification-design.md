## 2. 仕様と既存の公開の設計

**仕様**（[pokemon-trader-v0.24.md](pokemon-trader-v0.24.md)。p.259 の最新の説明）

| 段階 | 誰に | いつ | 根拠 |
|---|---|---|---|
| 手札からもどすカード | 相手 | 選んで、山札にもどす前（「相手プレイヤーに見せてから、あなたの山札にもどす」） | PT6 |
| 山札から選んだカード | 相手 | 選び出して、手札に加える前（「相手プレイヤーに見せてから、手札に加える」） | PT13 |
| 山札の選べるもの（ほかのカード） | 使ったプレイヤーだけ | 決定のあいだ | PT12 |

- 観戦者: 文面は「相手」だけを書きます。実装の約束では、`return_to_deck`・`reveal_from_deck` の `card` は「全員に見える情報」です（`zones.return_hand_to_deck`・`reveal_deck_to_hand` の説明）。
- 観測の約束では、公開の場所と公開のログは観戦者にも見えます（`observation.py` の冒頭）。観戦者を除く仕様上の根拠は見つかりませんでした。今回の設計も、観戦者を相手と同じに扱います。

**生成と配信**（コードの読み取り）

- 生成: `zones.return_hand_to_deck` が `{"kind": "return_to_deck", "player", "card": <uid>}` を書きます。`zones.reveal_deck_to_hand` は `{"kind": "reveal_from_deck", "player", "card": <uid>}` を書きます（ワザ・特殊能力のときは `effect`・`power` を足す）。
- 配信:
  - 2 つとも `observation.PUBLIC_EVENTS` で、`visible_event` はそのまま写します。カード ID は足しません。
  - 閲覧用記録（`ViewRecorder`）は、項目ごとにその時点の `visible_log` の写しと観測を保存します。
  - client_api（形式 1）の公開の更新（`ClientHub._on_result`）は `status` と `observation` だけで、ログの出来事を配りません。
- 観測:
  - 手札は持ち主だけに中身、山札は枚数だけ（uid も渡さない）です。
  - 公開の場所（トラッシュ・場・使用中のトレーナー）のカードには、uid とカード ID が並びます。
  - 見せたカードを残す項目はありません。
- GUI:
  - `web/src/state/logSummary.ts` は「エンジンの対戦ログ（visible_log）は client_api 形式 1 の応答に含まれない」として、更新の要約（枚数・段階など）だけを表示します。
  - カードの名前・画像は、カード ID からカードの定義（`server/kyuura_gui_server/card_definitions.py`）で引きます。

**uid がある ≠ 識別できる**: uid は、両方のデッキの入力の並びの位置です（`engine.new_game` で 0 から。構築盤面でも順に付く）。相手のデッキリストは公開されないので（[diagnostics-replay-api-design.md](diagnostics-replay-api-design.md)）、相手・観戦者にとって uid だけではどのカードかわかりません。

## 3. 構築盤面での再現（`scripts/repro_trader_reveal.py` → `out/repro_raw.json`・`repro_summary.json`）

**盤面**:

- 既存のテストの `tests/test_pokemon_trader_v0_24.board()` を、既定の引数のまま使いました（`tests.helpers.build_test_state`）。
  - 使用者（プレイヤー 0）の手札は交換おじさん・ジュゴン・炎エネルギー、山札は 5 枚（フシギソウをふくむ）です。
- `check_invariants` の問題は 0 でした（各時点でも 0）。
- もどすカード（ジュゴン）と探すカード（フシギソウ）について、同じカード ID の別の 1 枚が、使用前に相手・観戦者へ公開されていないことを確かめました（どちらも 0 枚）。
- 構築盤面なので、new_game からの到達の実績には数えません。元の w1 は replay・再実行していません。

**進め方**:

- `ClientHub.from_state`（公開の更新を作る正規の入口）の `ActionHost` のプレイヤーのセッションで進めました（候補 → 入力 → 送信）。3 回とも受理されました。
- 閲覧用記録は、3 閲覧者の `ViewRecorder.attach` に、ホストの結果を順に渡して作りました。

**時点ごとの結果**（識別 = その閲覧者に届いた観測・更新・ログ・閲覧用記録のどこかで、その uid とカード ID が同じ値に並ぶ。完全な記録は根拠に使わない）

| 時点 | 新しい公開ログ（3 閲覧者で同じ） | 使用者: もどす／探す | 相手: もどす／探す | 観戦者: もどす／探す |
|---|---|---|---|---|
| T1 使用前 | なし | 識別（自分の手札）／しない | しない／しない | しない／しない |
| T1b 使用の受理の直後（選ぶ前） | `play_trainer` | 識別／しない | しない／しない | しない／しない |
| T2＝T3 もどすカードを選んだ直後（山札から選ぶ決定のあいだ） | `return_to_deck`（`card` が uid だけ） | 識別／選べるものとして見える | **uid は出るが識別できない**／しない | **同じ**／しない |
| T4 探したカードを手札に入れた直後 | `reveal_from_deck`（`card` が uid だけ）・`shuffle`・`discard_trainer` | 識別／識別 | **識別できない／uid は出るが識別できない** | **同じ** |

- T2 と T3 は同じ状態です（もどす答えの受理で、次の決定が出る）。
- 公開の更新は、各受理のあと 3 閲覧者に 1 件ずつ届きます。中身は `status` と観測だけで、出来事はありません。
- 早すぎる公開はありませんでした。使用前・選ぶ前に、もどす・探すカードの uid は出ていません。
- 両方の段階で、相手・観戦者は「見せたカード」の uid を受け取りますが、どのカードかを識別できません。w1 の観察（もどすカード）と同じ形で、探したカードでも同じでした。

## 5. uid の方式との関係

| 論点 | 整理 |
|---|---|
| デッキリストの公開の範囲 | 使用者は自分のデッキを知っています（閲覧用記録の見出しの `own_decklist` は、カード ID の組を並べかえたもの）。相手・観戦者には渡しません |
| uid の公開の範囲 | 非公開の場所（手札・山札・サイド・相手のうら）のカードの uid は、観測にもログにも出しません（観測の約束・`PRIVATE_FIELDS`・`_mask_face_down`）。公開の場所のカードは、uid とカード ID が並んで出ます |
| 1 枚の（uid, カード ID）から、ほかの非公開のカードが特定できるか | uid は入力の並びの位置で、同じカードの写しは並びで続きます（明示リストの `entries-in-order`）。そのため、u がカード X とわかると、隣の uid も X かもしれない、という推論はできます。<br>ただし、非公開のカードの uid は相手・観戦者に渡らないので、推論を当てる相手がいません。隣の uid が出るのは、そのカードが公開の場所に出たとき（カード ID も一緒に出る）か、見せる出来事に出たとき（本来公開してよいカード）だけです |
| 外部で既知のデッキ | 固定デッキ（`decks.py` の公開のもの）を相手が使っていると知っていれば、uid の並びからカードがわかります。これは今の設計でも同じで、今回の変更で増えません |
| 既存の公開による推論と、今回の追加の違い | 今回足すのは「見せる指示があるカードの、その時点のカード ID」だけです。見せるカードは、文面上相手が知ってよい値です。足した値から非公開のカードの uid が新たに届くことはありません |

- **結論**: 公開の 1 枚を識別させる変更で、情報の境界は保てます。設計を止める根拠は見つかりませんでした。uid の方式は変えません。
- ただし、固定デッキを外部で知っている場合の推論は、今の設計の前提のまま残ります（今回の範囲の外）。

## 6. 修正方式の比較と推奨

| 比べる項目 | A. 公開の出来事にカード ID を足す | B. 観測に見せたカードを足す |
|---|---|---|
| 公開の時点と公開先 | 出来事が書かれる時点（見せる時点）に、`PUBLIC_EVENTS` の既存の配信で全員へ。正しい | 観測は状態から作るので、状態に「見せたカード」を持たせる必要がある。いつ消すかの規定が要る（次の受理で消すなど） |
| もどす・探すの両方 | 2 つの出来事のそれぞれで扱える | 1 回の受理の中で 2 枚（もどす・探す）が別の時点で出るので、決定のあいだの観測と受理のあとの観測に分けて持つ必要がある |
| 過去のログを後の状態から作り直さない | 出来事そのものに、その時点の値を持つ。閲覧用記録は書いた時点の値のまま | 観測は今の状態から作るので、過去の時点の表示には閲覧用記録の観測を使う。状態の項目を消したあとは作り直せない |
| ほかの非公開の検索への影響 | 生成の関数に、呼ぶ側が指定する引数で足すだけ。パソコン通信（`search_deck`）は別の関数で影響しない | 観測の新しい項目の約束を、すべての見せる効果について決める必要がある |
| 出来事・観測・閲覧用記録・GUI | 出来事に 1 項目。観測・閲覧用記録の形は同じ（記録の中の出来事に項目が増える）。GUI は今、client_api でログを受け取らないので、表示には別の段階が要る | 観測の形が変わる（client_api・GUI の検証の型・閲覧用記録の観測） |
| full replay・snapshot・実装の識別・版 | ログの中身が変わる（behavior の識別・P1/P3 の basis が変わる。版を上げる）。状態の項目は増えない | 状態の項目が増え、snapshot の形式・状態の指紋も変わる |
| 古い記録・項目のない出来事 | 項目がなければ「識別の情報なし」として扱う（推測しない） | 項目がなければ同じく扱う |

**推奨: A**。理由は次のとおりです。

- 出来事がその時点の値を持つという、既存の形（`quiz_reveal`・`quiz_kind_reveal`・`bench_as_basic` などは出来事にカード ID を書く）に合います。
- 状態・snapshot の形を変えません。
- 閲覧用記録の時点の値を保てます。

**推奨の仕様**（実装の単位で、そのまま書ける粒度）

1. **項目**: 出来事に `card_id`（文字列。その時点の `state.cards[card].card_id`）を 1 つ足します。
   - 名前・画像は足しません（カード ID からカードの定義で引ける。GUI はカードの定義を持っている）。
   - `card`（uid）・ほかの項目・出来事の順は変えません。
2. **生成の箇所**: `zones.return_hand_to_deck` と `zones.reveal_deck_to_hand` に、キーワードだけの引数 `identify: bool = False` を足します。真のときだけ `card_id` を書きます。
   - `effects.TradePokemonWithDeck`（`effects.py` の呼ぶ箇所 2 つ。もどす・手札に加える）だけが `identify=True` を渡します。
   - ほかの 8 の呼ぶ箇所は変えません（`SearchEvolutionCardToHand`・`SearchDeckTrainer`・`LookTopTakePokemonThenShuffle`・`SearchNamedFromDeckOrDiscard`・`CoinsSearchBasicEnergyPerHeads`・`ReturnHandEnergyThenCoinSearchBasicEnergy`（2）・`RevealDeckTopTakeSameNamed`）。これらは別の単位で文面を確かめてから判断します。無条件には広げません。
   - カード ID による分岐は、エンジン・`resolution/` に加えません。引数は効果の実装が渡します。
3. **配信**: 変えません。`PUBLIC_EVENTS` のまま、`visible_event` がそのまま写すので、相手・観戦者・使用者に同じ値が届きます。`PRIVATE_FIELDS`・`_mask_face_down` も変えません（見せるカードはうらでない）。
4. **新旧の出来事**: `card_id` のない `return_to_deck`・`reveal_from_deck`（0.181.0 以前の記録・ほかの効果の出来事）は、「見せたカード（記録に識別の情報なし）」として扱います。
   - 後の観測・完全な記録・デッキの並びから補いません。
   - 閲覧用記録・保存済みのログは書きかえません。
5. **GUI**: 今の GUI は client_api 形式 1 で出来事を受け取らないので、この項目だけでは表示が変わりません。
   - 表示するには、client_api が公開の更新にその受理の `visible_log` の写しを足すことが前提です。これは別の設計の単位で、情報の約束・形式の版を決めます。
   - その前提のもとで、GUI は `card_id` があればカードの定義で名前・画像を出し、なければ「見せたカード（識別の情報なし）」と出します（推測しない）。
6. **版**:
   - エンジンの振る舞いの識別（`effects.py`・`zones.py`）が変わるので、版を上げます（0.182.0 の想定）。
   - 検証用 AI の P1・P3 の basis（どちらも `effects.py`・`zones.py` をふくむ）が変わります。
   - 道具のコードを変えなければ `TOOL_VERSION` は同じです。ただし計画の識別が変わるので、新しい計画で実行します。
   - 新しいゲームの処理の裁定は入れません。
