[仕様](verification-ai-design.md)・[実装計画](verification-ai-implementation-plan.md) の V2 を実装しました。目的は勝率の向上ではなく、対戦を深く進めながらランダムの行動も交えて、
エンジンの問題を見つけることです。V3 以降（`boundary`・`negative`・双子・広い対象・最小化）は開始していません。V1 の内容は [verification-ai-v1.md](verification-ai-v1.md)。

この文書の 1 章〜5 章は対戦の実行の前に書き、コードと同じコミットに入れました（優先順位・混合の単位・計画を結果を見て変えないため）。6 章以降は実行のあとに書きました。

## 2. 共通の経路と責任の分け方

ランダム・ルール・混合は、同じ行動生成（`actions`）・check・submit・記録・計測（`runner`・`records`・`metrics`）を使います。違うのは方策（`policies`）の `choose` だけです。

- 方策は候補の順位と選択を決める。行動生成は段の契約を解釈する。合法性と実行の結果はエンジンに任せる
- 方策に渡すのは、その主体の入口の応答（JSON）だけ。完全な状態・相手の秘密・内部の乱数を参照せず、エンジンの試行・状態の複製による先読みをしない
- ルールの方策が読むのは候補の `kind` だけ。カード名・カード ID・効果の型・入力の中身・処理可能性を読まない（範囲の選択はランナーの `deep` のまま）
- 費用の不足のにげる（V1 の 7.2 節）などの選び直しは、今回の効率の改善の対象にしない（既存の選び直しの上限と計測のまま。合法性を戦略の側へ移さない）

## 3. rules-v1（候補の種類の優先順位）

### 3.1 採用した順序

| 順位 | 種類 | 理由 |
|---|---|---|
| 1 | `play_basic` | 場のポケモンを増やす（あとの進化・エネルギー・ワザの対象が増える） |
| 2 | `evolve` | 場のポケモンを進めて、ワザ・特殊能力の経路を増やす |
| 3 | `attach_energy` | ワザの費用に近づく |
| 4 | `use_attack` | ワザ・きぜつ・サイド・バトル場に出す決定・終局の経路へ進む（対戦を深くする） |
| 5 | `play_trainer`・`use_power`・`use_stadium`・`retreat`・`remove_disguise`・`discard_from_play`・`reveal_face_down`（と `check_face_up_deck`。ただし表示だけなので範囲の選択で先に外れる） | ほかの送信できる操作。同じ順位で均等 |
| 6 | `end_turn` | ほかに範囲の中の候補がないときだけ番を終える |

- 同じ順位の候補が 2 つ以上なら、方策の乱数（均等の方策と同じ種の導き方 `player_seed`）で均等に 1 つを選ぶ（理由のコード `rule:priority<n>:<種類>:tie<数>`）。1 つなら乱数を使わない
  （`rule:priority<n>:<種類>`）
- 表にない種類だけの場面（準備の `place_starting`・`mulligan_draw`、決定の回答の `answer_decision`・`take_prize`・`promote_active`）では優先順位を当てはめず、均等の方策と同じ
  選び方で選ぶ（`rule:fallback:no_priority`）。ホストの係（`report_janken`・`start_sudden_death`）は、どの方策でも V0・V1 と同じ均等の方策（ホストの種）
- 入力（段の選択）は uniform-stage のまま（V1 の 3.1 節）。V2 は入力の中身の戦略の評価を加えない
- 既存の設計の案（仕様 3.3 節）との違い: 仕様はワザを `play_trainer`・`use_power` のあと（順位 6）、バトル場へのエネルギーの優先、ワザのダメージの表示による選択、
  バトル場に出す決定のエネルギーの枚数による選択を挙げていた。V2 は利用者の出発の案（ワザをほかの操作より先）を採り、入力の中身の評価（つける先・ワザ・出すポケモン）は入れない。
  ワザは番を終える操作なので、順位 4 にすると、ワザが範囲にある番ではトレーナー・特殊能力（順位 5）は選ばれない。この偏りは混合（ε）のランダムの選択で一部を戻す

### 3.2 止まり方（既存のまま）

- ワザを選べない（範囲の中にない）番では、順位 5 の操作を選び、なければ `end_turn` を選ぶ
- 特殊能力などが繰り返し受理されて番が進まないときは、既存の上限（操作 2,000・受理 1,000・番 200・時間 120 秒）で止まる。同じ状態での拒否・選び直しは既存の
  `no_progress`（16・64）で止まる

## 4. 混合の方策（`mixed`）

### 4.1 混合の単位: 選択のエピソード

- **エピソード** = 1 つの状態での 1 つの主体の行動の選択（ランナーの `_act` の 1 回）。始まりで、混合の乱数を 1 回引き（`random() < ε` ならランダム、そうでなければ rules-v1）、
  エピソードのあいだ方式を固定する
- エピソードの区切り: 受理（状態が進む）・対戦の終わり（終局・停止・上限）・同じ状態での拒否・選び直しの上限（`no_progress`）
- 入力を作れない・check の invalid・送信の拒否・断りのあとの選び直しは、状態が変わらないので**同じエピソードのまま**で、混合の判定を引き直さない（都合のよい引き直しを
  隠さない）。選び直しの回数はエピソードの記録の `attempts` に残る
- 段の選択の途中で方式を変えない（ランダムのエピソードは候補も入力も均等、ルールのエピソードは候補が優先順位・入力が均等）
- ホストの係のエピソードは、どの方策でも均等（混合の判定をしない）

### 4.2 乱数

| 乱数 | 種 | 消費の単位 |
|---|---|---|
| ゲームの乱数 | `game_seed` | エンジンだけ |
| 混合の判定 | `kyuura-vai-v2:mix:<policy_seed>:<player>`（`mix_seed`） | プレイヤーのエピソードごとに 1 回（`random()`） |
| 候補・入力の選択 | `kyuura-vai-v0:player:<policy_seed>:<player>`（V0・V1 と同じ `player_seed`） | 均等の方策と同じ（候補 1 回・段の選択ごと）。ルールの同順位の選択も同じ乱数から 1 回 |
| ホストの係 | `kyuura-vai-v0:host:<host_seed>`（V0・V1 と同じ） | ジャンケン |

候補・入力の選択の乱数を 1 本にしたので、ε = 1 の混合は均等の方策と同じ列、ε = 0 は rules-v1 と同じ列になります（テストで確かめる）。均等の方策はエピソードの始めに乱数を
使わないので、V0・V1 の選び方は変わりません。

### 4.3 記録

試みの記録（`trace.jsonl`）に `type: "episode"` の行（エピソードの番号・主体・状態・方策の名前・方式 `mode`・混合の乱数の値 `draw`・ε・試みの数 `attempts`・結果 `result`）を加え、
各試みの行に `episode` の番号を入れます。選んだ理由のコード（`candidate_reason`）は試みの行にあります。結果の `policies` に方策の名前・版・分布・種・ε・混合の種・方式ごとの
エピソードの数を残します。意味の列（`meaning_sequence`）は試みの行だけから作るので、V0・V1 の比べ方は変わりません。

## 5. 計測と実行の計画

### 5.1 ランダムの基準（V1 の uniform-stage の 3 局）の再利用

再利用します。根拠:

- V1 の実行（`5d5e04e`）から V2 で変えたのは、方策の作り分け（`make_policies`。均等の方策は同じ型・同じ種・同じ分布）、エピソードの始めの呼び出し（均等の方策は乱数を使わない）、
  エピソードの行の追加（意味の列・記録の対応・数え直しは試みの行だけを読む）、サイドの枚数の変化の計測（公開の観測を読むだけ）。均等の選択の経路（範囲・候補の選択・
  入力の組み立て・check・submit）と V1 の計測の意味は変えていない

  `replay_run`）と比べる
- 再利用した 3 局は、V2 で加えた計測（エピソード・サイドの枚数の変化）を持たないので、比べる表では欠測（`unmeasured`）とする。表を埋めるための再実行はしない

### 5.2 比べる値

種類、ワザ・サイドを取る決定・バトル場に出す決定の受理、公開のサイドの枚数の減少、選び直し・`no_progress`・既知の停止・上限、混合で実際に使った方式の内訳。
**きぜつは未計測**（公開の応答・更新の観測から確実に数えられない。推測しない）。勝ちは参考値です。

### 7.2 rules-s13 の `limit_accepted`（方策による繰り返し）

rules-s13 は、7 番目の番の途中で受理 1,000 に届いて止まりました。最後の 200 回の受理はすべてフシギバナのエナジートランス（`use_power`。自分の場の「草」エネルギーを
別の自分のポケモンへつけかえる）で、エネルギーを場のポケモンのあいだで行き来させ続けていました。rules-v1 では `use_power`（順位 5）が `end_turn`（順位 6）より先なので、
エナジートランスを使える限り番を終えません。

- エンジンの拒否・停止・不整合は起きていない（どの送信も受理され、`replay_run` は `succeeded`）。カードの効果の上の回数の制限がない特殊能力を、方策が繰り返した
- 既存の上限（受理 1,000）で止まり、終わり方は `limit_accepted` として記録された。`no_progress` にはならない（状態が毎回変わる）
- V2 では、結果を見て優先順位を変えていない。繰り返しを防ぐ規則（同じ番の同じ種類の回数の上限など）は、V3 へ進む前の判断の材料（9 章）

### 7.3 計測の不具合（`e9fc20b` の実行）

- 公開のサイドの枚数の変化を、終わり方の判定のあとで数えていたので、終局の観測の変化（最後のサイドの減少）を数えていない。mixed-s13 の「プレイヤー 0 が 5」は、サイドを取る決定の
  受理 6 回より少なく、下限として読む。`6d6564f` で数える順を直した（テスト `PrizeTest.test_change_seen_with_game_over_is_counted`）。表を埋めるための再実行はしていない
- 局の見出し（`header.json`）に `policy`・`epsilon` の項目がない（`run_v1.game_header` の置換が効いていなかった。`6d6564f` で直した）。方策の名前・版・ε・混合の種・方式ごとの
  エピソードの数は、各局の `result.json` の `policies` と `plan.json` にある
- きぜつは未計測（5.2 節）
