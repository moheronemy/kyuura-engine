# 同時のきぜつ（v0.2f）: 原典照合と実装

1 つのワザで両方のプレイヤーのポケモンがきぜつしたときの処理（きぜつの判定、トラッシュ、サイドを取る順番、勝ち負け、バトル場に出す順番）について、原典で確かめたこと、実装上の判断、テストを対応づけた記録です。v0.2f のピカチュウ「でんげき」（[pikachu-v0.2f.md](pikachu-v0.2f.md)）で、相手の対戦ポケモンと自分のピカチュウが同じワザできぜつすることがはじめて起こるようになりました。自分へのダメージの規定は [self-damage-v0.2f.md](self-damage-v0.2f.md)、設計は [architecture-v0.2f.md](architecture-v0.2f.md) にあります。

- 基準のルール: 「ポケットモンスターカードゲーム公式ルール 2000.02.14版」（『ポケモンカードオフィシャルブック2000』pp.306〜326 [P43]、kyuura `NEO-2000-OFFICIAL-RULES`。kyuura の記録 `knockout_timing`・`sudden_death`）
- 照合の方法: Internet Archive のスキャン [J38] の PDF からページを画像にし、目で読んだ（2026-10-12。p.311 の表と pp.323〜324 は 300dpi で拡大）。OCR の文字は位置を探すのに使っただけ
- 読んだページ: p.311（勝ち負けが決まるとき・表）、p.312（サイドカード・トラッシュ）、p.323〜324（16 ポケモンの「きぜつ」、17 サドン・デス）、p.325（23 同じタイミングで起こったことの順番）、p.309（ワザを使う手順 6）

分類は CONFIRMED（原典に直接の根拠がある）・SUPPORTED（確定した規則から導出できる）・UNRESOLVED（決められない）・CONFLICT（資料のあいだで矛盾）です。

## 3. 処理の順番

ピカチュウ（プレイヤー 0、番）が「でんげき」を使い、相手の対戦ポケモンが 30 で、ピカチュウが「うら」の 10 で HP に達した場合です。

| # | 処理 | ログ | 根拠 |
|---|---|---|---|
| 1 | 相手の対戦ポケモンに 30 | `damage`（相手） | p.320 |
| 2 | コインを 1 枚投げる | `coin_flip` | p.125 |
| 3 | 「うら」なら自分に 10 | `damage`（`target: "self"`） | p.125・p.320 |
| 4 | きぜつの判定（場のすべてのポケモン） | — | p.323・p.324 |
| 5 | 相手のポケモンをトラッシュ | `knock_out`（プレイヤー 1、`simultaneous: true`） | p.323 |
| 6 | 自分のピカチュウをトラッシュ | `knock_out`（プレイヤー 0、`simultaneous: true`） | p.323 |
| 7 | プレイヤー 0 がサイドを 1 枚取る（決定 `take_prize`） | `decision`・`take_prize` | p.323 |
| 8 | プレイヤー 1 がサイドを 1 枚取る（決定 `take_prize`） | `decision`・`take_prize` | p.323 |
| 9 | 勝ち負けの判定（p.311 の表） | 決まれば `game_end`（`outcome` が `win` か `sudden_death`）。以下の処理はしない | p.311・p.324 |
| 10 | プレイヤー 1（番でない）がバトル場に出す（決定 `promote_active`） | `decision`・`promote_active` | pp.323〜324 |
| 11 | プレイヤー 0（番）がバトル場に出す（決定 `promote_active`） | `decision`・`promote_active` | pp.323〜324 |
| 12 | 番の終わり（期限のきたトレーナーをトラッシュ）→ 次の番 | `turn_end`・`turn_start` | p.309 |

- 決定は一度に 1 つ（`GameState.decision`）。サイドの決定の `context` の `remaining` に残りのプレイヤーの並び、バトル場の決定の `remaining` に残りの出す順を持ちます（v0.2a の仕組みのまま。新しい段階や保留中のリストは作っていません）。
- 7〜11 のあいだは、両方のバトル場が空のことがあります。不変条件は、対戦中のバトル場の空きを `TAKE_PRIZE`・`PROMOTE_ACTIVE` の段階だけに許し（終わった対戦は除く）、出す決定の並びに空きのあるプレイヤーが全員入っていることを確かめます。
- 7〜11 のあいだに、ほかのコマンド（ワザ、番の終わり、トレーナー、にげる、`TakePrize` の取り直しなど）は受け付けません（`WRONG_PHASE`・`NOT_YOUR_DECISION`・`WRONG_DECISION`。状態も乱数も変わらない）。
- 6 のあと、勝ち負けが決まらなくても、サイド・判定・交代のどこでも乱数は使いません（`test_no_randomness_after_the_coin`）。

## 4. 「順番を選ぶ」と「先に行う」の区別

原典には性質の違う 2 種類の「順番」が出てきます。

| 事項 | 原典 | 種類 | 実装 |
|---|---|---|---|
| バトル場に出す順番 | pp.323〜324「今が自分の番でないプレイヤーがまず、…今が自分の番のプレイヤーは、それを見てから」 | **ルールが決めた順番**。だれも選ばない | 固定（番でないプレイヤー → 番のプレイヤー）。番のプレイヤーの決定は、相手が出したあと（ログ `promote_active` が残ったあと）に出す |
| 両方がサイドを取る順番 | 明文はない。p.325「23」の一般の規定 | **番のプレイヤーが選ぶ順番**（「それらを処理する順番を、そのとき番をおこなっているプレイヤーが決めます」） | 選ぶ決定は出さず、番のプレイヤー → 相手 に正規化（5 章） |
| トラッシュする順番 | p.312（トラッシュに順番はない） | 結果に表れない | 相手 → 自分（ログの順だけ） |

「番のプレイヤーが先」と「番のプレイヤーが順番を選ぶ」は別のことです。バトル場に出す順番は前者でも後者でもなく「番でないプレイヤーが先」と決まっています。サイドの順番は後者で、エンジンは選ばせずに 1 つの並びに決めています。この正規化は「番のプレイヤーが先に取る」というルールを主張するものではありません。

## 5. サイドを取る順番を正規化してよい理由

p.325 によれば、両方がサイドを取る順番は番のプレイヤーが決めます。エンジンはその選択を決定として出さず、番のプレイヤー → 相手 の順に決めています。どちらの順番を選んでも、次のとおり何も変わらないためです。

1. **選べるもの**: 各プレイヤーは自分のサイドから選ぶ（p.323）。相手が取っても自分のサイドの枚数・位置は変わらないので、選べる位置は同じ。
2. **情報**: サイドは表を見ないで選び、取ったカードを相手に見せる必要はない（p.312）。先に取ったプレイヤーのカードはそのプレイヤーの手札に入り、後に取るプレイヤーが自分のサイドを選ぶのに使える情報は増えない（自分のサイドの内容は見られない。p.312）。
3. **乱数**: サイドを取る処理は乱数を使わない（プレイヤーが位置を選ぶ）。
4. **結果**: 勝ち負けはすべてのサイドを取ってから判定する（2 章 #5）。1 人目が取り終えた時点で判定しないので、順番で勝敗は変わらない。
5. **違い**: ログの `take_prize` の順番（と決定の番号）だけ。

テスト `PrizeOrderTest` は、エンジンの内部の関数（`engine._next_prize_or_judge`）に逆の並び（相手 → 番のプレイヤー）を渡し、選べるサイドの位置と、両方のプレイヤーの領域（手札・サイド・場・トラッシュ）・段階・番・結果・乱数の状態が同じになることを確かめています。

**前提**: p.312 は「カードに書かれている内容によって、相手のポケモンの「きぜつ」に関わらずサイドカードを取ったり、サイドカードを増やしたりすることもあるかも知れません」とします。サイドを取ることで何かが起こるカード、サイドを見る・入れ替えるカード、サイドの枚数で効果が変わるカードは、対応カードにありません。これらを加えるときは、この正規化が成り立つかを見直し、成り立たなければ p.325 の選択（番のプレイヤーが順番を選ぶ決定）を実装します。

1 匹のきぜつに 1 枚のサイドを取り、残りのサイドより多くは取りません（v0.1 から）。v0.2f の対応カードでは、1 つのワザできぜつするのは各プレイヤー 1 匹までです（ベンチへのダメージは未実装）。

## 6. 勝ち負け（p.311 の表）

表の列は「あなたがサイドカードをすべて取った」「相手がサイドカードをすべて取った」「あなたの対戦ポケモンが出せない」「相手の対戦ポケモンが出せない」です（画像で読み、tests/test_judge.py `TABLE_P311` に写した）。

| 行 | あなたが取った | 相手が取った | あなたが出せない | 相手が出せない | 結果 |
|---|---|---|---|---|---|
| 1 | ● | | ● | | サドン・デス |
| 2 | | ● | | ● | サドン・デス |
| 3 | ● | ● | ● | ● | サドン・デス |
| 4 | ● | ● | | ● | あなたの勝ち |
| 5 | ● | | ● | ● | あなたの勝ち |
| 6 | ● | | | ● | あなたの勝ち |
| 7 | ● | ● | ● | | あなたの負け |
| 8 | | ● | ● | ● | あなたの負け |
| 9 | | ● | ● | | あなたの負け |

表にない組み合わせは本文で決まります（1 条件だけなら、その条件のとおり。両方が同時に取り終えた・両方が出せないならサドン・デス）。`judge.decide` は、各プレイヤーが満たした条件（自分がサイドを取り終えた・相手が出せない）の数を比べ、多いほうの勝ち、同じならサドン・デスとします。この規則で表の 9 行と本文の場合がすべて合うことを v0.1 で確かめています。

v0.2f では、でんげきの同時のきぜつで 9 行すべてが起こります（`WinTableTest.test_every_row_of_the_table`。あなた = 番のプレイヤー。「取った」は残りのサイドを 1 枚、「出せない」はベンチを空にした盤面）。

サドン・デスは判定だけです。延長戦（すべてのカードを戻し、サイド 1 枚で最初からやり直す。p.324）は未実装で、`Phase.SUDDEN_DEATH` で止まり、以後のコマンドは `SUDDEN_DEATH_NOT_IMPLEMENTED` で拒否します。延長戦を実装するときに、ジャンケン・切り直しをやり直すか、延長戦の中の勝利条件をどう扱うかを p.324 の文面から読み方を決めます。
