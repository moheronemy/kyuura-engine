# v0.88 のテスト整理

2026-10-23。基点は main の `ccf5ca202d5ddad5902c67e0a5d3c26f1105d55f`（v0.88 の `b43a3e5` と同じ木）。作業ブランチは `codex/test-organization-v0.88`。

## 整理した範囲

現在のカード総数・種類別の数・登録数・スタジアム数・未対応数・研究の総数・最新の保存形式の期待値を `tests/test_catalog_contract.py` に集約した。期待を下限に変えていない。既存のカードごとの登録・出典・文面・動作の検査は残した。

全体の数だけを繰り返していた 14 メソッドを集約した。専用の契約テスト、版の範囲を切り出す補助処理、計測用ランナーの検査は計 11 メソッドを追加した。対戦・監査・情報漏れ・コイン・決定の再開・保存と復元の回帰ケースは削っていない。

後続の版の `pool_v0_74`、`pool_v0_75`、… を手で列挙していた箇所は、`tests/release_catalog.py` の版の比較で選ぶようにした。数字の大小、接尾辞、後から追加される版、不正な名前を検査する。これは登録カードの集合の範囲であり、過去のエンジンの挙動の再現ではない。

v0.71 のカタログ件数の検査は、v0.72 の 43 枚まで含む 756 枚から、v0.71 自身の 713 枚を確かめる形に直した。v0.71 の 78 枚の登録を除くと 635 枚になる。現在の全体の数は専用テストで引き続き厳密に確かめる。

登録を除く v0.83・v0.84・v0.88 の検査は、全体の件数の引き算ではなく、対象のカードの集合だけが失われることを比べるようにした。

## 保存形式

最新版の番号を繰り返し固定していた検査は専用テストへ集約した。旧形式で特定の項目を表せる・表せないこと、保存して復元した結果が同じことの検査は維持した。存在しない形式は固定の 24 ではなく `max(FORMAT_VERSIONS) + 1` で試す。

`tests/log_audit.py` の `LATEST_FORMAT` と項目の表は実装と独立したまま残し、専用テストで実装との一致を確かめる。実装から番号を自動取得して監査の更新漏れを隠す形にはしていない。

## 期待値の準備の読み込み

`tests/test_effects.py` の 14 の期待値リストが、各カードについて同じ 2.7 MB の JSON を読み直していた。カード 1,091 枚に対して `14 × (1 + 1,091) = 15,288` 回の読み込みになる。このリストの準備に限って、一度読んだデータを使う形にした。テストに渡す状態や、変更するテスト用データを共有する変更ではない。

旧式のリスト内包表記を、同じ固定データを返す読み込み関数で評価し、呼び出し数を数えた。新しい式と比べ、14 リスト・490 ワザのキーが順番を含めて一致した。準備の読み込みは 1 回になった。旧式の収集を完了まで計測していないため、速度の倍率は報告しない。

## 実行と計測

通常の `python3 -m unittest` は引き続き全テストを実行する。`tools/test_runner.py` は同じ unittest のテストを、収集時間・モジュール時間・各テスト時間とともに実行する道具。名前を指定した実行と、指定を省いた全体の収集に対応する。

モジュール時間には共通の準備と後片づけを含める。順番、モジュールの再登場、クラス共通の準備、準備のエラー、subTest の失敗、skip が通常の unittest と同様に扱われることを検査した。タイミングだけのために、既存の対戦の局数や seed は変えていない。

開発時・完了時・結果を書き込んだ後の文書だけの確認の手順を [testing.md](testing.md) にまとめ、README と CLAUDE.md から参照した。

初回の収集中に `test_effects.py` の繰り返し読み込みを見つけ、その分割を停止して修正した。そのモジュールをほかの分割が取り込まないことを確認し、該当分割を最終のファイルでやり直した。全実行が完了した後、ソース・テスト・道具・同梱データのハッシュが最終の記録と一致することを確認した。実行後の結果の追記は文書だけ。

- エンジン本体・同梱データ・既存の検査スクリプトは基点と同じ。
- 採用記録（1,004 件）・研究対応表・写しの検査が通る。
- 同じ ruff で基点と比較し、新しい指摘はない。

エンジン本体を変えていないため、別バージョンとの大規模な対戦比較は追加実行していない。全変異試験、複数の Python での実行、カードの追加、kyuura の変更はしていない。

## 実測から分かったこと

時間のかかったモジュール上位は次のとおり。共通の準備と後片づけを含む。この環境で並列実行した値であり、単独実行の性能比較ではない。

| モジュール | 秒 |
|---|---:|
| `test_card_sources` | 905.9 |
| `test_preflight_consolidation_v0_16c` | 573.4 |
| `test_reprint_text_variants_v0_71` | 425.4 |
| `test_fossil_hidden_info_v0_47` | 352.8 |
| `test_effect_preflight_v0_3d` | 341.3 |

個々のテストでは、不正な採用記録を拒否する `RejectTest.test_false_or_invalid_records_are_rejected` が 776.5 秒、先読み方式を比較する `BranchLimitBoundaryTest.test_derived_and_derived_full_agree_at_every_count` が 363.0 秒だった。次に実行時間を調べる対象は、これらの共通の準備と、個々の入力・盤面の処理の内訳。検査する拒否条件、先読みの一致、コイン結果の独立性は引き続き維持する。
