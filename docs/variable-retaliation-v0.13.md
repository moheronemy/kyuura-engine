# 量が受けたダメージで決まる「相手の番ではたらく効果」（v0.13）

v0.12 の `state.Retaliation`（R団のファイヤーの「ほのおのかべ」。決まった量 10 を返す）を、わるいカメールの「こうらがえし」（受けたダメージと同じ量を返す）にも使えるように、最小限に広げた記録です。

関連する文書:

- 裁定: [shell-attack-v0.13.md](shell-attack-v0.13.md)
- 設計の変更の一覧: [architecture-v0.13.md](architecture-v0.13.md)
- v0.12 の仕組み: [temporary-attack-effects-v0.12.md](temporary-attack-effects-v0.12.md)

## 1. v0.12 の構造（B1）

| 項目 | v0.12 の「ほのおのかべ」 |
|---|---|
| 型 | `state.Retaliation`（frozen。`PokemonInPlay.persistent_effects` の 1 つ）。項目は `source_card`・`source_player`・`created_turn`・`active_turn`・`attack_index`・`amount`。種類 `kind` は `"retaliation"`（クラスの値） |
| 量 | `amount`（10）。登録された `DamageAndRetaliation(retaliation=10)` と同じであることを不変条件（`engine._retaliation_problems`）で確かめる |
| 発生源・対象 | 効果を与えたワザを使ったポケモン自身（`source_card` はそのカード）。返す相手は、ダメージを与えた相手の対戦ポケモン（ワザを使ったポケモン） |
| 期限 | `active_turn` = 与えた番 + 1。`_end_turn` で消える（`remove_expired_persistent_effects`） |
| 適用 | 判定は `effects.deal_attack_damage`（相手のワザのダメージで、最終ダメージ > 0）→ `AttackUse.retaliations`（`PendingRetaliation`）。与えるのは `finish_damage_elements` の `_apply_retaliation`（`retaliation_use` で `deal_attack_damage` を通す） |
| 消える契機 | 期限・ベンチ（にげる・いれかえ・ふきとばし）・進化・きぜつ（`persistent.remove_persistent_effects`）。復活しない |
| ログ | `persistent_effect_added`・`retaliation`（`amount`）・`damage`（`retaliation: True`）・`retaliation_skipped`・`persistent_effect_removed` |
| 書き出し | 形式 8・9 の `persistent_effects` に `{"effect": "retaliation", …, "attack_index", "amount"}` |
| 不変条件 | 自分自身・持ち主の番・次の相手の番・期限・バトル場だけ・同じ種類は 1 つ・ログとの対応・登録との対応 |

## 2. 設計案の比較（B2）

| 案 | 内容 | 原典との整合 | v0.12 互換 | 型の安全 | 拡張性 | 保存形式 | ログの監査 | 複雑さ・過剰な抽象 |
|---|---|---|---|---|---|---|---|---|
| A | 既存の `Retaliation` の処理の中で、カードや量で分岐する（たとえば `amount` に 0 や −1 を入れて「受けたダメージ」を表す） | 量の決め方が値に隠れる。「0 は受けたダメージ」のような約束は、本当の 0 と区別できない | 形は同じ | 弱い（特別な値） | 弱い | 同じ形で意味が変わる（v0.12 の読み手が誤読する） | 特別な値を知る必要がある | 小さいが誤りやすい |
| **B（採用）** | `Retaliation` に決め方 `basis`（`fixed`・`received_damage`）を明示して加え、量 `amount` は `fixed` のときだけ持つ。基本となるダメージは `base_damage(received)` で求める | 2 つの説明（「相手に10ダメージ」「同じダメージ」）をそのまま表す | `fixed` の値・ログ・書き出しは v0.12 と同じ | `__post_init__` が組を確かめる（`fixed` は量が要る・`received_damage` は量を持たない・知らない決め方は作れない） | 決め方を加えるときは 1 か所（`base_damage`・`RETALIATION_KINDS`） | 形式 9 のまま。`received_damage` は種類を新しい値 `"retaliation_received_damage"` にして、v0.12 の読み手が知らない種類として拒否できる | 種類・決め方をログに書き、監査が照らす | 小さい |
| C | 固定と可変を別のクラスにする（`Retaliation`・`ReceivedRetaliation`） | 同じ | 固定は同じ | 強い | クラスごとに処理・不変条件・書き出し・監査の分岐が要る | 新しい種類 | 2 つの型を数える | 共通の処理（判定・期限・消える契機・相手・計算）が 2 重になる |
| D | ワザごとの個別の実装（こうらがえし専用の効果・判定・適用） | 同じ | 固定は同じ | 中 | 低い（同じタイプのワザ「クロスカウンター」を加えるたびに複製） | 新しい種類 | 個別 | 判定・時点・きぜつの扱いを複製する（v0.10・v0.12 で避けてきた形） |

B を選んだ理由:

- 原典の 2 つのワザは、時点・持続・消える契機・返す相手・計算（返すダメージはワザによるダメージ）が同じです（p.89 のワザ解説は、ほのおのかべと同じ形）。違うのは、返す量の決め方だけです。
- その違いを、型の 1 つの項目として明示しました。C・D は、同じ処理を 2 重にします。A は、量の決め方を値に隠します。
- 汎用のイベントの仕組み（購読・発行）は作っていません。

## 3. 受けたダメージの情報（B3・B8）

| 情報 | どこにあるか | 状態に持つか |
|---|---|---|
| 基本となるダメージ（元のワザの目安） | `deal_attack_damage` の引数 `base`・ログ `damage` の `steps` の 1 段階 | 持たない |
| 弱点・抵抗力・プラスパワー・ディフェンダーのあと（p.321 の 3〜7 段階） | `calculate_attack_damage` の `steps`・`modifiers` | 持たない |
| **最終ダメージ（受けたダメージ）** | `calc.final`。ダメージをのせる直前に `PendingRetaliation.received` に記録する（ワザ 1 回の中の値） | 持たない（`AttackUse.retaliations` は比較・表示に含めない） |
| 実際にのせたダメージ | `receiver.damage += calc.final`（HP で上限をつけない。v0.1 から） | 場のポケモンの `damage` |
| 与えたポケモン | `AttackUse.pokemon_id`（返す相手） | 持たない |

原典は「同じダメージ」を最終ダメージと読む根拠を示しています（[shell-attack-v0.13.md](shell-attack-v0.13.md) 3 章）。

- 受けたダメージは、効果を持つポケモンが受けるときの `deal_attack_damage` だけが知っていて、返すのは同じワザの `finish_damage_elements` です。
- 番をまたいで残す必要がないので、「直前に受けたダメージ」を状態の項目にしませんでした。
- 持続する効果（`Retaliation`）は番をまたぐので状態に持ち、決め方（`basis`）だけを書きます。
- ワザの処理の結果の構造（`DamageResult`）は変えていません。`PendingRetaliation` に 1 つの項目（`received`）を加えただけで、全ワザの書きかえはしていません。

## 4. 処理の順番（B4）

1 つのワザの中の順番です。p.89 のワザ解説で確かめました。

1. ワザの宣言が成り立つ。原典で決められない場合は、宣言の前に止める（S37。5 章）。
2. 相手のワザのダメージの要素で、わるいカメールが受けるダメージが決まる（p.321 の 1〜7 段階。`deal_attack_damage`）。
3. ダメージをのせる。受けたダメージを記録する（最終ダメージ > 0、相手のワザ、今の番にはたらく効果）。
4. そのワザのほかのダメージの要素（自分へのダメージなど）を処理する。
5. ダメージの処理がすべて終わったところで返す（`finish_damage_elements` → `_apply_retaliation`）。
   - 基本となるダメージは受けたダメージ。わるいカメールのワザとして、ワザを使ったポケモンに p.321 の順番で計算する（弱点・抵抗力・ディフェンダー・「とうめい」）。
   - 受けたポケモンの「はんげき」も、ここで与える。
   - ワザを使ったポケモンが自分へのダメージですでに HP 以上なら、返さない（`retaliation_skipped`）。
6. 元のワザのダメージ以外の効果（コイン・特殊状態・ふきとばしの決定・回復・持続する効果）を処理する。
   - ワザを使ったポケモンが返すダメージで HP 以上なら、そのポケモン自身への効果は、各ワザの実装が処理しない（S35）。
7. きぜつの処理・サイド・勝ち負け・バトル場に出す（`engine._finish_attack`）。

攻撃側が返すダメージできぜつする場合（S35）:

- そのきぜつは 7 で処理します（ワザの途中でトラッシュしない）。
- 6 の相手への効果（ふきとばし）は処理します。決定を待つ間、HP 以上のワザを使ったポケモンが場に残ることを、不変条件が許します（v0.10・v0.12 の狭い例外。返すダメージのログで確かめる。変えていない）。

## 5. 連鎖（B5）

| 組み合わせ | はたらくか | 理由 |
|---|---|---|
| こうらがえし → はんげき | はたらく（わるいカメールに 10） | 返すダメージはワザによるダメージ（S20・S25）。「はんげき」の 10 は特殊能力によるダメージなので、そのあとこうらがえしははたらかない（S5） |
| こうらがえし → ほのおのかべ | はたらかない | 返すダメージを受けるのは番のプレイヤーの R団のファイヤー。その「ほのおのかべ」がはたらくのは、持ち主の相手の番（与えた番 + 1）だけ |
| ほのおのかべ → こうらがえし | はたらかない | 同じ理由 |
| こうらがえし → こうらがえし | はたらかない | 同じ理由 |
| とうめい → こうらがえし | ゴーストが返すダメージを受けないことがある（S24）。ゴーストの「とうめい」のコインで、こうらがえしの効果がはたらくことはない（ダメージを与えない） | — |

持続する効果を与えるのは持ち主の番です（ワザは自分の番だけ。p.309）。はたらくのは次の相手の番です。返すダメージを受けるのは、いつも番のプレイヤーのポケモンです。この 3 つから、返すダメージで別の効果がはたらくことはありません（S45）。

- エンジンは、起こったら RuntimeError で止めます（`_apply_retaliation`）。回数の上限（再帰の深さ）で止める形にはしていません。
- 前提（与えた番が持ち主の番・はたらく番は次の番）は、不変条件で確かめています。
- 壊した盤面で止まることを `test_chain_is_refused_even_in_a_broken_state` が確かめます。ガードと不変条件を外すと連鎖が無限に続くことは、変異 22 で見つけています。

## 6. きぜつと勝ち負け（B6）

| 場面 | 処理 | 分類 |
|---|---|---|
| わるいカメールだけがきぜつ | 返してから、ワザのあとにきぜつの処理。サイドはワザを使ったプレイヤー | CONFIRMED（S18・S36） |
| ワザを使ったポケモンだけがきぜつ | 返すダメージのあと、ワザのあとにきぜつの処理。サイドはわるいカメールの持ち主。自分への効果は処理しない | CONFIRMED（S35 のスターブーメランの例）・SUPPORTED（一般化） |
| 両方がきぜつ（わるいカメールがワザで、ワザを使ったポケモンが返すダメージで） | ワザの宣言の前に `UNRESOLVED_RETALIATION_DOUBLE_KNOCKOUT` | UNRESOLVED（S37 = W24 と同じ問い） |
| 両方がきぜつ（ワザを使ったポケモンが自分へのダメージですでに HP 以上） | 返さない。1 つのワザによる同時のきぜつ（p.324） | v0.12 の W23 と同じ |
| 最後のサイド | 両方がサイドを取りうるのは「両方がきぜつ」の場合だけで、そこは止める | — |
| 手札・山札にもどす効果 | 対応カードにない（スターブーメランは模擬のワザで確かめた） | S38・S39 |
| 両方のバトル場が空 | 「両方がきぜつ」の場合だけで、止める | — |

S37 が W24 と同じ問いである理由:

- どちらも、1 匹は今のワザのダメージで、もう 1 匹は前の番のワザが与えた持続する効果のダメージ（p.321「8」で、そのワザによるダメージ）できぜつします。
- それが p.324 の「1つのワザ…によって引き起こされることがら」に当たるかが書かれていない、という同じ問いです。
- 新しい裁定 ID・コードは加えず、同じ停止の仕組み（`retaliation_double_knockout_problem`）で止めます。
- 違うのは返す量の求め方だけです。ダメージの組ごとに、わるいカメールが受ける最終ダメージを基本となるダメージにして計算します（`Retaliation.base_damage`）。

## 7. 期限と消える契機（B7）

v0.4b・v0.12 と同じ仕組み（`remove_expired_persistent_effects`・`remove_persistent_effects`）で、変えていません。

- 期限: 次の相手の番の終わり。
- 消える契機: ベンチ（ふきとばし・にげる・いれかえ）・進化・きぜつ。

期限（番の終わり）と、消える契機（場の変化）は別の処理です。わるいカメールが効果を持つ間に持ち主の番は来ないので、にげる・いれかえ・進化で消える場面は対応カードでは起こりません。共通の関数を直接呼んで確かめています（`test_shared_removal_for_every_reason`）。

## 8. 保存形式（B8）

形式 9 のままで表せます。

| 種類 | 形式 8・9 の `persistent_effects` の 1 つ |
|---|---|
| `retaliation`（ほのおのかべ。v0.12 と同じ） | `{"effect": "retaliation", "source_card", "source_card_id", "source_player", "created_turn", "active_turn", "attack_index", "amount"}` |
| `retaliation_received_damage`（こうらがえし。v0.13） | `{"effect": "retaliation_received_damage", "source_card", "source_card_id", "source_player", "created_turn", "active_turn", "attack_index"}`（量は書かない） |

- 種類の値を加えただけで、項目の意味を変えていません（v0.3b の特殊状態・v0.12 の `retaliation` と同じ扱い）。そのため、形式を 10 にしませんでした。
- v0.12 の読み手は、知らない種類として拒否できます。
- 受けたダメージ（ワザ 1 回の中の値）は書き出しません。
- 形式 1〜7 は、持続する効果があれば `ValueError` です（v0.4b から）。
- 保存・復元（pickle・deepcopy・clone）で効果は変わりません（`SaveRestoreAndInvariantTest`・自然な対戦・保存・復元の確かめ）。

## 9. ログ（B9）

新しいイベントは加えていません。既存の `retaliation` に、決め方 `basis` と受けたダメージ `received_damage` を加えました（こうらがえしのときだけ。ほのおのかべは v0.12 と同じ形）。

| 知りたいこと | ログ |
|---|---|
| 効果の発生 | `persistent_effect_added`（`persistent_effect` が種類） |
| 種類 | `retaliation` の `persistent_effect`・`basis` |
| 受けたポケモン | `retaliation` の `pokemon_id` |
| 元のワザ | `retaliation` の `trigger` |
| 受けたダメージ | `retaliation` の `received_damage`（直前のダメージのログの `amount` と同じ） |
| 基準となるダメージ（返すダメージの基本） | `retaliation` の `amount`・返すダメージのログの `steps` の 1 段階 |
| 返すダメージ（最終） | すぐあとの `damage`（`retaliation: True`）の `amount` |
| 返す相手 | `retaliation` の `attacker_pokemon_id`・返すダメージの `pokemon_id` |
| きぜつ | `knock_out`（ワザのあと） |
| 消えたこと | `persistent_effect_removed`（`reason`） |

ログの監査（tests/log_audit.py）は、v0.13 から次を確かめます。

- 受けたダメージが、きっかけのダメージのログの最終ダメージと同じこと。
- 基本となるダメージが受けたダメージであること。
- ほのおのかべの量が 10 であること（`basis`・`received_damage` を書かない）。
- 効果の種類が登録と合うこと。
- 状態の効果の種類が、ログで与えた種類と同じこと。

弱点・抵抗力・返す相手・期限・ダメージの組み立て直しは、v0.12 の確認がそのまま当てはまります。

## 10. これから同じタイプのワザを加えるときの約束

- 返す量の決め方が違うワザ（クロスカウンター「受けたダメージの2倍」・コインあり）は、`basis` の値を加えます（`RETALIATION_KINDS`・`Retaliation.base_damage`・`__post_init__`・登録の `retaliation_terms`・監査）。
- コインのある返し方は、乱数の順番と、止める判定（S37 と同じ問い。コインのすべての結果）を先に原典で確かめます。
- 返す相手・計算・時点は、p.89 のワザ解説と p.321「8」にしたがいます。違う規定のワザは、先に原典で確かめます。
- ベンチ・複数のポケモンにダメージを与えるワザで、効果を持つポケモンが 2 回以上ダメージを受ける場合（S7。C34・C35 と同じ問い）は、宣言の前に止める処理を先に加えます。
