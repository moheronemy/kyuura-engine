   - 合法性は `deck_problems` が計画を作るときに当てます。
   - 局の並び・方式・seed・デッキ・規約集合・観測・上限・停止方針・識別を、この下書きと照らし、`plan.sha256` を記録します。
3. 新しい外部の checked hash の pyc キャッシュを、`prepare_pyc_cache.py` で証跡の外の新しい空のディレクトリに作ります（実行の worktree・コミット・Python に対応するもの）。
   - 準備の時間・容量は、バッチの累積時間・ゲームの証跡と分けて記録します。
4. `run_seq_pyc.py … --dry-run` で、`use_cache` 真と、`batch run` を呼ばないことを確かめます。偽なら止めます。
5. 計画ごとに `run --stop-after-games 1` を 1 局ずつ呼びます（`-B` と `PYTHONPYCACHEPREFIX`）。
   - 各局の前に、計画の残りと出力先の空き（キャッシュが占めたあとの値）の両方が、必要量 max(128 MiB, その計画で保存済みの最大 1 局の証跡 × 1.5) 以上であることを確かめます。
   - 足りなければ未着手を残して終えます。記録の削除・圧縮・予算の延長はしません。
6. 停止したら、証跡を保存して報告します。`--acknowledge-stop`・`unlock` は自動で使いません。その場で直して再実行しません。
7. 各計画の最終集計を、同じキャッシュで 1 回だけ実行します。主要件数と、確定済みのゲームの証跡のハッシュの不変を確かめます。
   - ファイルの時刻や残差から出した区間の時間は、推定と明記します。区間の合計が合うことだけを、境界が正確な証拠にはしません。

## 7. 実行時の確認項目と未到達の扱い

### 7.1 T-A（w1）

| 確認 | 判定 |
|---|---|
| 前提 | パソコン通信・エネルギー回収・ポケモン交換おじさん・ポケモン育て屋さんの受理と、続く決定（`discard_from_hand`・`search_deck`・`retrieve_energy`・`return_to_deck`・`select_evolution_card`）の生成。trace の候補と本人の観測の `decision` で数える |
| 止まった段 | 提示（`answer_decision` の候補）・範囲・選択・入力の生成・check・送信の、どこまで進んだか（aggregate の funnel と trace） |
| 回答者と公開の範囲 | 決定の `player` が回答する主体で、本人の観測にだけ選べるものがあり、相手・観戦者の観測に選べるものがないこと。伏せる種類では `option_count` もないこと（既存の確かめ `decision_options_visible`・`hidden_count_visible`） |
| 本人だけの情報 | 山札・手札のカードの中身が、選べるものとして本人にだけ見えること。受理のあとの公開ログに出るのは、全員に見えるはずの値だけであること |
| 拒否（`UNRESOLVED_ENERGY_RETRIEVAL_ZERO_CHOICE`） | 拒否の行で 3 主体の観測の sha256 とログの位置が前後で同じ、更新が届かない、閲覧用記録の項目は本人の own_rejection だけ、同じ主体の決定待ちが続くこと（応答の `status`・`next`・`refetch_required`） |
| 判定 | 根拠の登録がないので evidence_missing_stop の undetermined の見込みです（続行）。known_stop にしません。未知の分類なら止めます |
| 効果の中身 | 受理の中身の確認があるのは P6・U-R3a・うらの特殊能力だけです。T-A の効果（探す・回収）は、公開ログの出来事（手札の数・トラッシュ・山札の数の変化）が選んだ数と合うかを、読むだけで比べます。合わなくても判定規則は変えず、記録して報告します |
| replay | replay_run が期待どおり（succeeded）であること |
| 未到達 | 種類ごとに、前提（トレーナーを使わなかった）・方策の非選択・入力の生成・check・別の拒否で分けます。決まらなければ不明とします。未到達でも局を足しません |

### 7.2 T-B（w2・w3）

| 確認 | 判定 |
|---|---|
| 前提 | 準備で、両方の回と片方だけの回の両方がある切り直しの組になったか。公開ログの切り直しの出来事・`mulligan_draw` の候補で見る |

| w3（既定の集合） | 準備で `UNRESOLVED_MULLIGAN_COMPENSATION` の停止（halted_known）になること。判定は `halt_condition_not_evidenced`（evidence_missing_stop。続行と指定した分類）の見込み。停止の診断が全員に同じであること。観測の記録が受理 0 のまま complete であること（未出現の形なので、問題なら止めて報告する） |

### 7.3 共通

- 新しい診断・不整合・期待と違う公開は、保存して止めます。その場で修正したり、判定規則を足したりしません。
- 未記録の値（エンジンの内部の状態・乱数）は推測しません。未出現の項目は確認済みとしません。
- 旧記録（b2・C2・C1）との比較は、差を記録する読み取りだけです。一致を強制する正規化はしません。

## 8. 実装変更の要否と採用の判断

- **推奨案（w1〜w3）は実装変更なしで実行できます。**
- 別の実装・採用の単位として残すもの（今回はしない）:
