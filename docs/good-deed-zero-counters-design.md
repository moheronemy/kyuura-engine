## 0. 先に結論

- **2 局面とも、0 個の答えは送っていません。** とりのぞく数の入力では、0 の選択肢が `processability: unresolved_ruling` で示され、方策はそれを除いて 1 と 2 から選びました。2 局面とも 2 を選び、`check` が有効、送信は受理、judge は expected でした。
- **実測の送信の拒否は 0 です。** 0 を送った局面がないので、拒否として数えるものはありません。13 章の「除外」2 行は、取得した入力の中の選択肢の除外（R5）です。

- **史料は、カウンターがあるときに 0 個を選べるかを直接は定めていません。** 文面は「好きなだけとりのぞく」で、「のぞむなら」がありません。kyuura の論点 `UQ-UP-TO-ZERO-CHOICE` は UNRESOLVED（公式の資料は insufficient）です。その事例の一覧に、このカードは入っていません（7 章）。
- **0 個を受理したと仮定すると、** 対象を選んだところでワザが終わり、とりのぞく数も引く数も 0 です。そのあとは、今の記録と同じ番の終わりの処理（`turn_end`・`pokemon_check`・相手の番の始まり）に進む見込みです。増えるのは、この決定への答えが 1 つだけです。新しく続けられる局面はありません。今も 1 個以上で続いているからです。

- **推奨は A（今のまま）です。** 規約を作るなら、このワザの元の経路に限った B を候補にします。C は勧めません。
  - B で増えるのは、効果のない答え 1 つです。2 局面では拒否がないので、拒否・完走率がよくなる見込みもありません。
  - C は、未解決の問いを厳しい側に決めてしまいます。今の方策の手はどれも変わりません。
- **規約の採用の前に足りない証拠:**
  - 当時の日本語の Q&A・裁定で、「好きなだけ」が 0 を含むかを書いたもの。
  - 0 の受理をエンジンで確かめた最小盤面（6 章）。
  - コピー・変身の経路で、このワザに届くかの確かめ。

**3 つの場面の区別:**

1. **対象を選んだあとの 0 個**（今回の場面）。カウンターのあるポケモンを選んだときだけ出ます。0 は選べますが、選ぶと止めます。
2. **対象そのものを選ばない答え。** ポケモンの選択は最小 1・最大 1 なので、0 匹の答えは不正です（`INVALID_CHOICE_COUNT`。未裁定ではない）。カウンターのないポケモンを選ぶことはでき、そのときは 1 の 2 段目が出ません（17 回の記録）。
3. **最初から取り除けるカウンターが 0 個。** 相手のどのポケモンにもカウンターがなければ決定は出ず、ワザは何もせずに終わります（78 回の記録）。0 個を「選ぶ」場面ではありません。

| 引く | なし（とりのぞいた数 0。「ワザをうけない」で受けなかったときの今の分岐と同じく、`draw` を呼ばない） |
| 決定 | 終わり（待っている決定はなくなる） |
| ワザの残り | ［よいおこない］にはほかの要素がないので、ワザの処理はここで終わる |
| きぜつの判定 | 今の、ワザのあとの確かめ（`pokemon_check`）のまま。このワザ自身はダメージを与えないので、0 の答えで新しいきぜつは起こらない見込み |
| 番の進行 | 今の記録（1.2 節）と同じ番の終わり（`turn_end` → `pokemon_check` → 相手の `turn_start`・`draw`）の見込み |
| 公開ログ | `attack` のあとに `convention_applied`（5.4 節の項目）、そのあとは番の終わり。`attack_heal`・`draw` は書かない |
| 再利用できる現行の経路 | 0 の終わり方は、対象のカウンターが 0 のとき（6569〜6570 行）・受けないとき（6580〜6581 行）の早い終わりと同じ形。規約の照会と記録は H4 の `RecoverEnergy.resume`（`programs.py` 2950〜2969 行。`continuation_for`・`record_application`）と同じ形 |

**実装の前に要る変更点（設計。今回はコードを変えていない）:**

- 決定を出すとき（6571〜6574 行）に、規約の照会で 0 を止める選択に入れるかを決めます。共通の確かめが先に止めるので、`resume` の中だけでは受理できません。H4・ER9 とはここが違います（あちらは `resume` の中で空の答えを止める）。
- `resume` の `1 <= choices[0]` の確かめ（6577 行）を、規約があるときだけ 0 を受けるように変えます。
- 決定の形の確かめ（`effects.py` 7548 行）を、規約があるときの形（止める選択なし）でも通るようにします。
- 先読み（6589〜6591 行）は、止める選択がなくなれば 0 も試します。

### 5.3 C を勧めない理由

- 今の方策は 0 をすでに選ばないので、C で変わる手はありません。
- 未解決の問いを、プレイ用とはいえ「0 を含まない」と決めることになります。
- 直接のコマンドの 0 の拒否が、未裁定（研究の問い）から不正な操作に変わり、停止の分類と診断の対応が変わります。

### 5.4 推奨: A。規約を作る場合は限定した B（採用の候補。利用者の判断）

**今は A を勧めます。** B で増えるのは「何もしないワザ」の答え 1 つです。2 局面とも拒否はなく、16 行・111 回の記録でも対戦を止めていません。13 章の順位（4 位）を変える根拠もありません。

利用者がプレイ用の集合の完成を優先して B を選ぶ場合は、次の範囲に限ります。

| 項目 | 案 |
|---|---|
| 規約 | `PC-GOOD-DEED-ZERO@1`（名前は案）。層は続行（`LAYER_CONTINUATION`）。承認は利用者の採用 |
| 場面 | 停止コードに事例を付けた `UNRESOLVED_DISCARD_ANY_NUMBER_ZERO#good-deed-remove-counters`（RS1 の `#lucky-once-stated-replacement` と同じ形）。事例を付けた照会だけが当たり、同じコードのほかの場所には当たらない |
| 適用の条件 | 決定 `remove_counters` を出す時点で、(1) 解決の基盤の要素が `ChosenOpponentHealThenDraw`、(2) 宣言したワザと処理しているワザが同じで、ワザを使ったポケモンの印刷のカードがそのワザのカード（H4 の「元のワザ」と同じ判定。カード ID の定数では分けない）、(3) 対象のカウンターが 1 個以上 |
| 対象外 | メタモンの［へんしん］などで持つ［よいおこない］、ゆびをふる・ほかのコピー、同じコードのほかのワザ・トレーナー（6 章の S4）、ER9・H4、ほかの「最大N枚」の場面、厳密側・既存の集合 |
| 0 のとき | カウンターをとりのぞかず、引かず、決定を終えてワザを終える（5.2 節） |
| 変えないもの | 1 個以上の答え、選択肢の範囲、ポケモンの選択、カウンターがないときに決定を出さないこと、「ワザをうけない」・「とうめい」の評価、山札が足りないときの引き方 |
| 集合 | 新しい開発用の集合（例 `CS-KYUURA-PLAY-TR9@1` = TR8@1 の 27 規約 + この規約）を明示的に選んだときだけ |
| 維持する集合 | `CS-KYUURA-CURRENT@1`（既定）・LEGACY・S2A・PO・TR3・TR4・TR6・TR7・TR8 の定義と固定ダイジェスト（TR8@1 は `sha256:27dfe27a…`） |
| 公開ログの最小の項目 | `convention_applied` に規約 ID・版・場面・停止コードと、`player`（ワザを使ったプレイヤー）・`target`（対象のポケモンの場の番号）・`available`（のっていたカウンターの数）。どれも既存の `APPLIED_FIELDS` にあり、秘密の情報をふくまない |

- **史料上の結論とプレイ用の取り決めの区別:** 史料上は未解決のままです（`UQ-UP-TO-ZERO-CHOICE`）。B は、0 を「とりのぞかない」と読んで続けるプレイ用の取り決めで、公式の裁定・kyuura の研究上の解決ではありません。
- **根拠が足りない点:** 「好きなだけ」が 0 を含むかを書いた当時の資料がありません。規約にする前に、kyuura の論点の資料探しと、6 章の最小盤面での確かめを勧めます。
