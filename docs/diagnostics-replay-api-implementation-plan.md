# 診断 API と対戦記録・再現インターフェースの実装計画（案）

[仕様案](diagnostics-replay-api-design.md)を実装するときの単位・依存・順・回帰テスト・完了基準の案です。この計画も**案**で、仕様の採用の判断のあとに、別の作業として実装します。この作業では、どの単位も実装していません。

表（`<!-- generated:… -->` の区画）は、仕様の JSON（[diagnostics-replay-api-design.json](diagnostics-replay-api-design.json)）と同じ元から `scripts/build_diagnostics_replay_api_design.py --write` で作ります。区画の中を手で直さないでください。

## 1. 前提

- 新しい仕組みは、既存の機能を包む形にする（仕様案 3 章）。`apply_command` の受理・拒否、観測の見える範囲、台帳の分類を作り直さない
- エンジンの動作を変える単位はない。例外に事例 ID を持たせる、拒否の文をコードごとの決まった文にする、などのエンジンの変更が要るとわかったら、その単位の中で進めず、別の判断として持ち上げる
- `engine.py`・`resolution/` にカード ID・モードの名前の分岐を加えない。例外を広く捕まえない（`EngineError` だけを診断にし、ほかは内部エラーとして記録して投げ直す）
- テストは、固定の少数の盤面・seed（目的と seed を先に決める）と双子の比較で作る。全 108 組・4,356 局・lockstep 全体・ストレス実行を、単位の完了の条件にしない

## 3. 依存と推奨の順

```
U1 診断の型と情報境界
 └─ U2 コマンド実行結果のアダプタ
     ├─ U3 完全な再現用記録の収集と検証
     │   ├─ U4 再現インターフェース
     │   │   └─ U6 JSON の保存・復元への接続（U3・U4 のあと）
     │   └─ U5 閲覧用記録（U1・U3 のあと）
     └─ U7 合法手 API・GUI アダプタへの接続（U2・U5 のあと）
```

推奨の順は U1 → U2 → U3 → U4 → U5 → U6 → U7 です。U5 は U4 と並べて進められますが、閲覧用記録の確かめに完全な記録を使うので、U3 のあとにします。U6 は、再現（U4）で「保存して復元した続きが同じ」ことを確かめられるようになってから始めます。

## 4. 共通の回帰テストの方針

- **情報境界**: 診断・閲覧用記録・合法手の一覧の、見る人ごとの写しを、v0.147〜v0.151 の双子（`swap_hidden`・`swap_set_aside` の盤面）で比べる。`twin_command_problems` の比べる値を、診断の写しに広げる
- **状態を変えない**: 拒否・診断の作成・閲覧用記録の作成のあとで、状態の書き出し・乱数・ログが変わらない（`command_outcome` と同じ確かめ）
- **既存の回帰**: 各単位の完了の前に、変えたファイルを使う既存のテストのモジュールを実行する。単位をまとめて終えたときに、[testing](testing.md) に従って全体を 1 回実行する
- **件数を写さない**: 「分類の数が N 個」のような件数をそのまま期待値にせず、台帳のすべてのコードが分類に入る・検証者だけの項目がない、のような性質で確かめる

## 5. 推奨案と利用者の判断事項

## 6. 最初に実装する単位と完了基準

v0.155 の結果: U5 を実装した（[view-record-v0.155.md](view-record-v0.155.md)。実行時の収集と、U4 の検証つきの再実行からの変換）。次の単位は U6（JSON の保存・復元）で、D-SNAPSHOT-BASE・D-HALT-SNAPSHOT は保留のまま。

v0.154 の結果: U4 を実装した（[replay-run-v0.154.md](replay-run-v0.154.md)。記録の行を seq の順に再実行し、確認値を照らす。`compare_runs` は実装していない）。次の単位は U5（閲覧用記録）。

v0.153 の結果: U3 を実装した（[replay-record-v0.153.md](replay-record-v0.153.md)。収集・JSON の読み書き・構造の検証。再実行して照らすのは U4）。次の単位は U4（再現インターフェース）。

v0.152 の結果: U1・U2 を実装した（[diagnostics-adapter-v0.152.md](diagnostics-adapter-v0.152.md)）。下の完了基準をどう確かめたかは、その文書の 5 章。次の単位は U3（完全な再現用記録の収集と検証）で、`adapter.submit` の結果（`CommandResult`。`operation_id`・`outcome`・検証者用の記録）を受け取る。

最初は **U1 と U2** を 1 つの作業として推奨します。この 2 つで、今の `apply_command` の結果（例外か状態）を、分類・status・見る人ごとの写しを持つ診断にできます。記録・再現・保存の単位は、すべてこの上に乗ります。

完了基準:

1. 台帳の停止コードがすべて分類に入り、台帳にないコード（`unlisted`）が 0
2. EngineError でない例外が、`internal_error` 以外にならない（わざと内部エラーを起こすテストの盤面で）
3. 拒否の結果で、状態・乱数・ログが変わらない
4. v0.147〜v0.151 の双子で、本人・相手・観戦者の診断の写しが状態によって変わらない
5. 見る人の写しに、検証者だけの項目がない。見る人の値に検証者がない
6. エンジンの公開 API（`apply_command`・`observe` など）の動作と既存のテストの結果が変わらない

## 7. この計画でしないこと

- オンライン対戦のサーバー・通信、本格的な画面（U7 は境界の文書と最小のアダプタだけ）
- 続行規約の採用、停止からの再開（`GAP-DEFERRED-HALT-NO-RESUME`）
- 旧記録の自動移行、すべての過去の版の記録への対応
- 形式 35 の意味の変更、pickle を保存の形式にすること
