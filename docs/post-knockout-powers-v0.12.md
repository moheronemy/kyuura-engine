# きぜつしたあとに使う特殊能力（v0.12）

v0.12 で、ポケモンが「きぜつ」してトラッシュに置かれたあとに、原典にもとづく特殊能力の使用（持ち主の選択・トラッシュから手札への移動）を挟めるようにしました。最初の対応カードは R団のファイヤーの「ふしちょう」（[phoenix-v0.12.md](phoenix-v0.12.md)）です。設計の比較は [architecture-v0.12.md](architecture-v0.12.md) 2 章。

汎用のイベントの仕組み（購読・発行）は作っていません。v0.2a の決定（`push_decision`・再開先 `_RESUMERS`）と、v0.2f からのきぜつの処理（`_knock_out` → `_after_knockouts` → サイド → 勝ち負け → バトル場に出す）をそのまま使い、きぜつの処理の前に候補を求める 1 か所（`_post_knockout_candidates`）と、勝ち負けの判定とバトル場に出すあいだの 1 か所（`_offer_post_knockout`）と、1 つの決定の種類（`POST_KNOCKOUT_POWER`）を加えただけです。

## 1. v0.11 の「こんじょう」と違うところ（流用しない理由）

| | こんじょう（v0.11） | ふしちょう（v0.12） |
|---|---|---|
| 条件 | 相手のワザによるダメージで「きぜつ」する「とき」 | 「きぜつ」した「とき」（原因を問わない） |
| 時点 | きぜつの処理（トラッシュ）の前 | きぜつの処理（トラッシュ）のあと（「トラッシュからとり出し」） |
| 結果 | 「おもて」ならきぜつしない（サイドもない） | きぜつしたまま（サイドを取られる。p.82 の解説）。カードが手札にもどる |
| 特殊状態 | ダメージを受けるとき「すでに」ねむり・マヒ・こんらんなら使えない（ワザの中で記録） | 「きぜつ」するとき、ねむり・マヒ・こんらんなら使えない（きぜつの処理の前に見る） |
| 経路 | ワザのあとだけ（`_finish_attack`） | ワザのあと（`_knock_out_after_attack`）とポケモンチェック（`_pokemon_check`） |
| 決定 | `KO_PREVENTION`（選ぶのは場のポケモンの番号）。再開先 `knock_out` | `POST_KNOCKOUT_POWER`（選ぶのはトラッシュのカードの uid）。再開先 `post_knockout` |
| 乱数 | コイン 1 枚 | 使わない |

同じ決定の種類にすると、選べるもの（場のポケモンの番号とトラッシュのカード）・再開したあとの続き（きぜつの処理に入るか、バトル場に出すか）・不変条件（HP 以上のポケモンが場に残ることを許すか）がちがうものを 1 つの種類で表すことになるので、種類を分けた。

## 2. 処理の順番

```
_knock_out_after_attack(state)            # ワザのあと（v0.11 のこんじょうのあと）
_pokemon_check(state)                     # ポケモンチェックの 2（どく）
  ├ knocked = HP 以上のポケモン
  ├ candidates = _post_knockout_candidates(state, knocked)   # トラッシュの前の場で求める（4 章）
  ├ _knock_out(...)  ×きぜつの数               # トラッシュ（ログ knock_out・persistent_effect_removed）
  └ _after_knockouts(state, prize_takers, then, post_knockout=candidates)
       └ _next_prize_or_judge
            ├ サイドを取る決定（TAKE_PRIZE。候補があれば context に "post_knockout"）… 1 枚ずつ
            ├ 勝ち負けの判定（judge.decide。p.311 の表）
            │    └ 決まった → _finish（対戦の終わり。ふしちょうは決めさせない）
            ├ 候補がある → _offer_post_knockout → POST_KNOCKOUT_POWER（player=持ち主、options=(カード,)、min 0・max 1）
            │                 └（持ち主が答える）_resume_post_knockout
            │                      ├ 選ばない → post_knockout_power_declined
            │                      └ 選ぶ     → post_knockout_power_declared → return_to_hand（トラッシュ → 手札）
            │                      └ _promotions_after_judge
            └ 候補がない → _promotions_after_judge   # バトル場に出す（番でないプレイヤーが先）→ 番の終わり／ポケモンチェックの 3・4
```

- 候補は、きぜつの処理（トラッシュ）の前に求める（P17・B2）。トラッシュのあとの場では、きぜつしたポケモンの特殊状態がもうない。
- 決定は、サイドを取る決定（あれば）と勝ち負けの判定のあと、バトル場に出す前に出す（3 章の正規化）。対戦が終わるなら出さない（P29・P30）。
- ポケモンチェックの中のきぜつでは、決定の `context` に `then`（`next_turn`）を書き、答えのあとバトル場に出してから、ポケモンチェックの 3・4 → 次の番（v0.3b と同じ続き）。
- 答えのあとは、同じきぜつで決定を出さない（P12）。
- 番のプレイヤー・番の番号は変えない。決定する人は持ち主（番のプレイヤーのことも、番でないプレイヤーのこともある。P3・P8）。

## 3. 順番の正規化（P27・P28・P30）

「ふしちょう」の宣言・サイドを取る・バトル場に出す・勝ち負けの判定の順番は、原典に書かれていない（p.323 のきぜつの処理の手順にも、p.325「23 同じタイミングで起こったことの順番」にも、きぜつしたときに使える特殊能力が含まれるかが書かれていない。UNRESOLVED）。エンジンは選ばせずに次の順番に正規化している（ルールの裁定ではない。実装上の仮定）。

> きぜつ（トラッシュ）→ サイドを取る → 勝ち負けの判定 →（対戦が続くなら）「ふしちょう」を使うか → バトル場に出す

止めずに正規化したのは、どの順番でも次のものが変わらないため（v0.2f のサイドを取る順番の正規化と同じ考え方。docs/simultaneous-ko-v0.2f.md 5 章）:

1. **カードの行き先**: 「ふしちょう」が動かすのは、トラッシュのそのカード 1 枚だけ（P22）。サイド・山札・ベンチ・バトル場・ほかのトラッシュのカードは変わらない。
2. **サイド**: 取る枚数は、きぜつの数で決まる（p.323）。手札にもどしても、きぜつの取り消しではない（p.82 の解説）。サイドは表を見ないで選ぶ（p.312）ので、どのサイドを選べるかも変わらない。
3. **バトル場に出せるポケモン**: 出すのはベンチから（p.323）。手札のたねポケモンはバトル場に出せないので、回収してもしなくても、出せるポケモンの集まりは同じ。
4. **勝ち負け**: p.311 の表の条件（すべてのサイドを取り終えた・かわりの対戦ポケモンを出せない）は、手札の内容に関わらない。勝ち負けとその理由は同じ。対戦が終わる場合（「そこで…対戦は終了します」）に「ふしちょう」を使わせても、結果は同じ。
5. **使えるか**: 特殊状態はきぜつするときのもの（P17）、かがくへんかガスは、きぜつの時点と決定の時点で同じ（ガスを持つポケモンがいっしょにきぜつする場合（P19）は先に止めている。サイドを取る・勝ち負けの判定はガスを変えない）。
6. **乱数**: 「ふしちょう」は乱数を使わない。サイドを取る・バトル場に出すも乱数を使わない。

順番で変わりうるのは、同時のきぜつで、番のプレイヤーがバトル場に出すポケモンを選ぶとき、相手が「ふしちょう」を使ったか（公開の情報）を知っているかだけ。正規化した順番（「ふしちょう」が先）は、これらが同じタイミングのことがらなら、番のプレイヤーが選べる順番の 1 つ（p.325）。対戦が終わる場合は、決めさせないので、ログに `post_knockout_power_declined` もない（自然な対戦の指標の「対戦の終わりで決めさせなかった」）。

サイドを取ることで何かが起こるカード・手札の枚数で勝ち負けが決まる効果・手札からバトル場に出せる効果・「きぜつしたとき」にほかの処理をする効果を加えるときは、この正規化が成り立つかを見直す。成り立たなければ、原典を確かめて順番を決めるか、順番の選択を決定にするか、止める（`UNRESOLVED_…`）。

## 4. きぜつしたあとのカードの識別（B2）

決定に必要な情報は、候補（`_post_knockout_candidates` の戻り値）の **(持ち主, カードの uid, カード id, パワーの位置)** だけで、サイドを取る決定の `context` の `"post_knockout"`（候補があるときだけ。ないときの形は v0.11 と同じ）と、「ふしちょう」の決定の `options`・`context` の `"power"` で運ぶ。

| 候補にした情報 | 持つ理由・持たない理由 |
|---|---|
| カードの uid | 手札に加えるのはこのカード（P22・P24）。トラッシュに同じカード id のカードがほかにあっても取りちがえない |
| 持ち主 | 決定するプレイヤー・手札に加えるプレイヤー（P3） |
| カード id・パワーの位置 | 宣言する特殊能力（ログ・登録の確認） |
| 元の場の位置（バトル場・ベンチ） | 持たない（場所の制限がない。P11） |
| きぜつの原因 | 持たない（原因を問わない。P5〜P10） |
| きぜつ直前の特殊状態 | 持たない。トラッシュの前に「使えるか」を判定し、使えない場合は候補にしない（P13〜P17） |
| かがくへんかガスの状態 | 持たない。トラッシュの前に判定し、決定の時点でも不変条件が `suppressors_of` で確かめる（P18） |
| トラッシュへの移動の履歴 | 持たない。カードがトラッシュにあることと、直前のきぜつ（ログ `knock_out`）のカードであることを不変条件が確かめる |

状態の正本は `GameState` で、ログから候補を決めない。候補を求めるのはエンジンが 1 回だけで、決定のあとで場の状態を調べ直して過去の特殊状態・抑止を判断しない（場をはなれたあとの状態では決められない）。

## 5. 決定（`POST_KNOCKOUT_POWER`）

| 項目 | 値 |
|---|---|
| `kind` | `post_knockout_power`（`decisions.POST_KNOCKOUT_POWER`） |
| `player` | カードの持ち主 |
| `options` | (カードの uid,)（トラッシュにある） |
| `min_choices`・`max_choices` | 0・1（選ばない = 使わない） |
| `resume` | `post_knockout` |
| `context` | `("power", (カード id, パワーの位置))`、ポケモンチェックの中なら `("then", "next_turn")` |

- 答えは `ResolveDecision(player, decision, choices)`。選ぶもの以外・人違い・重ねた選択は、v0.2a の決定の確認で `IllegalActionError`（状態・ログ・乱数は変わらない）。
- 決定を待つ間はほかの操作を受け付けない（v0.2a）。保存（pickle・deepcopy・clone）してから続けられる。
- 書き出しは形式 9 のまま（決定は既存の `decision` の項目で表す。形式 1 は再開先 `post_knockout` の決定、または `"post_knockout"` を持つサイドを取る決定があると `ValueError`）。

## 6. トラッシュから手札への移動（B4）

トラッシュのカードを手札に加えるのは `zones.return_discard_to_hand(state, player, cards)` だけ（v0.12 で加え、v0.9 のゴースの「エナジーへんかん」（`RecoverEnergyAndSelfDamage`）もこれを使うようにした。ログはそれぞれの呼ぶ側）。

| B4 の項目 | どこで確かめるか |
|---|---|
| 1. 正しい uid のカードだけ | 決定の `options` が候補のカード 1 枚。`recover` はそれだけを渡す。テスト `test_use_returns_only_this_card`、ログの監査（`return_to_hand` の `card` が直前のきぜつのカード） |
| 2. ほかのカードを回収しない | 同上。変異 5 |
| 3. エネルギーを回収しない | 同上。ログの監査が手札とトラッシュを組み立て直す。変異 6 |
| 4. 重複・消失がない | `return_discard_to_hand` は、トラッシュにないカード・重ねたカードを `RuntimeError` で拒否する（状態を変える前）。不変条件（カードの保存則） |
| 5. 手札・トラッシュの枚数 | 不変条件（保存則）・ログの監査（手札・トラッシュの組み立て直し） |
| 6. 持ち主の手札 | `return_discard_to_hand(state, owner, ...)`。変異 8 |
| 7. 回収したあと場に残らない | きぜつの処理で場をはなれている（`pokemon_id` は無効）。不変条件 |
| 8. 回収できない状態 | 決定を出すときと不変条件が、カードが持ち主のトラッシュにあることを確かめる（なければ `RuntimeError`・不変条件の違反） |
| 9. ログから追跡できる | `knock_out` → （`take_prize`）→ `post_knockout_power_declared` → `return_to_hand`。ログの監査 |
| 10. 保存・復元で変わらない | 決定は `GameState.decision`。tests/test_phoenix_v0_12.py の `test_pickle_deepcopy_clone_and_resume`、v0.12 の保存・復元の確かめ（[v0.12-verification.md](v0.12-verification.md)） |

## 7. 不変条件

- `_post_knockout_decision_problems`: 「ふしちょう」の決定の種類と再開先・選ぶ数・選べるもの（1 枚）・持ち主のトラッシュにあること・そのパワーの位置に `ReturnToHandOnKnockOut` が登録されていること・かがくへんかガスに消されていないこと・ログの最後のきぜつ（そのあとは `take_prize` だけ）にこのカードがあること。
- `_post_knockout_candidate_problems`: サイドを取る決定の `"post_knockout"` の形（候補 1 つ）・カード・直前のきぜつ。
- 決定を待つ間は、バトル場が空のプレイヤーがいてよい（バトル場に出すのはこの決定のあと）。`then` を持つ決定の種類に `POST_KNOCKOUT_POWER` を加えた。
- 特殊状態（ねむり・マヒ・こんらん）は、きぜつしたあとの状態からは確かめられないので、ログの監査が組み立て直して確かめる。

## 8. ログ

| イベント | いつ | 項目 |
|---|---|---|
| `post_knockout_power_declined` | 選ばなかった | `player`・`card`・`card_id`・`power` |
| `post_knockout_power_declared` | 選んだ（宣言。p.311 の手順 1） | 同上 |
| `return_to_hand` | 宣言のすぐあと（p.311 の手順 3） | `player`・`card`・`card_id`・`power`・`revealed`（True。「相手プレイヤーに見せてから」） |

ログの監査（tests/log_audit.py）は v0.12 から、きぜつ（`knock_out`）のたびに、そのときのいちばん上のカードの「ふしちょう」・きぜつするときの特殊状態（組み立て直したもの）・はたらいているかがくへんかガスから「使えるか」を求め、使えるのに対戦が続いて答えがない・使えないのに答えた・同じきぜつで 2 度答えた・答えのあとにサイド・きぜつ・対戦の終わりがある（バトル場に出すより前に答える）・宣言のすぐあとに `return_to_hand` がない・選ばなかったのに `return_to_hand` がある、を見つける。`return_to_hand` は手札とトラッシュの組み立て直しに含める。

## 9. これからきぜつしたときの特殊能力を加えるときの約束

- 候補は、きぜつの処理（トラッシュ）の前に `_post_knockout_candidates` で求める（場をはなれたあとの状態で過去の特殊状態・抑止を判断しない）。
- 候補が 2 つ以上になる（同時に 2 匹がきぜつする・2 つの能力を持つ）なら、順番は番のプレイヤーが決める（p.325）と読めるが、原典で確かめるまで、ワザ・ポケモンチェックの前に止める処理（新しい `UNRESOLVED_…`）を加える。今は `RuntimeError`（P32）。
- かがくへんかガスを持つポケモンがいっしょにきぜつする場合（P19）は、ガスの終わる時点を原典で確かめるまで、止める処理を加える。今は `RuntimeError`。
- 3 章の正規化が成り立つかを見直す（サイド・手札・勝ち負けに関わる効果）。
- 決定は 1 つずつ（v0.2a）。きぜつしたときに別の決定（選ぶもの）を出す能力を加えるときは、続きの持ち方（`context`）を見直す。
- ログの監査に、その能力の「使えるか」と答えの組み立て直しを加える。
