## V0: 固定条件の 1 対戦（最初の実装の単位）

**目的**: 公開の API（`client_api` の入口）だけで、固定条件の 1 対戦を最初から進め、上限つきで終わり、記録と再実行が成り立つことを確かめる。ランダムは
`uniform-candidate+uniform-stage` の 1 つだけ、プロファイルは `deep` だけ。

**変更の範囲**

- 新規: `tools/verification_ai/__init__.py`・`actions.py`（段の契約から入力を組み立てる。仕様の 1.1 節の項目と 3.1 節の段の中の選び方。知らない項目で止める）・`policies.py`
  （`uniform-candidate+uniform-stage` だけ。`kyuura_engine` を import しない）・`runner.py`（進行・上限・終わり方の分類・照合の一部）・`records.py`（見出し・操作の列・
  CN-1 の包み・完全な記録と閲覧者ごとの記録の書き出し）
- 新規のテスト: `tests/test_verification_ai_v0.py`
- 文書: `docs/verification-ai-v0.md`（結果）、`docs/implementation-status.md`・`README.md` の 1 行
- 変えない: `kyuura_engine` のすべて、既存の `tools/`・`tests/`・`examples/`

**固定の条件（案）**: デッキ `hitmonchan-dewgong` 対 `venusaur-parasect`、既定の規約集合、`game_seed` 1 つ、`policy_seed` 1 つ、`host_seed` 1 つ（値は実装の前に決めて文書に書く）。

**上限（案）**: 操作 2,000・受理 1,000・番 200・時間 120 秒・同じ状態の拒否 16・続けての断り 32（仕様の D-11）。

**完了の基準**

1. 対戦が、仕様の 6.1 節のどれか 1 つの終わり方で上限の中に終わる（`game_over` でなくてもよい。終わり方と理由が記録にある）
2. 操作はすべて `PlayerEndpoint`・`HostEndpoint` の `handle` を通り、ランナー・方策・行動生成のどこからも `HostedGame.submit`・`apply_command` を直接呼ばない（テストで確かめる）
3. 送った入力の前に、毎回 `check` を呼んでいる。`stage_dependency_problems` の問題が 0
4. 完全な記録の `replay_run.replay` が `succeeded`（`failed` で止めた対戦なら `recorded_failure`）。閲覧者ごとの記録の `validate_view_record` の問題が 0
5. 同じ `game_seed`・`policy_seed`・`host_seed` でもう 1 回走らせると、操作の列（取っ手を除く）が同じ（R-C）
6. 方策に渡した値がすべて JSON の値で、その主体の入口の応答と同じ。`policies.py` が `kyuura_engine` を import しない
7. CN-1 を確かめる: 道具の側の包みで `ClientHub` が動くこと。あわせて、`ClientHub(ViewHost…)` が候補の取得で失敗するかを 1 つのテストで確かめ、結果をエンジンへの報告事項として
   文書に書く（エンジンは直さない）

**限定のテスト（V0 の段で実行するもの）**

- `tests/test_verification_ai_v0.py` だけを 1 回（`python -m unittest tests.test_verification_ai_v0`）
- 行動生成の単体: 段の契約の各形（`options_by_choice`・`upstream_stages`/`after`・`options_by_path` の任意の段・`options_from_stage`・`total_units`・`choose_value`）を、
  既存の U7 のテストの盤面（`tests/test_legal_actions_u7_3.py`・`u7_4`・`u7_5e`・`u7_5g_energy2` の構築の関数）から作った応答で確かめる
- 1 対戦の通しのテスト（上の完了の基準 1〜6）

**証跡**: 1 対戦の完全な記録・閲覧者ごとの記録・操作の列・要約（JSON）と、テストの結果。

## V1: ランダムの分布と到達範囲

**変更の範囲**: `policies.py` に `uniform-candidate+uniform-tuple`（組の数の上限 4,096 で `uniform-stage` に落とす。落とした事実を記録）、`records.py` に到達範囲の集計（仕様の 6.8 節）。
テスト `tests/test_verification_ai_v1.py`。

**完了の基準**: 2 つの分布の選び方が、小さな既知の段（組の数が分かる応答）で期待の分布に合う（方策の乱数の固定の種で、組ごとの回数が期待の範囲。統計の検定ではなく、
決まった種での決定的な確かめ）。到達範囲の集計が、`IMPLEMENTED_KINDS`・`DISCLOSURE_CONFIRMED_KINDS` と比べて届かなかった種類を出す。

**実行の上限**: 固定デッキ 4 つ × 3 つの規約集合 × 1 seed（12 対戦。仕様の D-12）を、1 対戦ずつ順に、上の 1 対戦の上限で。合計の時間の上限 30 分。

**証跡**: 対戦ごとの要約と到達範囲の集計。

## V2: ルールの方策と混合

**変更の範囲**: `policies.py` に `rules-v1`（仕様の 3.3 節）と `mixed`（仕様の 3.4 節）。選択ごとの理由のコード・出所・方策の乱数を使った回数の記録。テスト `tests/test_verification_ai_v2.py`。

**完了の基準**: ルールの方策が、同じ観測・候補で同じ選択と理由を返す。混合率 0 と 1 で、それぞれルールだけ・ランダムだけと同じ列になる。ルールが候補を「合法でない」と
判定する処理がない（候補の除外は理由のコードだけで、記録に「戦略が選ばなかった」と残る）。V1 と同じ 12 対戦で、ランダム・ルール・混合（例: 0.2）の到達範囲を比べた表を作る
（勝率は比べない）。

**実行の上限**: V1 と同じ組 × 3 つの方策（36 対戦）、合計の時間の上限 60 分。

## V3: `boundary` と `negative`

**変更の範囲**: `runner.py` に `boundary` のプロファイル（仕様の 4.5 節）と、別の入口の `negative` の試験（仕様の 6.5 節）。テスト `tests/test_verification_ai_v3.py`。

**完了の基準**: `boundary` で、`unverified` の拒否・`CANDIDATE_NOT_EXECUTABLE`・`INPUT_BOUNDARY_UNCONFIRMED`・表示だけの候補の断りが、期待した区分で記録される。`negative` で、
各種類の不正な入力がホストの段の拒否になり、状態（確認値）・取っ手・ほかの閲覧者への更新が変わらない。どちらの結果も `deep` の結果に混ざらない。

**実行の上限**: `boundary` は 12 対戦、`negative` は 3 対戦の決まった位置（それぞれ 1 対戦の上限）。

## V4: 情報境界の強化と U7 の経路の再実行

**変更の範囲**: 双子のテスト（公開の情報と本人の知識が同じで、相手の秘密だけが違う状態から、同じ種で同じ選択。比べる前に `observe`・`visible_log`・所有するカードの id が
同じことを確かめる）、閲覧者ごとの記録と方策の記録の分離の確かめ、R-B（記録の操作を U7 の入口で取り直して送る）。テスト `tests/test_verification_ai_v4.py`。

**完了の基準**: 双子で同じ選択。閲覧者ごとの記録に seed・相手の選択の理由・完全な記録の `seq` がない。R-B で V1 の 12 対戦の記録が同じ応答（取っ手を除く）・結果になる。

## V5: 対象の拡大

**変更の範囲**: 実行の入口（コマンドラインの道具。`--decks`・`--conventions`・`--seeds`・`--policy`・`--profile`・`--out`・上限）。証跡の保存（マニフェスト・sha256）。

**完了の基準と上限**: 利用者が対戦の数・組・時間の上限を決めてから実行する。1 対戦ずつ順に、空きメモリの下限を下回ったら止めて報告し、自動で再開しない。
対戦の数ではなく、到達範囲の表（仕様の 6.8 節）の増え方と、異常の分類で十分さを判断する。

## V6（将来）: 最小化

異常の列を、R-A・R-B の再実行で確かめながら短くする。今回の計画の範囲の外です。
