## 2. 現在の凍結判定

- 登録カードを増やす作業は終了しているが、全合法局面の完全対応を宣言しない。
- 機能凍結は未解決一覧を固定して行うことも可能。ただし、R1の既知の情報漏れを解消するか、利用範囲を明示して受容する判断が必要。
- サドン・デスを外部側が開始する契約にするなら、それも明示的な製品境界として決定し、通常の完走率から除外した理由を示す。現在は開始APIがない。
- C分類は根拠が得られるまで止める。D分類は出典と採用範囲を維持する。E/P3を単に削除する作業はしない。

## 3. 修正単位ごとの検証

各修正を独立したレビュー可能な変更にする。最小再現を旧コードで失敗させ、新コードで通す。既存の不変条件、両プレイヤー・観戦者の観測、拒否時の状態・乱数・ログ、保存・復元、監査を確認する。

共通経路を変えた修正は、関係する既存テスト、固定v0.133との比較、理由付き旧バッチで意図した差を列挙する。広い正規化や参照データの再生成で差を消さない。変異定義の適用確認と、変異を実際に検出したことを分ける。

最後にコード・テストを固めて全体を1 worker・モジュール別プロセスで走らせ、開始・終了・各終了コード・件数・skip理由・ソース指紋を保存する。修正後に全体を走らせていなければ、その限界を残す。今回の53件の選定試験と短い4局を全体試験の代わりにしない。

## 4. ストレス／総合監査の完了基準

1. コード単位のテスト言及ではなく、発生・拒否・隣の受理枝を観測した対応行列を作る。
2. 初期デッキからの合法経路、構築盤面、テスト専用の改変を別々に集計する。
3. コマンドの拒否、HALTED、途中停止、サドン・デス、内部エラー、道具の予期しない拒否を区別する。
4. 選んだseed・両席・デッキ・方策を実行前に固定。停止した局も結果から除外しない。
5. 受け付けた操作だけでなく、拒否による情報漏れと、進める回答のない決定を監査する。
6. 全600内部ガードが到達不能と証明できたといった主張はしない。残るunknownと、精査した機能・入力範囲を列挙する。
7. 凍結基準となる最終状態で全体試験と関連ストレスを行い、台帳の基点・優先度・残存制限を更新する。

## 5. 今回の制約の遵守

本計画に挙げた修正は一つも実施していない。既存のエンジン・テスト・固定デッキ・比較参照データ・kyuuraは変更せず、3つの棚卸し成果物だけを追加。コミット・push・PR作成はしていない。
