# 設計の変更（v0.4e）

v0.4e は機能を加える版ではなく、v0.4a〜v0.4d の総合監査と品質の強化の版です。ルールの処理（受け付ける操作・拒否のコード・状態の変化・ログ・乱数の使い方）は v0.4d と同じで、前の版との比較で確かめました（[compatibility-v0.4e.md](compatibility-v0.4e.md)）。監査の全体は [integration-audit-v0.4e.md](integration-audit-v0.4e.md) です。

## 1. 変えたもの

| 場所 | 変更 | 理由 |
|---|---|---|
| `effects.TrainerEffect.decision_problems` | 加えた。既定は「決定するのはトレーナーを使ったプレイヤー」。決定を出す実装（きずぐすり・ポケモンいれかえ・ディフェンダー）は上書きして、種類（`SELECT_POKEMON`）・選ぶ数（1）・選べるもの（自分の場のポケモン、ポケモンいれかえは自分のベンチのポケモン。並びも同じ）・原典で決められない選択（きずぐすりはダメージのないポケモン）を宣言する（共通の部分は `effects._select_own_pokemon_problems`） | C1。ワザの `AttackEffect.decision_problems`（v0.4d）と同じ考え方。決定を待つ間は場が変わらないので、宣言はいつでもちょうど成り立つ |
| `engine._trainer_problems` | 共通の確認（使用中のトレーナー・続きの情報・番のプレイヤー・登録表）のあとで、実装の `decision_problems` を呼ぶ | 同上 |
| `engine._decision_problems` | サイドを取る・バトル場に出す決定（v0.1 からある種類）の再開先が種類と同じこと、選ぶ数が 1 つであることを、いつも確かめる（それまではポケモンチェックの中の決定だけ）。両方がバトル場に出すときの順番（番でないプレイヤーが先。pp.323〜324）を確かめる | C2・C4 |
| `engine._prize_queue_problems` | 加えた。サイドを取るプレイヤーの並び（決定するプレイヤーと残り）と、すでに取ったサイドをあわせたものが、直前のきぜつ（ログ `knock_out`）から決まる「だれが何枚取るか」と同じかを確かめる。順番は確かめない（同時のきぜつで両方が取る順番は番のプレイヤーが選べる。p.325。エンジンの正規化（v0.2f）と違う順番もルール上は正しい） | C3 |
| `engine._progress_problems` | 状態の番の番号・番のプレイヤーが、最後の `turn_start` の番・プレイヤーと同じかを確かめる | C5 |
| `kyuura_engine.__version__`・pyproject.toml | `0.4.0e0` | 版の名前 |

効果の登録表の id（`kyuura-engine-0.4d`）は変えていません。登録の中身（どのカード・ワザ・トレーナーに、どの実装を登録したか）が変わっていないためです。

## 2. 変えなかったもの

- ルールの処理・裁定の分類・処理の順番（原典に新しい根拠がない。[unresolved-audit-v0.4e.md](unresolved-audit-v0.4e.md)）
- 書き出しの形式（形式 1〜8 のまま。形式 9 は加えていない。v0.4e の変更は状態の項目を増やしていない）
- ログの形（イベントの種類・項目）。ログを状態の正本にはしていない（不変条件と監査は、状態とログの対応を確かめるだけ）
- 固定値（tests/test_reproducibility.py・各対戦のテストの `GOLDEN_DIGEST`・`EXPECTED_COUNTS`・tests/fixtures/v0_1_reference.json）
- ポケモンパワーの基盤（先行して実装していない。[v0.5-readiness.md](v0.5-readiness.md)）

## 3. 不変条件を強めたときの確認

強めた確認が合法な状態を拒否しないことを、次で確かめました。

- 既存のすべてのテスト（958 件）が、強めたあとも変更なしで通る
- 自然な対戦: v0.4e の 48 局（tests/test_combined_games_v0_4e.py）と、既存の 13 の対戦のテストの手順で 15 局ずつ（195 局）
- 前の版との比較（50 局・11,377 手）で、受け付けた操作・拒否のコード・状態が v0.4d と同じ
- ストレス実行（[integration-audit-v0.4e.md](integration-audit-v0.4e.md) 10 章）で内部の誤り（`StateIntegrityError` を含む）が 0

最初の C3 の実装は、サイドを取る順番まで正規化した並びと比べていて、tests/test_simultaneous_ko.py `PrizeOrderTest`（同時のきぜつで、正規化と逆の順番で取っても結果が同じことを確かめるテスト）の状態を拒否しました。p.325 で順番は番のプレイヤーが選べるので、その状態はルール上正しいと判断し、既存のテストは変えずに、C3 を「だれが何枚取るか」の比較に直しました。

## 4. テストの段階

| 段階 | 内容 | 走らせ方 |
|---|---|---|
| A 速い単体テスト | 1 つの規定・1 つの組み合わせのマス（盤面を直接作る） | `python3 -m unittest`（ふだん） |
| B 決まった seed の統合テスト | `new_game` からの対戦（48 局）・ログと書き出しの監査・小さなストレス実行（8 局）・前の版の参照データとの比較（4 局） | `python3 -m unittest`（ふだん） |
| C 大規模な実行 | ストレス実行（tools/stress_engine.py）・前の版との大きな比較（tools/compare_engine_versions.py） | 明示的に実行する（ふだんのテストでは走らない） |

## 5. 道具

| ファイル | 役割 |
|---|---|
| tools/compat_driver.py | 版の比較の駆動（公開の API だけを使う。別のプロセスで 1 つの版を動かす） |
| tools/compare_engine_versions.py | 2 つの版の比較（`git archive` で取り出した木・別のプロセス・最初の食い違いの診断） |
| tools/stress_engine.py | ストレス実行（結果の分類・拒否で状態が変わらないことの確認・ログと書き出しの監査・問題のある seed の記録） |
| tests/log_audit.py | ログと状態の整合（ログから組み立て直した場のポケモンのダメージ・エネルギー・トラッシュ・サイド）と、書き出しの形式 1〜8 の監査。テストではない（`test_` で始まらない） |

## 6. この先の変更で気をつけること

- 決定を出すトレーナー・ワザを加えたら、その実装の `decision_problems` で決定の形を宣言する（宣言しなければ、既定の確認だけになる）。
- ログに場のポケモンのダメージ・エネルギー・トラッシュを変えるイベントを加えたら、tests/log_audit.py の組み立て直しにも加える（加えないと監査が違いを報告する）。
- 状態の項目を加えたら、tests/log_audit.py の `required_format`・`POKEMON_FIELDS_SINCE`（書き出しの監査）を更新する。
- 駆動（tools/compat_driver.py）を変えたら、参照データを基準の版から作り直す。
