  - 集計（`aggregate`）が局の記録と一致する。
  - キャッシュ（checked-hash の pyc）が変わっていない。
  - 次の局を始められる（開始前の条件を満たす）。
- 費用評価・D4・［エナジートランス］が出ることは、条件にしません。
- 打ち切り:
  - 停止方針の発動、実行・照合の異常、予算不足のときに打ち切ります。
  - 打ち切ったときは、未完了の局（始めて終わらなかった局）と未着手の局を分けて数えます。
  - 再試行・停止の解除・追加局・上限の延長は、この計画に含めません（別の判断）。

## 8. 測定項目と証拠

- 完走率: `game_over`／着手した局数です。条件・方策ごとに、件数と終了の理由（`game_over`・上限・停止）を並べます。
- 費用評価（rules-v8 の `energy_trans_progress`。ワザと「にげる」を分ける）:
  - 評価できた件数（目標ごと）
  - 判断できず従来の選び方へ戻った理由ごとの件数（`unevaluable:*`、`skipped` の理由。例: `attack_special_energy_on_active`・`moved_card_not_basic`・`retreat_*`）
  - 費用を初めて満たすまでの移動の数
  - 実際に受理された後続の操作（選択・組み立て・送信・受理）
  - 「未出現」（［エナジートランス］を選ばなかった）・「未到達」（満たす前に番の終わりやバトル場の交代）・「評価不能」は、別々に数えます。
- D4: 選択の対象が変わった件数（`kept`）を、優先段階による絞り込み（`restricted` で D4 が `all_keep`・`none_keep`・なし）と分けて数えます。
  - 変化があれば、次の 3 点を記録します。
    - 同じ段に崩す組と維持する組があったこと（記録の段の大きさと `set`）
    - 実際に選んだ組
    - その組が受理されたか
  - 構築盤面の確認（[D4 の構築盤面での確認](tr8-rules-v8-d4-board-verification.md)）は、通常の対戦の実績に含めません。
- 各組の最初の差: 最初に候補が変わった地点と、最初に操作（送信）が変わった地点を求めます。分岐のあとの総操作数と勝敗は参考として示します。
- `rules-v8` が働かなかった組（評価 0）も報告します。
- この監査だけで、全デッキの完走率や既定化は判断しません。
- 証拠: 局ごとの照合の出力、条件・方策ごとの集計、組ごとの比較の JSON（実行の単位の作業記録の下）。

## 9. 実行時に決まる値（JSON では `null`）

- 確定計画の `plan.sha256`（16）
- 明示リストの保存先のパス（新しい 3 条件の 6 席）
- キャッシュの準備の記録
- 局ごとの量、先行のあとの見積もり、実行前の seed の再照合の結果
- 完走率・費用評価・D4・最初の差の値
