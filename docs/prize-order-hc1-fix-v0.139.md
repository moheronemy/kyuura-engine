## 2. 同時のきぜつでサイドを取る順番

### 2.1 問題（修正の前の再現）

new_game(seed=473) からの合法な操作（P0: コイル PMCG1-036 ×4・ロケット団参上! PMCG4-062 ×4・雷 ×52 / P1: コラッタ PMCG1-060 ×4・水 ×56。`finish_setup(janken_winner=0)` →
1 番 P0 雷をつけて番を終える → 2 番 P1 番を終える → 3 番 P0 雷をつけ、ロケット団参上!、じばく）で、両方のバトル場のポケモンがきぜつし、両方のサイドがおもてになる。基点の木では:

- 最初の決定は P0（番）の `take_prize`（`remaining` は `(1,)`）。順番を選ぶ決定はない
- P0 が取ったあと、P1 の `take_prize` の時点で、P1 の `visible_log` に P0 の `take_prize`（カード uid 57。おもてだったので `card` が見える）がある

v0.2f（[simultaneous-ko-v0.2f.md](simultaneous-ko-v0.2f.md) 5 章）は、順番を正規化してよい理由の 2 つ目を「後に取るプレイヤーが自分のサイドを選ぶのに使える情報は増えない」とし、
前提に「サイドを見る・入れ替えるカードが対応カードにない。成り立たなければ p.325 の選択（番のプレイヤーが順番を選ぶ決定）を実装する」と書いていた。v0.63 のロケット団参上!・v0.80 の
カードめくりゲーム（`GameState.face_up_prizes`）で、この前提が成り立たない場面が合法な操作で起こる。

### 2.2 根拠と適用範囲

**適用範囲の不足（明示）**: サイドを取ることが p.325 の「同じタイミングで起こったことがら」に当たることは、原典に直接の記述がなく、v0.2f の導出（SUPPORTED）のままである。
「順番をまとめて先に決める」か「1 枚ずつ次を決める」かも原典は書かない。この版は、既存の p.325 の実装（反応の順番）と同じ「1 つずつ次を選ぶ」形を使った。これは実装の形であり、
新しい裁定・プレイ用の規約として記録していない。p.325 のこの場面への当てはめを、公式資料にない処理順の承認として広げていない（両方がサイドを取る場面のほかの処理順は変えていない）。

| 変えていないこと | 先後・サイドの枚数・きぜつの処理・勝ち負け（すべて取ってから判定）・サドン・デス・バトル場に出す順番（番でないプレイヤーから）・トラッシュの順番 |

### 2.4 意図した差

- おもてのサイドがあり両方がサイドを取る局だけ、`take_prize` の前に `prize_order` の決定が 1 つ（1 匹ずつ 2 匹以上なら、まだ両方が残るたびに 1 つ）増え、決定の番号がずれる。番の
  プレイヤーを先に選べば、カードの動き・ログの種類の並び（決定を除く）・結果は基点と同じ。相手を先に選べば、`take_prize` の順番と、それぞれの決定の時点の観測が変わる
- どのサイドもうらの局は変わらない（決定もログも同じ）

対戦の道具の方策（`tests/helpers.py` の `trainer_policy_command`）は、この決定に番のプレイヤーを選ぶ（v0.2f の正規化と同じ順番。旧バッチの結果と比べられるように）。

### 2.5 残る制限

- **自分だけが知っているサイド**: にせオーキドの発明（neo4-111）でサイドを見た・コラッタ（PMCG4-045）の［わるふざけ］でサイドと山札の一番上を入れ替えたなど、プレイヤーが位置ごとに中身を知っているうらのサイドは、
  エンジンの観測が表さない（取ったサイドの位置もログに残らない）。その場面で順番が情報を変えるかは確かめておらず、この版の出す場面に入れていない（未確認）
- 「1 つずつ次を選ぶ」形は既存の p.325 の実装に合わせた形で、「まとめて先に決める」読みとの違い（決める時点の情報）は原典で決まらない（2.2 節）

## 3. HC1 の手順 4 のコイン

v0.114 はベイビィポケモンのルールのコインに止める場面を広げたが（[baby-rules-evolution-v0.114.md](baby-rules-evolution-v0.114.md)）、手順 4 のコインには広げていなかった。
