# ［ダメージスワップ］の往復だけを後回しにする方策 rules-v4 の実装と比較

2026-11-24。基点 `claude/tr8-damage-swap-transition-policy-design` の `988bdc5`（[設計](tr8-damage-swap-transition-policy-design.md)）。実装のコミットは `8dc96a2`
（道具の版 15。エンジンは 0.198.0 のまま、`a358378` からエンジンの差分なし）。`rules-v4` は明示的に選んだときだけ使う試験の方策で、既定にしない。
`rules-v2`・`rules-v3`・既定の方式・エンジンの合法性・規約 TR8・judge・単局上限は変えていない。機械可読の値は同名の JSON にある。

設計の未決事項 U1 は、**追加の抑制を入れずに試す**と決めて実装した。1 番あたりの新しい使用上限も、検出の回数による持ち主の全体の降格も入れていない。
既存の同一入力の再送抑止（`rules-v2` の入力単位の評価）と単局上限はそのまま。

## 0. 要約

- **S5 で別の移動を受理できたか**: 4／4 seed で受理した。`1 → 2 → 1` の往復のあと、戻った観測で `1 → 2` だけを入力の選べるものから外し、［ダメージスワップ］の候補は順位 5 のまま。
  方策自身が `1 → 3` を選び、通常の `candidates` → `inputs` → 組み立て → `check` → `submit` で受理された。`1 → 3` のあとの観測で新しい周期は検出していない。
- **9023 は完走したか**: 完走した（`game_over`、41 番・受理 161）。受理の上限には達していないので、採用の保留の条件（9023 が再び上限に達する）には当たらない。
- **往復・使用数は `rules-v3` からどこまで戻ったか**（往復は直後の逆操作と周期の操作の数。`rules-v2` → `rules-v3` → `rules-v4`）:
  - 9023: 往復 601 → 8 → 10、［ダメージスワップ］の受理 775 → 11 → 12、1 番の最大 84 → 5 → 4。
  - 9022: 往復 20 → 7 → 16、受理 38 → 19 → **46**、1 番の最大 18 → 6 → **17**。
  - 9024: 往復 8 → 4 → 6、受理 9 → 5 → 6、1 番の最大 4 → 3 → 4。
- **`rules-v2`・`rules-v3` は維持されたか**: 維持された。新しいコードでの `rules-v2`・`rules-v3` の行動の列は、基点のコードの値と 4／4 で同じ（既定のデッキ seed 13、L67-U seed 9023）。
  新しい `rules-v3` の 3 局は、保存済みの `rules-v3` の 3 局（道具の版 14）と試みの列・行動の列がすべて同じだった。
- **追加の抑制を検討すべき証拠があったか**: あった。9022 では `rules-v4` の［ダメージスワップ］の受理が `rules-v2` を上回り（46 対 38）、1 番の最大（17）も `rules-v2`（18）に近い。
  その 17 回の番の検出は 1 回だけで、観測が以前と完全に一致しないまま移動が続き、`rules-v2` の再送抑止で番を終えた。検出の回数に応じた歯止めでは止まらない形なので、
  検討するなら 1 番あたりの使用数か、ダメージの配置の戻りで数える歯止めになる。9023 では使用数は増えていない。採用は判断していない（5 章）。

## 1. 実装

### 1.1 方策 `rules-v4`（`policies.TransitionRulePolicy`）

- `rules_version` 4・分布 `rules-v4-candidate+uniform-stage`。`rules-v2` の順位・同順位の選び方・入力単位の評価はそのまま。`rules-v3` の `LoopRulePolicy` は継承していない（`rules-v3` を変えないため）。
- 検出は `rules-v3` と同じ: 同じ番・同じ主体の［ダメージスワップ］の受理が続く区間で、本人の観測の応答（観測の外の識別子だけを除く）が区間の以前の観測に戻ったら周期を確認する（直近の一致）。
- 周期を確認したときだけ、直近の一致から今回の受理までの各移動を **（操作前の本人の観測, 持ち主の鍵, 移動元, 移動先）** で記録する。方向付き。
  持ち主の鍵は `rules-v3` の `loop_key`（種類と場のポケモンの番号）、移動元・移動先は受理した入力の意味の `option.pokemon`（場のポケモンの番号）。候補の番号・選べるものの番号・場所は使わない。
  番号が取れない移動は記録しない（件数 `keys_missing_ref`）。
- 別の操作・別の主体の受理で区間を切り、記録した鍵は番の終わりまで保つ。番が変われば区間・鍵・組の写しを消す。拒否・組み立ての失敗・送信の抑止では受理の履歴を進めない。

### 1.2 候補と入力の扱い

| 場面 | 扱い | 理由のコード・記録 |
|---|---|---|
| 今の観測 V・持ち主 h に鍵がない | 順位も入力も `rules-v2` のまま | `rule4:…` |
| 鍵があり、V での h の組に鍵にないものがある | 順位は 5 のまま。入力の段で鍵の組だけを外して選ぶ（段ごとの乱数は 1 回のまま） | 試みの `input_restriction`（`restricted`・外した組） |
| (V, h) の組の写しがすべて鍵にある | `inputs` を取り直さず、候補を順位 7（`end_turn` の後ろ） | `:deferred_allN` |
| 新しい `inputs` の応答で外さない組が 0（写しと食い違い） | 組み立てずに、そのエピソードで候補を順位 7 にして選び直す | 試みの `build` が `transition_deferred_all`・`pairs_cache_mismatch` |
| 順位 7 の候補しか残らず、後回しで下げた候補を選んだ | その試みの入力を制限しない（`rules-v2` の再送抑止は効く） | `:no_alternative`・`lifted_no_alternative` |
| 組の写しがない・段の形が違う・範囲が `deep` でない | 推測で下げない・制限しない | `restriction_unavailable` |

### 1.3 道具の差し込み口（`rules-v4` の物だけが持つ）

- `runner`: `inputs` の応答のあと・組み立ての前に `observe_inputs(candidate, stages, allowed)` と `input_restriction(candidate, stages, allowed)`、本人の受理のあとに
  `accepted_input(candidate, meaning, position)` を呼ぶ。`rules-v2`・`rules-v3` の物はこれらを持たない（試験で確認）。
- `actions.transition_pairs(stages, allowed)`: 2 段の移動の入力（段 2 が `depends_on_stage: 1` と `options_by_choice` を持つ）の、組み立てられる（移動元, 移動先）の番号の組。
  `build_choices` と同じ `_allowed_ids` で引くので、段を独立に組み合わせた存在しない組は作らない。
- `actions.build_choices(..., restriction=None)`: 外す組の集合を与えたときだけ、移動元の段では外さない移動先が残る移動元だけ、移動先の段では外さない組だけを選べるものにする。与えないときの動作は今と同じ。
- `batch`: 方式 `rules-v4`、計画の方策の記録 `transition_deferral`、`TOOL_VERSION` 15（版 14 の計画は道具の識別の違いで再開しない）。`run_v1.game_header` は版 4 にも閾値を書く。
- 使う値は本人の観測・候補・`inputs` の応答だけで、相手の非公開の情報やエンジンの内部状態は読まない。

## 5. U1 の判定と採用

- 採用の保留の条件（9023 で受理の上限に再び達する）には当たらない。9023 は完走し、使用数は `rules-v3` と同程度（12 対 11）にとどまった。
- ただし 9022 では、`rules-v4` の使用数が `rules-v2` を上回り、1 番の最大も `rules-v2` とほぼ同じに戻った。U1 で心配した「最悪の数は `rules-v2` と同じ上限」が実際に起きた。
  観測の全体の一致による検出は、この番の繰り返しを 1 回しか捉えなかった。
- 判定: **追加の抑制を検討すべき証拠はある**。今回は試験の条件どおり入れていない。入れる場合の候補（どれも未実装・未検証）:
  1 番あたりの［ダメージスワップ］の受理の上限、ダメージの配置（自分の場のポケモンのダメージ）の戻りで数える検出、検出の回数による `rules-v3` の持ち主の単位への切り替え（9022 の番 36 では検出が 1 回なので効かない）。
- `rules-v4` の既定化・採用は判断していない。3 局・1 条件（C1）の結果で、使用数の増減は seed によって向きが違う。

番 36 の 17 回の照合と追加の抑制の判断は [9022 の抑制の調査](tr8-rules-v4-9022-guard-analysis.md) にある。
番 36 では配置の戻りは 1 回（= 検出）で、配置の戻りで数える検出の案は効かない。推奨は、1 番あたりの受理の回数で順位を下げる案（N = 6）。
