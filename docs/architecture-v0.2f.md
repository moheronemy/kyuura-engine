# v0.2f のアーキテクチャ（自分へのダメージと同時のきぜつ）

> **v0.3d の見直し**: この版で加えた `self_damage_problem`（`UNRESOLVED_SELF_DAMAGE_WEAKNESS_RESISTANCE`）は、v0.3d で原典の根拠（p.90 の解説）が見つかったので外しました。自分へのダメージにも弱点・抵抗力を計算します（[architecture-v0.3d.md](architecture-v0.3d.md) 4 章）。以下は v0.2f の時点の記述です。


v0.2f は、ワザを使ったポケモンが自分自身にダメージを与える処理と、1 つのワザで両方のプレイヤーのポケモンがきぜつする処理（同時のきぜつ）を加えた版です。最初のカードはピカチュウ（PMCG1-035）の「かじる」「でんげき」です。原典の照合と裁定は [self-damage-v0.2f.md](self-damage-v0.2f.md)（自分へのダメージ）、[simultaneous-ko-v0.2f.md](simultaneous-ko-v0.2f.md)（同時のきぜつ）、[pikachu-v0.2f.md](pikachu-v0.2f.md)（カード）にあります。v0.2e の設計（[architecture-v0.2e.md](architecture-v0.2e.md)）の上に作っています。

## 1. 目的と範囲

- ワザのダメージの**発生源**（ワザを使うポケモン）と**受けるポケモン**を分け、同じ p.321 の計算の順番で、相手の対戦ポケモンにも自分にもダメージを与えられるようにする。
- 自分へのダメージに、プラスパワー（5 段階、使う側）とディフェンダー（7 段階、受ける側）を、原典（p.257 の解説、p.321）どおりに一度ずつ計算する。
- 自分のワザで自分のポケモンがきぜつすること、相手と自分のポケモンが同時にきぜつすることを、サイド・勝ち負け・バトル場に出す順番まで原典どおりに処理する。
- 既存の対戦結果・ログ・状態の書き出し・乱数の使い方を変えない。

作らなかったもの: 汎用のカード効果の記述言語、イベントの仕組み、控えポケモンへのダメージ、特殊状態（こんらんの自分へのダメージを含む）、ワザの失敗、サドン・デスの延長戦、サイドを取る順番を選ぶ決定。

## 3. ダメージの発生源と受けるポケモン

p.320 はワザの要素の「ダメージ」を、受けるポケモンで 4 つに分けます:「(1) 相手の対戦ポケモンへのダメージ。(2) 相手の控えポケモンへのダメージ。(3) このワザを使うポケモンへのダメージ。(4) 自分の控えポケモンへのダメージ。」v0.2f はこのうち (1) と (3) を `target` の値として持ちます。

| 役割 | 決め方 | 使うところ |
|---|---|---|
| 発生源（ダメージを与えるポケモン） | いつもワザを使うポケモン（`use.pokemon_id`） | 弱点・抵抗力のタイプ（p.321 の 3・4 段階は「ワザを使うポケモンのタイプ」）、5 段階のカード |
| 受けるポケモン | `damage_receiver(state, use, target)`: `OPPONENT_ACTIVE` は相手のバトル場、`SELF` はワザを使うポケモン自身 | 弱点・抵抗力の値、7 段階のカード、ダメージカウンターをのせる先、ログの `player`・`pokemon` |
| 受けるプレイヤー | `OPPONENT_ACTIVE` は相手、`SELF` はワザを使うプレイヤー | ログ `damage.player` |

`target` の種類を文字列の定数にしたのは、ログにそのまま書け、控え（(2)・(4)）を加えるときに値を足すだけでよいためです。未知の値は `ValueError`（エンジンの不具合）。

自分へのダメージの計算は、受けるポケモンが自分であること以外は相手へのダメージと同じです（p.321「8」: ワザによってもたらされたダメージは「ワザによるダメージ」）。弱点・抵抗力は、ワザを使うポケモンのタイプが、受けるポケモン（自分）の弱点・抵抗力のタイプかで決まります。ワザの説明による自分へのダメージに弱点・抵抗力を計算するかは原典に書かれていないので、それが結果に関係する場合（自分のタイプ = 自分の弱点・抵抗力のタイプ）だけ止めます（`self_damage_problem`。[self-damage-v0.2f.md](self-damage-v0.2f.md) 2 章 #3）。

## 4. `DamageModifier` との統合

`attack_damage_modifiers(state, attacker, defender)` は、ワザを使うポケモンについているカードに `role="attacker"`、受けるポケモンについているカードに `role="defender"` で効果を聞きます（v0.2c・v0.2e）。自分へのダメージでは `attacker is defender` です。

| ついているカード | `role="attacker"` で聞く | `role="defender"` で聞く | 自分へのダメージでの結果 |
|---|---|---|---|
| プラスパワー（`AttachedAttackBonus`） | 5 段階 +10 | なし | +10（一度だけ） |
| ディフェンダー（`AttachedDamageReduction`） | なし | 7 段階 −20 | −20（一度だけ） |

各カードの実装が自分の立場でだけ効果を返すので、同じポケモンを両方の立場で聞いても、同じカードを二重に数えません。v0.2e で検討した「`DamageModifier` に対象の項目を加える」ことはしていません。変更効果はダメージ 1 つ（ログの `damage` 1 件）ごとに計算し、その `damage` に `target`・`pokemon_id` があるので、どのポケモンへのダメージの効果かはログから分かるためです。

変異テスト（自分へのダメージでディフェンダーを二重に数える、変更効果を使わない）は、test_self_damage.py `SelfDamageModifierTest` が検出します。

## 5. ワザの効果: コインと自分へのダメージ

`SelfDamageOnTails.resolve` の手順:

1. `self_damage_problem` を確かめる（原典で決められなければ、ダメージもコインもなく `UnsupportedError`）。
2. 相手の対戦ポケモンにダメージの目安の数字ぶん（`damage_opponent_active`）。
3. コインを 1 枚投げる（`flip_coins`。v0.2d の唯一の口。乱数を 1 回）。
4. 「うら」なら `deal_attack_damage(state, use, SELF, self_damage)`。

- **原子性**: `apply_command` は渡された状態を clone してから処理する（v0.1 から）。途中で `UnsupportedError` が出ても、渡された状態と乱数は変わりません。テスト専用の効果でコインを投げてから止めても同じです（`test_error_after_the_coin_keeps_the_original_state`）。
- **乱数**: 不正な操作・決められない操作では乱数を使いません（1 の確認がコインの前。CLAUDE.md のコインの約束）。「おもて」なら自分へのダメージがないことを理由に、投げてから使えるかどうかを決めることはしません（`test_stops_before_any_damage_or_coin` は「おもて」「うら」の両方で確かめる）。
- **ワザの途中のきぜつ**: 2 で相手のポケモンが HP に達しても、3・4 は処理します（p.309「それ以降の内容を無視してはいけません」）。HP の判定はワザの要素をすべて処理してから（6 章）。

## 6. きぜつ・サイド・勝ち負け・交代

`engine._finish_attack` が、ワザの要素をすべて処理したあとで、場のすべてのポケモンについて HP 以上のダメージを確かめます（相手 → 自分の順。トラッシュに順番はない p.312）。

```
_finish_attack
  ├─ きぜつの一覧を作る（相手のバトル場・ベンチ、自分のバトル場・ベンチ）
  ├─ _knock_out（それぞれ。2 匹以上なら simultaneous=True）
  │    ポケモン・エネルギー → 持ち主のトラッシュ、ついているトレーナー → 使ったプレイヤーのトラッシュ
  └─ _after_knockouts(prize_takers)  ← きぜつ 1 匹につき、その持ち主の相手側のプレイヤー（p.323）
       ├─ サイドの並び（番のプレイヤーのぶんが先。残りより多くは取らない）
       ├─ _next_prize_or_judge: TAKE_PRIZE の決定を 1 つずつ → すべて取ったら judge.decide（p.311 の表）
       │    決まれば _finish（GAME_OVER / SUDDEN_DEATH）
       └─ _next_promotion_or_end: PROMOTE_ACTIVE の決定（番でないプレイヤー → 番のプレイヤー。pp.323〜324）
            → _end_turn（期限のきたトレーナーのトラッシュ → turn_end → 次の番）
```

v0.2f でこの流れの構造は変えていません。v0.1 から、場のすべてのポケモンを判定し、サイドを取ってから判定し、番でないプレイヤーが先に出す形になっていました。v0.2f で変えたのは、きぜつの一覧を先に作ってから処理すること（`simultaneous` の印のため）と、ログの印です。同時のきぜつの原典照合・順番の区別・正規化の理由は [simultaneous-ko-v0.2f.md](simultaneous-ko-v0.2f.md) にあります。

自分のワザで自分のポケモンだけがきぜつしたときも同じ流れで、相手がサイドを取り、自分がバトル場に出します（出せなければ負け）。最後のサイドが相手のぶんなら相手の勝ちです。

## 7. PendingDecision との関係

- 決定の種類は増やしていません。サイドは `take_prize`、バトル場は `promote_active`（v0.2a）。
- 残りの並びは決定の `context` の `remaining` に持ちます（v0.2a）。同時のきぜつでは、サイドの決定が 2 つ、バトル場の決定が 2 つ、この順に 1 つずつ出ます。決定は一度に 1 つ（CLAUDE.md の約束）。
- サイドを取る順番を選ぶ決定（p.325）は出しません（正規化）。サイドに関わるカードを加えるときに見直します。
- `TakePrize`・`PromoteActive`（v0.1 のコマンド）も、`ResolveDecision` も、そのまま使えます。

## 8. 不変条件

新しい状態がないので、`check_invariants` に加えたものはありません。v0.2f の処理は、既存の不変条件で次のように確かめられています。

| 不変条件（既存） | v0.2f での意味 |
|---|---|
| 場のポケモンが HP 以上のダメージで残っていない（v0.1） | 自分へのダメージで HP に達したポケモンは、必ずきぜつの処理を受ける（変異テスト「自分のきぜつを確かめない」は、これで `StateIntegrityError` になる） |
| バトル場の空きは `TAKE_PRIZE`・`PROMOTE_ACTIVE` の段階だけ（v0.1） | 同時のきぜつのあいだ、両方のバトル場が空でもよいのはこの段階だけ |
| サイドの決定: 取る回数が残りのサイドより多くない、並びのプレイヤーが正しい（v0.2a） | 両方がサイドを取る並び |
| バトル場の決定: バトル場が空のプレイヤーが全員並びに入っている、選べるものがベンチと合う（v0.2a） | 両方が出す並び |
| カードの保存則、ついているトレーナーの持ち主（v0.1・v0.2c） | きぜつしたポケモンのカードとついているトレーナーが、それぞれの持ち主のトラッシュに 1 回だけ入る |

## 9. 状態の書き出し

新しい状態がないので、形式は変えていません（形式 1〜4。既定は形式 1）。**形式 5 は加えていません。** 同時のきぜつのあとの状態（サイドの決定を待つ、両方のバトル場が空）は、形式 1 から書き出せます（決定の中身は形式 2 以上）。ついているトレーナーがある場合は形式 4（v0.2c から）。

## 11. 互換性

[api-review.md](api-review.md) の「v0.2e → v0.2f」と、最終報告の E にまとめています。

- コマンド・エラーコード: 増やしたエラーコードは `UNRESOLVED_SELF_DAMAGE_WEAKNESS_RESISTANCE`（v0.2f のカードでは起こらない。テスト専用のカードで確かめる）だけ。既存の操作のエラーコードは変わらない。

| 特殊状態（v0.3。v0.3a でどく・ポケモンチェックを実装。[architecture-v0.3a.md](architecture-v0.3a.md)）。こんらんの自分へのダメージ 20（弱点・抵抗力を計算する。p.322） | `deal_attack_damage` の計算の経路 | 状態の項目（ポケモンごとの特殊状態。形式 5）、ポケモンチェック（番の終わりのあと）、ワザ・にげるの前のコイン、こんらんの自分へのダメージを「ワザによるダメージ」として計算するかの照合 |
| ワザの失敗 | 番の終わりの流れ | 失敗してもワザを使ったことになる（p.323）。失敗の記録 |
| 進化・退化 | `pokemon_id`（進化しても同じ） | ダメージ・ついているカードの引き継ぎ（p.324）、HP が減ってきぜつする場合のきぜつの時点 |
| サイドに関わるカード | サイドの並び | p.325 の順番の選択（番のプレイヤーが選ぶ決定）を実装するかの見直し |
| サドン・デスの延長戦 | `Phase.SUDDEN_DEATH`、勝ち負けの表 | 新しい対戦の始め方（p.324）。ジャンケン・切り直しの扱いの読み方を決める |

## 13. 設計上のトレードオフ

| 判断 | 理由 | 代償 |
|---|---|---|
| 受けるポケモンを文字列の種類（`target`）で表した | ログにそのまま書ける。控えへのダメージで種類を足せる | 控えのように「どのポケモンか」を選ぶ場合は、種類に加えて `pokemon_id` を渡す形が要る |
| `DamageModifier` に対象の項目を加えなかった | 変更効果はダメージ 1 つごとに計算し、そのダメージの記録に対象がある | 1 つのダメージを複数のポケモンに分ける効果があれば見直す |
| 自分へのダメージの弱点・抵抗力を、関係する場合だけ止めた | 原典で決められない場合を推測で実装しない。関係しない場合は、どちらに決めても結果が同じ | 自分のタイプと同じタイプが弱点・抵抗力のポケモンに自分へのダメージのワザがあれば、使えない |
| サイドの順番を選ばせずに正規化した | 結果・情報・選べるものが変わらない（原典で確かめた）。操作を増やさない | サイドに関わるカードを加えるときに見直しが要る |
| きぜつの処理をワザの要素のあとにまとめた | p.309（要素を無視しない）、p.324（同時）。v0.1 からの流れのまま | ワザの途中で対象がいなくなる（きぜつしたポケモンへの続きの要素）を扱うカードを加えるときは、途中のきぜつの扱いを照合する |
