## 1. 結論

- **補足監査の 2 局面**（`vai-batch-tr7s-c4` g001・番 35 と番 63）は、どちらも同じ形でした。
  1. 本人（主体 0。LUCKY_DECK）がこの番に場のラッキースタジアム（PRN-015）を 1 回使う。
  2. 手札から別の PRN-015 を出して入れかえる。
  3. 新しいカードの `use_stadium` が RS1（`UNRESOLVED_STADIUM_REUSE_AFTER_REPLACEMENT`）の条件で候補から外れる。
  4. 本人は「にげる」を選んで入力を取得したが送らず、取り直して番を終わり、その送信は受理された。

  2 局面は別の使用と別の入れかえで、共有していません。局面 2・使用 2・使用のあとの入れかえ 2 です。番 63 には使用の前の入れかえがもう 1 回あります（57→58）が、除外にはつながっていません。
- **旧 TR3・TR6 監査のコード不明の `use_stadium`** は、すべて RS1 に対応づけられました。延べ・取り直し除外後・局面・局の数は旧集計と同じです。
  - TR3: 先行 2 / 1 / 1 / 1、本実行 14 / 7 / 7 / 4
  - TR6: 先行 2 / 1 / 1 / 1、本実行 6 / 3 / 3 / 2

  どれも実測の診断ではなく、局面の状態の記録と実行時のソースの判定の順番から静的に照合したものです。コード不明は 0 です。
- **史料が定める制限の単位:** 印刷の文面は「おたがいのプレイヤーは、それぞれ、のぞむなら、自分の番ごとに1回」です。プレイヤーごと・自分の番ごとの 1 回であることは書かれています。同じ名前の別のカードに入れかわったあとに、新しいカードの効果として数え直すかは書かれていません。2000.02.14 版の公式ルール・kyuura の記録（固定コミット `71d1728`）・既存の裁定のどれも、この場面に直接は答えません。
- **推奨: 追加検証が先**（7 章）。採用の候補の形は、ラッキースタジアムの「自分の番ごとに1回」の版だけに限り、場に出たカードの個体ごとに数える明示選択の規約です。その規約にすると、保存局面 14 のそれぞれで、手が 1 つ（`use_stadium`）増えます。

## 5. 実行時のソースの経路

3 つの実行コミットで、関係する関数・クラス・定数のソースの区間と、`stadium_uses_this_turn` を含む行の sha256 が同じでした（`out/source_check.json`。6 ファイルの 23 区間と、7 ファイルの記録を含む行。合わせて 10 ファイル）。以下の行番号は `bca9623` のものです。

- **判定の順番:**
  1. `engine.check_use_stadium`（`kyuura_engine/engine.py:2599`）で、番・段階（`require_turn`）と場のスタジアム（`NO_STADIUM`）を確かめる。
  2. 実装の `check_activation` を呼ぶ。
  3. ラッキースタジアム `CoinDrawStadium.check_activation`（`effects.py:21451`）が、`energy` の指定（`STADIUM_CHOICE_NOT_USED`）を確かめ、`_check_stadium_use_count`（`effects.py:21390`）を呼ぶ。

  `_check_stadium_use_count` の中の順番は次のとおりです。

  | 順 | 条件 | 結果 |
  |---|---|---|
  | 1 | (本人, このカード) の記録があり、使ったあと同じ番に場にもどった（`stadium_returned_after_use`） | SX2 `UNRESOLVED_STADIUM_REUSE_AFTER_RETURN` |
  | 2 | (本人, このカード) の記録がある | `STADIUM_ALREADY_USED`（ゲーム上できない。候補を作らない） |
  | 3 | トレーナーの使用の禁止（`trainer_use_blockers(from_hand=False)`） | STB1 `UNRESOLVED_STADIUM_ACTIVATION_UNDER_TRAINER_BAN` |
  | 4 | 「自分の番ごとに1回」のない版（PRN-027）で、同じ名前の記録がある | LK1 |
  | 5 | 「自分の番ごとに1回」の版で、同じ名前の別のカードの記録がある | **RS1** |

  どれも状態・乱数・ログを変える前です。
- **RS1 の発生条件:** 次の 4 つがそろうと RS1 になります。
  - 場のカードが「自分の番ごとに1回」の版である（NIP2X-009・PRN-015〜PRN-022・neo4-106。`LUCKY_STADIUM_TEXTS`）。
  - (本人, このカード) の記録がない。
  - (本人, 同じ名前の別のカード) の記録がある（`stadium_use_history`。名前の完全一致）。
  - 禁止がない。

  `use_stadium` の候補（`legal_actions._stadium_candidate`）は同じ `check_use_stadium` を探り、停止なら `unresolved_ruling` の候補として残します。
- **同じ `use_stadium` の除外を生む別の条件:**
  - ラッキースタジアムでは SX2（同じカードが場にもどった）・STB1（禁止）・LK1（PRN-027）。
  - ほかのスタジアムでは、EN1・NJ1・GG1 などの効果ごとの停止、FG1（セキチクシティジム）。

  今回の 14 局面は、どれも SX2・STB1・LK1 の条件を満たしません。記録がなく（SX2 ではない）、禁止がなく（STB1 ではない）、PRN-015 です（LK1 ではない）。
- **使用済みの記録:** `GameState.stadium_uses_this_turn`（`state.py:2550`）で、(使ったプレイヤー, スタジアムカードの uid) の並びです。
  - **書く時:** `_use_stadium`（`engine.py:2613`）で、確かめのあと、ログ `stadium_used` の直後、コインの前に書きます。「うら」でも使ったことになります。
  - **入れかえのとき:** 記録は消しません。古いカードの uid が残るので、新しいカードからは「同じ名前の別のカード」として見えます。
  - **番の終わり:** 次の番の始め（`procedures.begin_turn`）に空にします。サドンデスの組み立て直しでも消します（`sudden_death.py`）。
  - **保存と復元:** 状態スナップショット（`snapshot.py`）は `GameState` の全項目を値として保存・復元します。書き出し（`serialize.py`）は形式 17 から記録を書きます。
  - **観測:** 観測（`observation.py:575`）は記録を公開の情報として出します。
- **番号の重なり:** RS1 という記号は、v0.83 の [shining-gentle-pokemon-v0.83](shining-gentle-pokemon-v0.83.md) にもあります（`UNRESOLVED_REFLECT_SHIELD_TIMING`）。この文書の RS1 は、[remaining-stadiums-v0.74](remaining-stadiums-v0.74.md) 7 章の `UNRESOLVED_STADIUM_REUSE_AFTER_REPLACEMENT` だけを指します。

## 6. 史料・既存の記録・数え方の比較

### 6.1 版と文面

- 保存局面の版は、どれも PRN-015（プロモ（neo）。kyuura の日本語の文面は pcg-search.com の転記）です。採用している文面（`LUCKY_STADIUM_PRN_TEXT`）は次のとおりです。

  > おたがいのプレイヤーは、それぞれ、のぞむなら、自分の番ごとに1回、コインを投げてもよい。コインを投げて「おもて」なら、山札からカードを1枚引いて、手札に加える。

  この文面は、PRN-016〜PRN-022 と登録を共有しています。
- NIP2X-009・neo4-106 は「投げてよい」「自分の山札から」と書き方が違いますが、「自分の番ごとに1回」があります。PRN-027 には「自分の番ごとに1回」がなく、LK1 で扱います。
- どの版にも、最新の説明・エラッタ・裁定の記録は kyuura にありません（[remaining-stadiums-v0.74](remaining-stadiums-v0.74.md) 11 章）。

### 6.2 規定と既存の記録

kyuura の固定コミット `71d1728`（`research_links.json` の research_commit）で照らしました。

- **2000.02.14 版の規定**（kyuura `rule_differences` の stadium。[P43]）: スタジアムはトレーナーの種類のひとつで、両方の場の境界に出し、両方の場のカードとして扱います。1 番に出せる枚数の制限はありません（2003 年の「1 番に 1 枚」は持ち込まない。[stadiums-v0.57](stadiums-v0.57.md) 1 章）。
- **p.310「トレーナーカードを使う」**（GR-2000-P310-TRAINERS）: 手順・使いすて・1 回の番に何枚でも使えることが書かれています。スタジアムの効果の回数の数え方はありません。
- **kyuura の未解決の記録:**
  - UQ-FUCHSIA-GYM-ONCE-PER-TURN（セキチクシティジムの FG1）は、同じ形の問いを「公式の資料の記述だけでは決められない」としています。当時の Q&A・会報・雑誌の記事は探していないとも書いています。
  - RS1 そのものは kyuura の一覧にありません（`research_links.json` の `kyuura_disposition` は `not_in_kyuura`）。
- **エンジンの記録:** RS1・FG1・SX2・LK1 は、どれも確定した裁定として記録していません。

### 6.3 通常の連続使用と、入れかわり後の使用

- **通常の連続使用**（同じカードで同じ番に 2 回目）: 文面の「自分の番ごとに1回」がそのまま当たり、できません（`STADIUM_ALREADY_USED`）。どちらの数え方でも同じです。
- **入れかわり後の使用:** 新しいカードにも同じ文面があります。この文面の「1 回」が次のどちらを数えるのかを、史料は直接答えていません。
  - 「そのプレイヤーがラッキースタジアムの効果を使った回数」
  - 「そのカードが与える使用の回数」

### 6.4 2 つの数え方

| | 使用者とカード名で数える | 場に出たカードの個体で数える |
|---|---|---|
| 入れかわり後の使用（RS1 の局面） | できない（同じ名前を使った） | できる（新しい個体は未使用） |
| 同じ個体の 2 回目 | できない | できない |
| 同じ個体が同じ番に場にもどる（SX2。ポリゴン2 の［じくうへんかん］） | できない | 2 通りに分かれる: カードで数えるならできない、場に出るたびに数え直すならできる。この案では決めず、SX2 のまま止める |
| 版の違うラッキースタジアム（PRN-015 → NIP2X-009 など） | できない（名前が同じ） | できる（別の個体） |
| PRN-027（回数の書かれていない版）がからむ | LK1 のまま | LK1 のまま。PRN-027 を使ったあとの「自分の番ごとに1回」の版も、この案の範囲に入れない |
| 名前の違うスタジアム | 数えない（今のまま） | 数えない（今のまま） |
| 相手の番・次の番 | プレイヤーごと・番ごと（今のまま） | 同じ |

どちらも文面と矛盾しません。資料から決まらないので、どちらを採るかはプレイ用規約で決める判断として残します。

## 7. 案と推奨

| 案 | 保存局面で新たに実行できる手 | その使用で起きる効果 | 繰り返し入れかえたときの上限 | 既存のカード・規約集合への影響 |
|---|---|---|---|---|
| A 現状維持 | 0 | なし | なし | なし。14 局面は未裁定の候補として表示が続く |
| B 史料に基づく修正 | 今はできない（6 章。直接の史料がない） | — | — | 史料が見つかれば、その答えで RS1・FG1 をまとめて見直す |
| C1 明示選択の限定規約（個体で数える） | 14 局面のそれぞれで `use_stadium` が 1 つ（取り直し除外後の局面の数。TR3 8・TR6 4・補足 2） | 本人がコイン 1 枚。「おもて」なら 1 枚引く。番 63 の局面は山札 0 なので、引けない（負けではない）。記録に (本人, 新しいカード) を足す | プレイヤーの番ごとに、その番に場に出たラッキースタジアムの個体の数まで。14 局面とも手札にラッキースタジアムはなく、続けて増える手はない。LUCKY_DECK の PRN-015 は 4 枚（uid 56〜59） | 規約は「自分の番ごとに1回」のラッキースタジアムの 10 枚だけ。エネルギースタジアム・キョウの忍者ジムは RS1 のまま、FG1・SX2・LK1・STB1 も変えない。新しい規約集合が要り、TR7@1 などの既存の集合は固定のまま。judge の期待・観測の表示・方策の候補が変わる |
| C2 明示選択の限定規約（名前で数える） | 0 | なし | なし | 14 局面の候補が「ゲーム上できない」に変わり、表示されなくなる（表示と診断だけの変化） |
| **D 追加検証が先（推奨）** | 今は 0 | — | — | 下の 3 つを先に行い、そのあと C1・C2・A から選ぶ |

**推奨は D です。** 理由:

1. 史料が直接答えず（6 章）、2 つの数え方はどちらも文面と矛盾しません。kyuura の同じ形の記録（UQ-FUCHSIA-GYM-ONCE-PER-TURN）は、当時の Q&A・会報・雑誌の記事を探していません。見つかれば B になります。
2. RS1 のコードは、ラッキースタジアム・エネルギースタジアム・キョウの忍者ジムの 3 つの名前で共有しています。同じ形の FG1、同じ個体の SX2 とも数え方がつながっています。ラッキースタジアムだけを個体で数える規約にすると、同じ文型のスタジアムで扱いが分かれます。この範囲の決め方は、利用者の判断です。
3. 増える手は 14 局面とも 1 つで、効果はコイン 1 枚と最大 1 枚のドローです。止まる局はなく（どの局面もほかの手が受理された）、急ぐ理由がありません。方策がその手を選ぶか、完走率が変わるかは推定していません。

先に行うこと:

1. kyuura の側での、当時の日本語の資料（Q&A・大会の裁定・会報・雑誌の記事）の調査。kyuura の作業として別に行います。公式ガイドブックの新しいキャプチャ・OCR・読み直しは、利用者が依頼したときだけ行います。
2. 規約にするなら、範囲を決めること。ラッキースタジアムだけにするか、RS1 の 3 つの名前と FG1 まで含めるか、SX2 を含めるか。数え方は C1（個体）か C2（名前）か。
3. 8 章の最小盤面で、今の動き（基準）を確かめること。規約を実装する単位では、同じ盤面で差を確かめます。

## 8. 次の単位で使う最小盤面と合格条件

### 8.1 共通の確かめ方

- **候補:** `legal_actions` の候補一覧に `use_stadium` があるか、その `processability`・`reasons`・`stadium`（card・card_id・owner）を確かめます。
- **入力:** 入力の段がない（`input_disclosure` が `no_input`・`choices: []`）ことを確かめます。
- **`check`:** client API の `check` の結果（受理の見込み・停止のコード）を確かめます。
- **`submit`:** client API の `submit` の結果（`outcome`・`refusal.code`）を確かめます。
- **使用回数:** `stadium_uses_this_turn` の前後を確かめます。
- **コインと公開ログ:** `stadium_used`・`coin_flip`（source `stadium`・effect は card_id）・`draw` の並び、山札・手札の枚数を確かめます。
- **拒否時の状態:** 拒否のときは、状態の全体（スナップショットの比較）・乱数の状態・ログの長さが変わらないことを確かめます。
- 各盤面は、乱数のコインを固定（「おもて」「うら」）して両方を確かめます。
