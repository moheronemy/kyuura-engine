# v0.2a のアーキテクチャ（カード効果を実装するための土台）

v0.2a は、v0.1 のルールと対戦の結果を変えずに、内部の構造を整えた版です。ゲームの機能（トレーナー・コイン・進化・特殊状態・ポケモンパワーなど）は加えていません。[v0.1 のレビュー](review-v0.1.md) の D の 3 項目（M3・M4・M5）に対応しました。

> **その後の変更（v0.2b）**: この構造を使ってトレーナーカード 3 枚を実装し、効果の登録表にトレーナーの欄、状態に使用中のトレーナー、状態の辞書に形式 3 を加えました（[v0.2b のアーキテクチャ](architecture-v0.2b.md)）。この文書は v0.2a の時点の記録です。

## 1. 目的

将来、次のものを安全に加えられるようにします。

| 将来の機能 | 必要になるもの | v0.2a で用意したもの |
|---|---|---|
| トレーナー・効果のあるワザ | 「どのカードの効果を実装したか」を明示する仕組み。説明文から推測しない | 効果の登録表（3 章） |
| 対象を選ぶワザ・トレーナー、コインの結果による分岐、処理の順番の選択 | 処理の途中でプレイヤーの選択を待ち、選択のあとに続きから処理する仕組み | 保留中の決定（4 章） |
| 進化・退化 | いちばん上のカードが変わっても、同じ場のポケモンを指せる識別子 | 場のポケモンの番号（5 章） |
| コイン | 乱数の状態の複製・保存・復元 | 乱数の扱いの整理（6 章） |
| プレイヤーごとの非公開の情報・AI | 内部の完全な状態と、見せる状態を分けられる構造 | 方針の記録（8 章）。実装はしていない |

## 2. 変更の概要

| 項目 | v0.1 | v0.2a |
|---|---|---|
| ワザを使えるかの判断 | ワザの説明文がなく、ダメージが固定なら使える（`Attack.supported` をデータから計算） | 効果の登録表に（カード id, ワザの位置）で実装が登録されていれば使える。説明文がないことは根拠にしない |
| ワザの処理 | `_use_attack` の中で、相手のバトル場のポケモンにダメージを与える | 登録された実装（v0.2a では `DamageOnly`）の `resolve` が処理し、エンジンがその後のきぜつ・サイド・交代を続ける |
| サイドを取る・交代 | `pending_prizes`（辞書）と `pending_promotions`（リスト）を専用に持つ | 共通の保留中の決定（`GameState.decision`）。`TakePrize`・`PromoteActive` はその決定に答える形として残した |
| 場のポケモンの識別子 | カードの uid（`PokemonInPlay.card`） | カードの uid と、場のポケモンの番号（`PokemonInPlay.pokemon_id`）を分けた |
| 乱数 | `GameState.rng` と、状態の辞書の中の指紋 | 同じ。指紋（比べる用）と、状態の保存・復元（`rng.py`）を分けた |
| 状態の辞書 | 1 つの形 | 形式 1（既定。v0.1 と同じ）と形式 2（場のポケモンの番号・決定などを加えた） |

新しいファイル: `kyuura_engine/effects.py`（効果の登録表）、`kyuura_engine/decisions.py`（保留中の決定）、`kyuura_engine/rng.py`（乱数の状態）。

## 3. 効果の登録表（M5）

### 構造

```
EffectRegistry（対戦ごとに 1 つ。GameState.effects、CardPool.effects）
  AttackKey(card_id, attack_index) → AttackEntry(effect, name_ja)
                                        effect: AttackEffect の実装（v0.2a は DamageOnly だけ）
                                        name_ja: 登録したときに確かめたワザ名（照合用。識別子ではない）
```

- 識別子は、カード id とワザの位置です。ワザ名は識別子にしません。同じ名前のワザでも、カードが違えば別の登録です。
- `AttackEffect` は 3 つの処理を持ちます。
  - `check(attack)`: カードのデータがこの実装で処理できる形かを確かめます。`DamageOnly` は、説明文や「+」「×」のダメージがあれば問題として返します。効果のあるワザを、効果のないワザとして登録する誤りを防ぐためです。
  - `resolve(state, use)`: ワザの処理です（p.309 の手順 6）。
  - `resume(state, use, decision, choices)`: 自分で出した決定が選ばれたあとの続きです（4 章）。
- ワザを使えるのは、次の 3 つがすべてそろったときだけです（`EffectRegistry.attack_problem`）。
  1. 登録がある。
  2. 登録したワザ名がデータと同じ。
  3. 実装の `check` が問題を返さない。
- カードの分類（`CardDefinition.supported`・`Attack.supported`）は、プールを作るときにこの登録表で決めます。値はデータのまま持ちます（`classify_record(record, effects)`、`pool_from_extract(extract, effects)`）。
- 対戦で使う登録表は、デッキの検査に使ったプールの登録表と同じものです（`new_game` が `pool.effects` を `GameState.effects` に入れる）。エンジンはワザを使うたびに `state.effects` を引き、カードの分類の結果（`supported`）には頼りません。

### 登録の内容（`DEFAULT_EFFECTS`）

| 登録 | 実装 |
|---|---|
| 対戦用のたねポケモン 10 種の 13 のワザ | `DamageOnly` |
| ヒトカゲ（参照カード。デッキには入らない）の「ひっかく」 | `DamageOnly` |

v0.1 で使えたワザだけを、同じ処理で登録しました。どのカードも『オフィシャルブック2000』のカードのページで「ワザ」欄に説明文がないことを画像で確かめてあります。照合の記録は `card_verification.json` にあり、ヒトカゲは v0.2a で p.63 を照合して加えました。登録したカードに照合の記録があることは、テストで確かめています。

### 未対応のままのもの

- トレーナーカード・特殊エネルギー・ポケモンパワーには、登録の欄がまだありません。これらのカードは「効果の実装が登録されていない」として未対応のままで、デッキに入れられません。
- 最初のトレーナーを実装するときに、トレーナーの登録（カード id → 実装）を同じ形で加えます。登録表に欄だけ先に作ることはしていません。
- 基本エネルギーは効果を持たず、公式ルールの規定（p.310・p.318・p.320）だけで扱います（エンジンの中心部分）。

## 4. 保留中の決定（M4）

### 構造

```
GameState.decision: PendingDecision | None（一度に 1 つ）
  id           決定の通し番号（GameState.next_decision_id から。使い回さない）
  kind         決定の種類（"take_prize"・"promote_active"・効果ごとの種類）
  player       決定するプレイヤー
  options      選べるもの（サイドなら位置、ポケモンなら場のポケモンの番号）
  min_choices / max_choices   選ぶ数
  resume       選んだあとに続ける場所の名前（"take_prize"・"promote_active"・"attack"）
  context      続きに必要な情報（(名前, 値) の組。値は整数・文字列とそのタプル）
```

- 決定を出すと、段階（`phase`）は決定の種類で決まります。
  - `take_prize` は `Phase.TAKE_PRIZE`、`promote_active` は `Phase.PROMOTE_ACTIVE` です（v0.1 と同じ値）。
  - それ以外の種類は、新しく加えた `Phase.DECISION` です。
- 決定を待っている間は、その決定に答えるコマンドしか受け付けません。ほかのコマンドは `WRONG_PHASE` になります。
- 答え方:
  - `ResolveDecision(player, decision, choices)`: どの種類にも使えます。`decision` は決定の番号で、古い決定への答えは `WRONG_DECISION` になります。
  - `TakePrize(player, index)`: サイドを取る決定に、v0.1 と同じ形で答えます。
  - `PromoteActive(player, pokemon)`: バトル場に出す決定に、v0.1 と同じ形（カードの uid）で答えます。`ResolveDecision` では場のポケモンの番号で答えます。
- 答えの検査（`decisions.check_choices`）では、次の誤りを拒否します。
  - 選ぶ数が範囲外: `INVALID_CHOICE_COUNT`
  - 重複: `DUPLICATE_CHOICE`
  - 選べないもの: `INVALID_CHOICE`
  - 違うプレイヤー: `NOT_YOUR_DECISION`
  - 拒否したときは状態を変えません（`apply_command` は複製してから処理する）。
- 再開先は関数ではなく名前で持ちます。状態を pickle・JSON にしても、どこから続けるかが失われないようにするためです。
  - `"attack"` の決定は、`context` の `"use"`（プレイヤー・場のポケモンの番号・カード id・ワザの位置）から登録表の実装を引き、その `resume` を呼びます。
- 複数段階の決定（1 枚の効果が 2 回以上選ばせる）は、再開した処理が次の決定を出す形で表します。
  - 前の選択は、次の決定の `context` に入れて渡します。
  - テスト専用の効果 `tests/helpers.py` の `TwoStepTestEffect` で、2 段階の決定を確かめています（製品の登録表には入れていない）。
- 決定そのものはログに残しません（v0.1 のログの形を保つため）。選んだ結果は、再開した処理がログに残します（`take_prize`・`promote_active`）。

### 状態遷移

```
MAIN ──UseAttack──▶ 実装の resolve ──（決定を出した）──▶ DECISION ──ResolveDecision──▶ 実装の resume ─┐
                         │                                    ▲                                  │
                         │                                    └──（さらに決定を出した）──────────┤
                         └──（決定なし）──▶ ワザの後の処理 ◀──（決定なし）──────────────────────┘
                                           │
                     HP 以上のダメージのポケモンはきぜつ（相手のポケモン → 自分のポケモン）
                                           │
             サイドを取るプレイヤーの並び（番のプレイヤーが先）が残っていれば
                     TAKE_PRIZE（決定 take_prize）──TakePrize / ResolveDecision──▶ 次のサイド、または ↓
                                           │
                     勝ち負けの判定（p.311 の表）── 決まれば GAME_OVER / SUDDEN_DEATH
                                           │
             バトル場にポケモンがいないプレイヤー（番でないプレイヤーが先）が残っていれば
                     PROMOTE_ACTIVE（決定 promote_active）──PromoteActive / ResolveDecision──▶ 次、または ↓
                                           │
                     番の終わり → ポケモンチェック → 相手の番（MAIN）
```

v0.1 との違いは 1 つです。両方のプレイヤーが同時にサイドを取る場合の順番です。

- v0.1: 2 人のどちらから取ってもよかった。
- v0.2a: 番のプレイヤーから順に取る。原文では、同じタイミングのことがらの順番は番のプレイヤーが決めます（p.325）が、その選択は未実装です。
- 今の対応カードでは、サイドを取るのはワザを使ったプレイヤーだけなので、この場面は起こりません。

## 5. 場のポケモンの番号（M3）

| 識別子 | 何を指すか | いつ決まるか | 変わるとき |
|---|---|---|---|
| カードの uid（`CardInstance.uid`、`PokemonInPlay.card`） | 物理的なカード 1 枚 | `new_game` でデッキの順に 0 から | 変わらない（カードの重複・保存則の検査に使う） |
| 場のポケモンの番号（`PokemonInPlay.pokemon_id`） | 場のポケモンそのもの | 場に出たとき（`GameState.next_pokemon_id` から） | 変わらない。場を離れたら無効 |

### ライフサイクル

1. **場に出る**: 対戦準備でバトル場・ベンチに出す（バトル場 → ベンチの順）とき、または番の途中でベンチに出すときに、番号を付けます（`engine._enter_play`）。番号は 1 から順に増えるだけで、乱数は使いません。同じデッキ・seed・コマンド列なら同じ番号になります。
2. **場にいる間**: にげる・交代でも、ポケモン（`PokemonInPlay`）ごと移るので番号は変わりません。将来の進化・退化でも、いちばん上のカードが変わるだけで番号は変えません。
3. **場を離れる**: きぜつするとポケモンはなくなり、番号はどの場のポケモンも指さなくなります（`GameState.find_pokemon` が `None`）。決定の選べるものにも入りません。
4. **もう一度場に出る**: 同じカードでも、新しい番号を付けます。前の番号は使い回しません。

番号 0 は「付けていない」意味で、不変条件で拒否します。番号は場のポケモンの中で重ならず、`next_pokemon_id` より小さいことも、不変条件で確かめます。

### コマンドの移行の方針

- v0.1 からあるコマンドは、場のポケモンをカードの uid で指したまま残します（`AttachEnergy.target`・`Retreat.new_active`・`PromoteActive.pokemon`）。エンジンが uid から場のポケモンを探します。
- `ResolveDecision` の選べるもの（場のポケモン）は、場のポケモンの番号です。
- 進化を実装するときの予定:
  1. `PokemonInPlay` にカードの重なり（下のカードから順）を持たせ、uid で指すコマンドは「重なりのどのカードの uid でも、そのポケモンを指す」ようにする（v0.1 のコマンドはそのまま使える）。
  2. 場のポケモンの番号で指すコマンド（または項目）を加える。
  3. ログのイベントに `pokemon_id` を加える（ログの形式を上げる。v0.2a ではログを変えていない）。
  4. uid で場のポケモンを指す形を、非推奨にするかを決める。

## 6. 乱数

- 乱数は対戦ごとの `GameState.rng`（`random.Random(seed)`）1 本だけで、モジュールの `random` は使いません。v0.2a は、v0.1 と同じく対戦準備（山札を切る）のあとは乱数を使いません（テストで確かめている）。
- **指紋**（`rng.rng_fingerprint`）は、乱数の状態の SHA-256 です。`state_to_dict` の `rng_state_sha256` に入ります。状態を比べるためのもので、ここから乱数はもどせません。
- **複製**: `GameState.clone()`・`copy.deepcopy`・`pickle` は、乱数の状態をそのまま複製します（`rng.copy_rng`）。複製を進めても元は進みません。
- **保存・復元**: `rng.rng_state_to_json(rng)` は、乱数の状態を JSON にできる形にします（形式 `python-random-mt19937-v3`。メルセンヌ・ツイスタの内部状態 625 個の整数）。`rng.rng_from_json(data)` でもどすと、同じ乱数の続きを再現できます。
- 将来のコイン: コインは `state.rng` だけを使い、エンジンか登録した実装の中で投げ、結果をログに残します（コインの関数は、コインを実装するときに加える）。

### セーブ・ロードに必要な情報（設計の記録。未実装）

対戦を保存してもどすには、次の 2 つの方法があります。

1. **再生**（今でもできる）: 次のものを保存し、`new_game` から同じコマンドを送り直します。結果は Python 3.11〜3.13 で同じです（固定値のテスト）。
   - デッキ 2 つ・seed
   - コマンドの列（`command_to_dict`。ジャンケンの結果を含む）
   - エンジンの版・kyuura のコミット・効果の登録表の id
2. **状態の保存**（未実装）: 状態の辞書（形式 2）に、次のものを加えた形を定めます。
   - 乱数の状態の全体（`rng_state_to_json`）
   - ルールの組の id、カードデータの出典（kyuura のリポジトリ・コミット）、効果の登録表の id
   - ログの全体（今も入っている）

   もどすときは、カードの定義を同じ出典のプールから引き、登録表を id から選びます。テスト用の登録表のように id から引けない登録表を使った対戦は、この形では保存できません（pickle はできる）。

## 7. 不変条件

`new_game`・`apply_command` は、返す前に必ず `check_invariants` を通します。破れていれば状態を返さず、`StateIntegrityError` を投げます。v0.2a で加えたものは太字です。

- カードの保存則: すべてのカードが、持ち主のゾーンのどこか 1 か所にだけある。未知の uid はない。カードの表の番号は uid と一致する。`new_game` で作った対戦では、カードの組がデッキリストと同じ。
- 場の形: 場のポケモンはポケモンのカード、ついているのは基本エネルギー、ダメージは 10 の倍数で HP 未満、ベンチは 5 匹まで、サイドはルールの枚数まで。
- **場のポケモンの番号**: 1 以上、`next_pokemon_id` 未満、重ならない。
- **段階**: `Phase` の値である。
- 番の途中は、両方のバトル場にポケモンがいる。エネルギーをつけた回数はルールの範囲。
- **決定と段階**: 決定を待つ段階（TAKE_PRIZE・PROMOTE_ACTIVE・DECISION）なら決定があり、その種類が段階と合う。それ以外の段階では決定がない。
  - 決定の番号は `next_decision_id` 未満。
  - 選べるものは重ならない。選ぶ数の下限は選べる数まで（上限は超えてよい。「2 匹まで」で 1 匹しかいない場合）。
  - 再開先が存在する。
  - サイドを取る決定の選べる位置はサイドの枚数と合い、取る回数は残りのサイドを超えない。
  - バトル場に出す決定のプレイヤーは、バトル場が空でベンチがある。選べるものはベンチのポケモンの番号。
  - ワザの決定の続きの情報が、場のポケモンと登録表の登録を指している。
- 終わった段階: 結果（または止めた理由）があり、決定がない。

## 8. 非公開の情報（方針。未実装）

今の `GameState` と `state_to_dict` は、エンジンの内部の完全な状態です。山札の順番・両方の手札・サイドの中身を含みます。画面・Web・AI に渡すときは、次の 4 つを分けます。

| 見る人 | 見えるもの |
|---|---|
| エンジンの内部 | すべて |
| プレイヤー 0 | 自分の手札。相手の手札・山札・サイドは枚数だけ。自分の山札の順番は見えない。場・トラッシュ・公開された情報（切り直しで見せた手札、使ったトレーナーなど）は見える。取ったサイドは自分には見える |
| プレイヤー 1 | プレイヤー 0 と対称 |
| 観戦者 | 両方の手札・山札・サイドは枚数だけ。場・トラッシュ・公開された情報 |

- 一般向けの API（画面・Web）では、内部の完全な状態（`GameState`、`state_to_dict`）を、見る人を分けずに渡さないでください。見る人ごとの形（例: `view(state, viewer)`）を、非公開の情報を実装するときに加えます。
- ログも見る人ごとに伏せる必要があります。たとえば `draw` の `cards` は、引いた人以外には見せません。
- v0.2a の構造は、この分け方の妨げになりません。
  - 隠す情報はゾーン（手札・山札・サイド）で決まります。
  - 決定の選べるものは、隠す情報を含みません。サイドは位置、ポケモンは場の番号です。
- AI は 2 つを区別します。
  - 完全な状態を使う AI（テスト・調査用）: `GameState` をそのまま使えます。`copy.deepcopy`・`pickle` もできます。
  - 不完全な情報で判断する AI（対戦用）: 見る人ごとの形だけを受け取ります。

## 9. 互換性

- 対戦の結果: v0.1（6068785）で記録した 15 の場面を、今のエンジンで再生して、完全に同じ結果になることを確かめています（`tests/test_compat_v0_1.py`、参照データ `tests/fixtures/v0_1_reference.json`）。比べているもの:
  - 各コマンドの受け付け・拒否とエラーコード
  - 山札の並び・手札・サイド・場・トラッシュ
  - 番の進行・ダメージ・きぜつ・勝敗
  - イベントログの内容と順序
- 固定値のテスト（配りと、1 局の状態の SHA-256）は、値を変えずに通ります。
- 状態の辞書: 既定（形式 1）は v0.1 と同じです。形式 2 は項目を加えただけです。
- ログ: 製品の処理で出るイベントは v0.1 と同じです（決定そのものはログに残さない）。
- コマンド: v0.1 のコマンドはそのまま使えます。`ResolveDecision` を加えました。

### API の変更（互換でないもの）

| 変更 | 理由 | 影響 | 移行 |
|---|---|---|---|
| `GameState` を作るときに `effects` が必要 | 対戦ごとの効果の登録表を状態に持たせるため（`state.py` から `effects.py` を読み込まないようにして、循環を避けた） | `GameState(...)` を直接作るコード（テストの `build_test_state` だけ） | `new_game` を使う。直接作るなら `effects=load_card_pool().effects` を渡す |
| `pending_prizes`・`pending_promotions` は読み取り専用の値（決定から作る） | 決定を共通の仕組みにしたため | 代入していたコード（エンジンの中だけ） | 読み取りはそのまま使える。決定は `state.decision` を見る |
| `CardPool` に `effects` が加わった。`classify_record`・`pool_from_extract` が登録表を受け取る | カードの分類を登録表で決めるため | `CardPool(...)` を直接作るコード（なし） | `pool_from_extract(extract, effects)` を使う |
| 未対応の理由の文言 | 登録表で判断するようになった | 文言を比べていたコード | コード（`UNSUPPORTED_CARD`・`UNSUPPORTED_ATTACK`）は変わらない |
| `Phase` に `DECISION` が加わった | 効果の途中の決定のため | `Phase` の値を全部並べて扱うコード | 決定を待つ段階は `decisions.DECISION_PHASES` |
| 既存のテストの変更 | M5 で、登録のないカードは使えなくなった | `test_deck.py` の `test_same_name_counts_across_different_cards`（テスト用のカードを、テスト用の登録表に登録するようにした。確かめる性質は同じ） | — |

代わりの案として、登録表を状態に持たせず、モジュールの 1 つの登録表だけを使う形も考えました。採らなかった理由は、テストで登録を差し替えるのにグローバルな書き換えが要り、対戦ごとに使った登録表が状態から分からなくなるためです。

## 10. 設計上のトレードオフ

| 判断 | 理由 | 代償 |
|---|---|---|
| 決定は一度に 1 つ（スタックにしない） | 単純で、どの段階で何を待っているかが一意に決まる。v0.1 からある決定と、2 段階の決定はこれで表せる | 入れ子の流れ（トレーナーの効果の途中できぜつが起きて、サイドの決定のあとにトレーナーの続きにもどる、など）は、続きを `context` に明示して書く必要がある。必要になったら、続きを積む形を検討する |
| 再開先は名前（文字列） | pickle・JSON にしても失われない | 名前と関数の対応を `engine._RESUMERS` で管理する |
| v0.1 からある段階（TAKE_PRIZE・PROMOTE_ACTIVE）を残した | 状態の辞書・ログ・コマンドの互換性 | 決定を待つ段階が 3 つある（`DECISION_PHASES`） |
| 状態の辞書の既定は形式 1 | v0.1 の固定値・参照データとの互換性 | 新しい情報を使うクライアントは `format_version=2` を指定する |
| ログに場のポケモンの番号を加えない | ログの互換性。進化がない今は、カードの uid と場のポケモンが 1 対 1 | 進化を実装するときにログの形を上げる |
| 登録表を対戦ごとに状態に持たせる | テストでの差し替え、使った登録表が状態から分かる | pickle した状態に登録表のオブジェクトが入る |
| 登録にワザ名の照合を持たせる | データの並びが変わったときに、別のワザに実装を当てる誤りを防ぐ | ポニータのように kyuura と原典で名前が違うとき、登録は kyuura の値に合わせる |
| 毎回の不変条件の検査 | 壊れた状態を返さない | 1 手あたりの処理が重い（AI の大量の探索では、検査を外す選択肢が要る） |
