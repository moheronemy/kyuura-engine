## 2. 公開の判定の基準

| 区別 | 意味 |
|---|---|
| (a) uid が出る | その閲覧者の閲覧用記録の出来事に、カードの uid（ログはカードを uid で書く）が出る |
| (b) 識別できる | その閲覧者に配信・保存された閲覧用記録（観測と出来事）の、その時点まで（同時点をふくむ）のどこかで、同じ uid とカード ID が結びついている |
| (c) 本人・完全な記録だけで対応できる | 決めた本人の観測、完全な記録、他者の手札や山札、計画のデッキの並びでしか対応できない（公開の根拠に使わない） |

- 公開の根拠に使ったのは、閲覧者ごとの閲覧用記録（`observe/view-<閲覧者>.json`）だけです。
- その時点より後に結びつきが出た場合は、「後の公開」として別に数え、当時から識別できたとは扱いません。
- 相手と観戦者は別々に確かめました。比べるために、決めた本人も同じ方法で確かめました。

**uid だけでは識別できない根拠**（コードと文書）:

- uid はデッキリストの順で付きます（`observation.py` の冒頭の説明「uid の付け方はデッキリストの順で決まるので、uid から中身がわかる」）。
- 相手のデッキリストは公開されません。
  - [diagnostics-replay-api-design.md](diagnostics-replay-api-design.md) の表（デッキリスト: 持ち主だけ。「相手のデッキリストは公開されない」）。
  - [oracle-leak-fixes-v0.138.md](oracle-leak-fixes-v0.138.md)（「相手は行為者のデッキリストを知らない」）。
- 保存した閲覧用記録の見出しには、閲覧者の自分のデッキリスト（`own_decklist`。カード ID の順に並べたもの）だけがあります。相手のものはなく、観戦者は null でした。
- 観測の最上位の項目に、uid とカード ID の対応表はありません。公開の場所（トラッシュ・場・使用中のトレーナーなど）のカードには、uid とカード ID が並んで出ます。

## 4. 不具合候補: ポケモン交換おじさんでもどしたカードを、相手・観戦者が識別できない

**記録で確かめたこと**（4 件すべて。`out/audit_publication.json`・`out/audit_trader_supplement.json`）

| 閲覧者 | uid が出る | その時点までに識別できる | 後で識別できる（後の公開） |
|---|---|---|---|
| 決めた本人 | 4 / 4 | 4 / 4（自分の手札の観測。前の項目から） | — |
| 相手 | 4 / 4（出来事 `return_to_deck` の `card`） | **0 / 4** | 4 / 4（あとで場・トラッシュなどに出たとき） |
| 観戦者 | 4 / 4（同上） | **0 / 4** | 4 / 4（同上） |

- 相手・観戦者の閲覧用記録の出来事は `{"kind": "return_to_deck", "player": …, "card": <uid>, "turn": …}` だけでした。カード ID・名前はありません。
- その項目と、それより前の全項目に、同じ uid とカード ID が結びついた値はありませんでした。`card` 以外の鍵で uid とカード ID が同じ辞書に出るものもありません。
- 項目の `notice` にもカードの情報はありません。
- 4 件のうち 2 件では、同じカード ID の文字列が同じ項目に出ていました。これは公開の場所にある同名の別の 1 枚と見られ、もどした uid とは結びついていません（識別の根拠にならない）。
- これは「調べた範囲で見つからなかった」ではありません。相手・観戦者に配信・保存された閲覧用記録に、対応を示す情報がないことを確かめました。
- 閲覧用記録は、その時点の観測と出来事を保持しています（後の項目で同じ uid が公開の場所に出たことは記録されている）。保持の欠けではありません。

**期待と実際**

| | 期待（文面・裁定） | 実際 |
|---|---|---|
| 相手 | もどすカードを見せる（どのカードか分かる） | uid だけで、どのカードか分からない |
| 観戦者 | 実装の約束では、`return_to_deck` の `card` は「全員に見える情報」（`zones.return_hand_to_deck` の説明・PT6）。観戦者に見せない仕様上の根拠は見つからなかった | uid だけで、どのカードか分からない |

**どの層に原因がありそうか**（静的な読み取り。修正の確かめはしていない）

- ログの出来事: `zones.return_hand_to_deck` が `return_to_deck` に `card`（uid）だけを書きます。`reveal_deck_to_hand` の `reveal_from_deck` も同じ形です（探したカードの分類は未調査）。
  - 比べると、`quiz_reveal`・`quiz_kind_reveal`・`bench_as_basic` などは、出来事に `card_id`（と名前）を書きます。
- 配信: `observation.visible_event` は `PUBLIC_EVENTS` の出来事をそのまま渡し、カード ID を足しません。
- 観測: 手札・山札のカードはカード ID を出さないので、見せたカードの情報が観測に残る経路もありません。
- 設計の前提の食い違いの可能性: 実装は「uid が公開されれば公開」と扱っています（PT6・PT13・`faceup.SHOWN_EVENTS`）。一方で、uid とカードの対応は持ち主のデッキリストにしかなく、相手には公開されません。

**既存の結論への影響**

- 棚卸しの文書 10.4 節の表の「ポケモン交換おじさん: 出た（`return_to_deck`・`reveal_from_deck`）。合う」は、uid の出現だけで判断していました。もどしたカードについては、識別の観点で誤りです（公開不足の候補）。

- 情報の漏れ（過剰公開）は、この分類では見ていません。対照のパソコン通信の探したカードの非公開は、未調査のままです。
- 10.4 節の「決定の公開の範囲」（選べるもの・数を、決める主体以外に渡さない）の結論は、識別とは別の確かめなので影響しません。
