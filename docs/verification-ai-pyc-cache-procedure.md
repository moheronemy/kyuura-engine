## 3. 外側の手順への接続（`scripts/run_seq_pyc.py`）

s1・s2・t1・t2 で使った `run_seq.py` の写しに、次だけを足しました。

- 子のプロセス（`python -B -m tools.verification_ai.batch run --stop-after-games 1`）に `PYTHONPYCACHEPREFIX`＝準備したキャッシュを渡します。`-B` は保ち、キャッシュは読むだけです。
- 準備の記録と今の状態が合うときだけキャッシュを使います。照らすのは、記録の ok、Python の実体、worktree の場所とコミット、未コミット 0、キャッシュの場所と件数です。
  - 合わないときは `PYTHONPYCACHEPREFIX` を渡さず、従来どおりソースから読み込みます。そのことを `outer_start` に記録します。
- `outer_start` に、キャッシュの件数・容量・同じドライブか・準備の時間を、道具の累積時間・ゲームの証跡とは別に記録します。
  - 出力先の空きの確認は、キャッシュが既に占めたあとの値で行います（同じドライブ C:）。
- `--dry-run`: 確かめと最初の容量の確認だけで終わり、`batch run` を呼びません。

**変えないもの**: `run --stop-after-games 1`、毎局の前の容量の確認（必要量 max(128 MiB, 最大の局 × 1.5)）、計画・デッキ・実装識別の照合、完了局の必須ファイルと全ハッシュの照合、時間・証跡の上限、停止の承認とロックの扱い（`--acknowledge-stop`・`unlock` を自動で使わない）。計画・台帳・COMPLETE・識別の値はキャッシュのために変えません。

**キャッシュが使われないとき**: 合わない pyc・ない pyc は Python が使わず、ソースから読み込みます。照合は同じに行われ、遅くなるだけです。速さだけでキャッシュが効いたとは判断しません（記録の照らしと、使ったかどうかの記録で判断する）。

**確かめた結果**（`--dry-run`）: lt12 で t1・t2 を指定すると `use_cache` 真。worktree の違う lt11 を指定すると `use_cache` 偽（キャッシュを使わない）。どちらも `batch run` を呼ばず、バッチのディレクトリに書いていません。

## 4. 対戦なしの確認

- キャッシュありの内訳（中央値）は次のとおりです。
  - t1: `adapter.identity()`（エンジンの読み込みをふくむ）1.53 秒、`scan` 0.11 秒。
  - t2: `adapter.identity()` 1.49 秒、`scan` 0.23 秒。

### 4.2 照合の対象と結果が変わらないこと（`raw/compare_results.json`）

キャッシュなしの 1 回を基準に、キャッシュありの全測定で次が同じでした。

- 識別（道具・エンジン）・`plan.json` の sha256・完了の attempt の一覧・`scan` の問題（0）。
- 照合したファイルの数と量（t1 90 ファイル・66.9 MB、t2 120 ファイル・219.0 MB）。
- `verify_complete` と `check_entry` の回数。
- 区間で読み込んだモジュールの数（100）。

**集計の読み取りの部分**（`load_plan`・`scan`・台帳・`_aggregate`。書き込みなし）:

- 既存の `aggregate()` はロックを取り、`aggregate.json`・公開の要約を書くので、元のバッチには呼んでいません（改修もしていない）。
- 保存済みの `aggregate.json` との差は `evidence` の管理のファイルの数と量（1 ファイル・261 バイト）だけでした。
  - 保存済みの集計は `aggregate()` がロックを持った状態で数えたので、`LOCK` を管理のファイルにふくみます。
  - 読み取りだけの再現ではロックを取りません。キャッシュとは関係しません。
  - 比較のスクリプトは「派生の量だけが違う」と期待していたので、そこで不一致を出しました（期待の書き方の誤りとして記録。7 章）。

## 6. 次のバッチへの適用の手順

1. 実行の worktree とコミットを決め、`tools/`・`kyuura_engine/` が想定の識別と同じこと、無視をふくめ変更 0 であることを確かめる。
2. 証跡の外の新しい空のディレクトリに、`prepare_pyc_cache.py` でキャッシュを作る（実行の worktree・バッチと同じ Python）。記録の ok・件数・容量・識別を確かめる。
3. 出力先の空きが、キャッシュの容量（約 14 MB）を引いたあとで、各計画の上限と必要量に足りることを確かめる。
4. `batch plan` は今までどおり（キャッシュは計画に入らない）。
5. `run_seq_pyc.py … --pyc-cache <dir> --pyc-record <記録> --dry-run` で `use_cache` 真と容量を確かめてから、`--dry-run` を外して実行する。
6. 実行のあと、台帳の開始の照合の時間（`session_start` → `attempt_start`）と、`outer_start` のキャッシュの記録を報告する。準備の時間は累積時間に入れない。
7. キャッシュは実行の単位ごとに作り直す。ソース・Python が変われば使わない（外側の照らしで外れる。外れなくても Python が照らす）。
