## 3. 原因と修正（情報境界と安全性の根拠）

原因: 山札を見る前の止める判定が、実際の山札（`players[p].deck`）のカードを読んだ。山札とうらのサイド・持ち主に見えない置いておくカードの配分は持ち主にも見えないので、受理・拒否と理由の文が
持ち主の知らない情報で変わった（宣言の拒否は状態を変えないので、ワザを使わずに何度でも問い合わせられた）。

修正（共通処理。v0.147・v0.148 の `searchable_deck_cards`・`deck_lower_bound_where` の上に作った）:

- `effects.deck_rainbow_possible(state, player)`: 山札にあるかもしれないカード（`searchable_deck_cards`。山札・うらのサイド・持ち主に見えない置いておくカード。山札にうらのカードがなければ山札だけ）に
  レインボーエネルギーがあるか
- `effects.deck_count_may_fall_short(state, player, fits, count, *, added=0)`: 山札の対象の枚数 c が 0 < c < count になる配分がありうるか。c は「配分を読まない下限 + added」以上、
  「山札にあるかもしれない対象の枚数（山札の枚数まで）+ added」以下のどれにもなりうるとみなす
- `programs.rainbow_deck_attach_question(run, energy_type)`: 山札からつける 3 つの要素（`AttachFromDeck`・`AttachFromDeckToBench`・`AttachFromDeckUpToNamedCount`）の `candidates` の RB2。
  理由の文は決まった文（`DECK_PRECHECK_NOTE`）
- ゆうでん: 下限が「おもて」の数より少ないときだけ、レインボーエネルギーがあるかもしれなければ RB2、なければ足りないかもしれなければ FC1。下限が足りれば、山札のレインボーエネルギーは
  今までどおり選ぶと止める選択肢（`unresolved_choices`）として出す（山札を見たあとなので実際の山札を使う）
- はらだいこ: FC1 を `deck_count_may_fall_short`（2 枚）で
- てじな: 段階 1 の答えの FC1 を `_may_fall_short`（もどすカードの基本エネルギーカードは山札に入ることが持ち主に分かっているので `added`）で。先読みの答えの候補（`dry_choices`）も同じ確かめで除く
- 確かめを通ったのに実際の山札が足りない・レインボーエネルギーを選ばないと足りないことは起こらない（実際の枚数は下限以上で、あるかもしれない集合は実際の山札を含む）。起こったらエンジンの
  不具合として `RuntimeError`（不変条件を加えた。弱めていない）

情報境界: 判定に使うのは、持ち主の所有カードから見えるカードを除いた集合（持ち主が知っている）・公開の枚数（山札・サイド・置いておくカード・おもてのカード）・カードの定義だけ。どのカードが
山札とサイドなどのどちらにあるかは読まない。検索が始まったあと（決定を出したあと）は、本人の選択の候補・答えの確かめに実際の山札を使う（v0.148 と同じ境界）。

安全性の根拠:

- 双子（山札とサイド・山札と置いておくカード）は、持ち主の知っている集合・公開の枚数が同じなので、判定の結果・コード・理由の文が同じになる（`twin_command_problems` で、持ち主を含む 3 つの
  見る人で確かめた）
- 理由の文は決まった文。uid・山札の枚数・位置を書かない（てじなの「もどす N 枚」は持ち主の答えの枚数で、持ち主が知っている）
- コインの経路（しおまねき・ゆうでん）の判定はコインの結果によらず、宣言の前の先読みが両面を試して宣言で止める。コインを投げたあとに止めて投げ直す経路はない
- てじなの段階 1 の拒否は持ち主の知っている情報だけで決まるので、答え直しても新しい情報は得られない。1 枚をもどす答えは配分によらず受理する（`TrickStageOneTest`）
- 任意の辞退（ひなたぼっこの 0 枚）と必須の処理（もえあがるのちょうど 1 枚）は、どちらも v0.150 の決定の形のまま（判定は検索の前だけ）

## 6. 増えた制限・維持した経路・残る選択肢

増えた制限（保守的な停止）:

- RB2: 持ち主のレインボーエネルギーがうらのサイド・持ち主に見えない置いておくカードにあって山札にないときも、ひなたぼっこ・じゅうでん・もえあがる・しおまねき・エナジーサポート・あたためる・
  せいでんきは宣言の前に止める（v0.150 までは実際に山札にあるときだけ）。トラッシュ・手札・場・おもてのサイドなど持ち主に見えるレインボーエネルギーは数えない
- ゆうでん: 配分を読まない下限（見えない「雷」の基本エネルギーカード − 山札の外の見えない枚数）が 3 より少なく、山札に対象があるかもしれなければ止める（レインボーエネルギーがあるかもしれなければ
  RB2、なければ FC1）。うらのサイドが 6 枚なら、見えない「雷」の基本エネルギーカードが 9 枚以上ないと使えない
- はらだいこ: 下限が 2 より少なく、山札に基本エネルギーカードがあるかもしれなければ FC1。うらのサイド 6 枚なら見えない基本エネルギーカードが 8 枚以上
- てじな: 2 枚・3 枚をもどす答えは、下限 + もどす基本エネルギーカードの枚数がもどす枚数より少なく、山札に対象があるかもしれなければ FC1（決定は待ったまま。1 枚をもどす答えは常に受理）
- 対象がどこにもない（持ち主に分かる）なら、今までどおり受理し、選べるもののない決定（v0.150）

維持した経路: 実際の候補を選ぶふつうの使用、任意の辞退、山札が 0 枚（決定なし）、コインの両面、控えがいない・つけられない（公開の情報）、v0.150 の決定の有無の修正、v0.148 の先読みの修正、
v0.147 の使う前の確かめ、ゆうでんの山札のレインボーエネルギーを選ぶと止める選択肢、既存の FC1・RB2 の停止（実際に足りない・山札にある場合は今までどおり止める）。

残る選択肢（この版では選んでいない。研究上の停止の範囲を変えるので利用者の判断）:

- RB2 を、山札を見る前に止めず、山札のレインボーエネルギーを「選ぶと止める選択肢」として決定に出す形（ゆうでんと同じ）に広げる。「てよい」（ひなたぼっこ・じゅうでん・せいでんき）は
  選ばないことがどの裁定でも合法なので止めなくてよくなり、ちょうど 1 枚（もえあがる・エナジーサポート・あたためる）・しおまねきは、止めないカードの下限が 1 以上なら止めなくてよくなる
  （v0.148 の `deck_choice_may_only_stop` の形）。使える範囲は広がるが、v0.58 からの「山札にあれば止める」の範囲を狭める変更なので、この版ではしていない

てじなの処理段階: 段階 1 の判定は、持ち主の知っている集合と下限で決められ（もどすカードは持ち主が選ぶので分かる）、裁定の判断はいらなかった。段階 2 は v0.150 のまま（検索のあと）。

## 7. 残る不具合・未確認

- `new_game` からの合法な対戦の列で漏れを再現することはしていない（構築盤面と、構築盤面からの合法な操作だけ）
- 修正の後の自然対戦は、v0.113・v0.116・v0.44 などの既存の道具の対戦テスト（固定の seed）だけ。新しい保守的な停止の頻度は数えていない（全 108 組・4,356 局は実行していない）
- FC1・RB2 の停止コード全体の監査はしていない（範囲の外）。山札以外（トラッシュ・手札・相手の公開のカード）を読む FC1・RB2 は、本人・全員に見えるカードなので対象にしていない
- 残る選択肢（6 章）は利用者の判断が要る

## 8. 監査の区切りと引き継ぎ

山札をさがす効果の情報漏れの監査（v0.147〜v0.151。使う前の確かめ・先読み・決定の有無・研究上の停止）は、今回の対象群に既知の漏れが残っていない。台帳の `silent_information_leak` で
active のものはない（`PSP-DECK-SEARCH-STOP-ORACLES` は fixed）。未確認の事項は 7 章に書いた。この監査は一区切りにできる。

次の作業「診断 API と対戦記録・再現インターフェースの仕様作成」へ引き継ぐ要件（この版では設計・実装に着手していない）:

- 拒否の結果（例外の種類・コード・理由の文）を、見る人（本人・相手・観戦者）ごとに、受理・拒否と同じ情報境界で返す。理由の文は秘密の配分によらない決まった文にする前提（v0.135〜v0.151 の
  修正の前提）を、API の契約として書く
- 宣言の前の先読み（試した枝・止めた問い）と、山札を見る前の確かめ（あるかもしれない集合・下限）の診断は、本人の知る情報だけを返す。実際の配分を返す診断は、検証用の権限に分ける
- 対戦の記録は、コマンド・決定（種類・決めるプレイヤー・本人だけの候補）・コインの結果・乱数の状態を、見る人ごとの写しと完全な写しに分けて持つ。決定が増える修正（v0.150）・受理が変わる修正
  （v0.151）で、同じ seed の記録が変わることを版で区別する
- 再現は、同じ版・同じ規約集合（ID・版・照合値）・同じ seed・同じコマンドの列で同じ状態になること。双子（配分だけが違う状態）を作る道具（`swap_hidden`・`swap_set_aside`）と
  `twin_command_problems` を、診断の検査として API から呼べる形にする候補
- 方策が秘密の配分を読まないこと（道具の方策も含む。4 章のてじなの例）を、記録の再現で確かめられるようにする
