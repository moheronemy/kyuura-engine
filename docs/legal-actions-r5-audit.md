## 1. 結論

- R-5 の正式な条件は「`input_disclosure` が `unconfirmed` の候補のうち、自分のうらのカードの特殊能力（R-3）でないもの」。分類は本人の応答にだけ現れる（`scope: actor`）（2 章）
- R-5 を作る経路は 8 つある（3 章）。今の登録で実際に生成されうるのは 5 つで、残りの 3 つは今の登録では生成されない保守の守り（決定の種類・特殊能力の型・スタジアムの選ばせるもの）
- **回答者が答えられず対戦が止まる R-5（決定の候補）のうち、確かめられたのは C 群（この版が続けられない状態）だけ**。これは、この監査で確かめた登録・経路の範囲での結論。
  決定の種類による入力の非公開は v0.162 の監査で 0 種類になっている（`OPTION_MEANINGS` と `DISCLOSURE_CONFIRMED_KINDS` が同じ集合。既存のテストが主張）。実行時の確かめ
  （見えないカードが選べるものにある。P2）は、起これば A 群で、決定待ちを止める。通常の到達は未確認で、届く経路がないとは断定しない
- B 群（本人の知識・公開の情報だけで安全に返せるが、API の対応が足りない）は **自分のうらのバトル場のポケモンのにげる** の 1 経路。進行は止めない（ほかの操作・番を終えるは示される）。
  補完しても進行不能の解消にはならず、API から選べる操作を補うだけ
- 棚卸しの R-5 の「次の最小の作業」（`DISCLOSURE_CONFIRMED_KINDS` にない決定の種類の索引）は、対象が空の作業だった。優先度「高（進行が止まる）」も、今の登録では B 群の進行の停止がないので
  過大だった（[残件の一覧](verification-ai-inventory.md) を訂正した。7 章）
- 最初の補完の提案は、うらのバトル場のにげるの入力（5 章）。v0.174 で採用・実装した（入力の形は 5 章の案のうち、`units`・`total_units` を省いて `cost_evaluation` で示す形）

## 2. R-5 の正式な条件と進行への影響

### 2.1 条件（コード）

| 項目 | 内容 | 根拠 |
|---|---|---|
| 分類の定義 | `RESIDUAL_CLASSES` の `R-5`: `kind` None（どの種類も）・`field` `inputs`・`situation` `any`・`status` `input_withheld`・`reason` `input_boundary_unconfirmed` | `legal_actions.py` の `RESIDUAL_CLASSES` |
| 当てはまる候補 | `c.disclosure == DISCLOSURE_UNCONFIRMED` で、`kind == use_power` かつ `power.face_down` でないもの（そちらは R-3） | `_residual_present` |
| 出る応答 | 本人の候補の応答の `coverage.residual.present`（`scope: actor`・`candidate` に候補の番号）と `coverage.withheld_input_candidates`。ホストの入口は出さない | `_candidates` |
| 網羅との関係 | `input_withheld` は `completeness` を `partial` にしない（種類の網羅は変えない。`partial` にするのは `not_offered` だけ） | `_candidates` の `partial_by` |
| `inputs` | 取っ手が合えば `{"withheld": INPUT_BOUNDARY_UNCONFIRMED, "stages": []}`（選べるもの・数・並びを返さない） | `_inputs` |
| `check`・`submit` | 処理可能性が実行できない区分（`not_implemented` など）なら先に `CANDIDATE_NOT_EXECUTABLE`。実行できる区分なら `INPUT_BOUNDARY_UNCONFIRMED`。どちらも送らない | `_input_problem` の `blocked()` → `disclosure` の順 |
| `client_api` | `inputs` の応答をそのまま包む（`withheld` を変えない） | `client_api.py` の `_inputs` |

- **入力の非公開は、合法な選択肢がないことでも未裁定でもない**（`REFUSAL_MESSAGES[INPUT_BOUNDARY_UNCONFIRMED]` は「ゲーム上の禁止・未裁定ではない」）。ただし同じ R-5 の中に、処理可能性が
  `not_implemented`（この版が続けられない）の候補も入る（3 章の P3〜P5）。R-5 の分類だけでは、情報境界の未確認か、続けられない状態かを区別できない。区別は候補の `processability`・`reasons` で読む
- R-3 と R-5 は、うらのカードの特殊能力かどうかで重ならない（`_residual_present` の分岐）。R-2（`not_offered`）・R-4（`out_of_scope`）は候補ごとでなく公開の状態で決まる別の分類

### 2.2 単位

- **候補単位**: 分類は候補の `disclosure` で決まる。同じ応答の中で、ほかの候補は入力を返しうる
- **状態単位**: `D.state_usable`（規約集合・保留中の決定の再開先）が偽の状態では、決定・初期配置・番の操作のすべての候補が `not_implemented`・`unconfirmed` になる（P3〜P5）
- **主体単位**: 出るのは決める人（決定の回答者・番のプレイヤー・初期配置のプレイヤー）の応答だけ。相手・観戦者の応答には出ない

### 2.3 決定と通常の操作の違い・進行への影響

- **決定の候補**: 決定待ちでは、回答者の候補は答えの候補 1 つだけ（`_build` の `AWAITING_DECISION`）。それが R-5 なら回答者は U7 で答えられず、ほかの操作もない。進めるのは、ホストが
  エンジンへ直接送ることだけ（U7 の契約の外。[U7 の決定の入力の監査](legal-actions-decision-audit.md) 7 章）。検証用 AI の終わり方 `input_unavailable` に当たる
- **番の操作の候補**: 番を終える（`end_turn`）・ほかの操作の候補が並ぶので、その操作ができないだけで進行は止まらない（P6〜P8）。ただし状態が続けられない（P4）なら、番を終えるも
  `not_implemented` で、どの操作も実行できない
- **初期配置**: 候補は 1 つ。続けられない状態（P5）では進めない
- 検証用 AI の実際の対戦（V0〜V3-2）で R-5 は示されていない（実行証跡の計測。[V1](verification-ai-v1.md) 7.4 節・[V0](verification-ai-v0.md)）

## 4. 情報境界の監査

### 4.1 共通

- 候補の作成は、完全な `GameState` を受け取る（検証者が完全な状態を読めることと同じ立場）。公開してよいかは、候補が読む値の出どころで決まる。`GameState.card_def` はうらのカードに
  `FACE_DOWN_DEFINITION` を返し、うらのあいだ決まらない項目（タイプ・にげる・ワザなど）を読めば `HiddenPropertyRead`（FD1）になる。これは読み取りを止める守りで、`printed_def`・
  `definitions[...]`・`cards[uid].card_id` の直接の読み取りは通る（守りの外）。守りがあることを、読まないことの証明にしない
- 本人だけが知る値（本人の手札・本人のうらのカードの本当のカード）は、本人の応答にだけ使える。R-5 の分類も本人の応答にだけ出る
- 入力を返さないときも、候補の存在・種類・処理可能性・理由・保証の文は返る。これらが本当のカードで変わらないかは経路ごとに確かめる（P6 は既存の双子のテストが応答全体の一致を主張）

### 4.2 P2（見えないカードが選べるものにある）

- 選べるものの内容（uid・カード ID）だけでなく、数（何枚あるか）・並び（山札の並び）・制約（選ぶ数）が、見えないカードの配分を表す。uid だけを伏せて残りを返すと漏れるので、
  入力全体を返さない今の扱いが正しい
- 到達: v0.162 の監査は、決定を出す 309 の組の選べるものの式をたどり、見えないカードを選べるものに置く出し方を見つけていない（コードを読んだ判断。動的な呼び出しは人が読んだ範囲）。
  今回は再走査していない。実行で起きたことはない（テストの注入だけ）

### 4.3 P3〜P5（続けられない状態）

- 入力を作らない。エンジンはどのコマンドも処理の前に拒否する（`_require_supported_decision`・`require_state_conventions`）ので、入力を返しても実行できない
- 情報境界の問題ではない。R-5 に数えられるのは `disclosure` が `unconfirmed` だからで、処理可能性 `not_implemented`・理由 `decision_not_supported`・`state_not_supported` で区別できる

### 4.4 P6（うらのバトル場のにげる）の値の出どころ

| 入力の要素 | 出どころ | 本当のカードによるか | 相手・観戦者の秘密を読むか |
|---|---|---|---|
| 入れ替える控え（選べるもの・数・並び） | 本人のベンチ（公開。うらの控えは `face_down` で示し、カード ID を出さない `_pokemon_option`） | よらない | 読まない |
| トラッシュするエネルギーカード（選べるもの・並び） | バトル場のポケモンについているカード（公開）。カード ID・特殊エネルギーかはエネルギーカードの定義（エネルギーカードはおもて） | よらない | 読まない |
| 選ぶ数の上限 | ついているカードの枚数（公開） | よらない | 読まない |
| にげるエネルギー（`total_units`）・カードごとの個数（`units`） | 本当のカードのにげるエネルギーと、持ち主のポケモンのタイプで変わる読み方（［おいしげる］など） | **よる**（FD1。今の `retreat_cost` は `HiddenPropertyRead`） | 本人の本当のカードだけ（相手の秘密ではない）。ただし候補の作成で読む必要はない |
| 処理可能性・理由 | うらであること（公開）だけ: `unverified`・`face_down_reveal_not_evaluated` | よらない | 読まない |
| 受理・拒否 | エンジンがおもてにしてから確かめる。拒否なら状態・ログをもどし、おもてにしたことも公開しない（送った本人への拒否だけ）。たねポケモンでなければトラッシュして受理（全員に公開） | よる（受理のあとに公開される事実で、相手に公開されるのはエンジンの既存の処理と同じ） | 読まない |

- 結論: 控え・エネルギーカード・数の上限・処理可能性・理由は、公開の値とうらであることだけで決まり、本当のカードによらない。にげるエネルギーとカードごとの個数を返さなければ、
  候補の作成で本当のカードを読まずに入力を作れる。本人の知識（本当のカード）を使って費用を示すことも本人の応答なら許されるが、使う理由がない（エンジンが確かめる）ので使わない
- 未確認: `energy_units` の読む先（`card_color_readings`・`_printed_units`・`_color_replacements`・`_wild_growth_card`）は、持ち主のポケモンのタイプを読みうる。うらのポケモンでは
  `HiddenPropertyRead` になるか、登録の動的な効果を通じて別の値を読むかを確かめていない。提案では `units`・`total_units` を返さない（5 章）。返す形を選ぶなら、この読む先の監査が先
- 未確認: うらのバトル場のポケモンについた状態の特殊状態（ねむり・マヒ）・にげられない効果は、今は候補の作成で確かめず（`check_retreat_declaration` を呼ばない）、エンジンがおもてにして
  から確かめる。これが候補の存在から本当のカードを予告しないことは、既存の双子のテスト（ディグダ・ユンゲラー）が候補の応答の一致として主張する範囲だけ
- 「同じにげるの種類のおもての経路でテスト済み」は、この経路の安全の根拠にしていない

## 5. 最初の補完の提案: うらのバトル場のポケモンのにげるの入力（P6。1 単位）

### 5.1 選んだ理由

| 基準 | P6 |
|---|---|
| 回答できないことで対戦が止まる影響 | 小さい。止めない（ほかの操作・番を終えるがある）。ただし、にげるには先に `RevealFaceDown` で公開するしかなく、うらのままにげる選択（ルール上できる）が U7 にない |
| 通常の対戦での到達 | マチスの秘策を入れたデッキで、うらのカードがバトル場にいる番（v0.67 の正式な開始からの対戦の手順にある）。公開の固定デッキでは届かない |
| 情報境界の説明 | 4.4 節のとおり、公開の値とうらであることだけで作れる |
| 既存の入力の形の再利用 | おもてのにげると同じ 2 段（`new_active`・`discard`）。`_retreat_candidate` の `verify` は既にうらなら確かめずに送る分岐を持つ |
| 裁定の変更 | 不要（エンジンの処理は変えない） |

B 群はこれだけなので、候補は 1 つ。決定の候補で進行が止まる経路（P3〜P5）は C 群で、補完の対象にならない（入力を返しても実行できない）。P2 は A 群（今の扱いが正しい）。

### 5.2 修正の範囲と API

- 変えるのは `legal_actions._retreat_candidate` の `HiddenPropertyRead` の分岐だけ（うらのバトル場）。エンジン・観測・コマンド・ほかの候補は変えない
- 候補: `processability` `unverified`・`reasons` `["face_down_reveal_not_evaluated"]`（今と同じ）、`input_disclosure` を `unconfirmed` → `confirmed`
- 段 1（`new_active`）: 今のおもての形と同じ（控えの選べるもの。各 `unverified`）
- 段 2（`discard`）: 選べるものはついているカード（`card`・`card_id`・`special`・`processability` `unverified`）。`count` は `{min: 0, max: 枚数}`。`units`・`total_units` は返さず、
  かわりに `total_units_unknown: "face_down"` のような明示の項目と注記を加える（**API への追加**。名前は実装の前に決める）
- 既存のクライアントへの影響: 今まで入力のなかった候補が、2 段の入力を返すようになる。`total_units` を必ずあると仮定するクライアントは、この候補で欠けることを扱う必要がある。
  `coverage.withheld_input_candidates`・`residual.present` から、この候補の R-5 が消える。版を上げ（エンジンの実行時のファイルを変えるので既存の運用どおり）、識別の `behavior_digest` が変わる

### 5.3 候補・入力・check・submit の期待

| 段 | 期待 |
|---|---|
| `candidates` | にげるの候補が `confirmed`・`unverified`。相手・観戦者の応答は変わらない（にげるの候補は番のプレイヤーだけ） |
| `inputs` | 2 段を返す。`withheld` はない |
| `check` | 形の確かめだけ（1 つめが段 1、残りが段 2、重なりなし、数の範囲）。`verify` は今の分岐どおり確かめない。形が合えば `valid`（受理の保証ではない） |
| `submit` | `Retreat(actor, トラッシュするカード（選んだ順）, 控え)` をそのまま送る。最終の判定は `apply_command`（おもてにして確かめる。たねポケモンでなければトラッシュして受理） |
| 拒否 | エンジンの拒否（エネルギーの不足・ねむりなど）は送った本人への `rejected`。状態・ログはもどる。拒否で取っ手は失効しない |
| 取っ手 | 受理ですべて失効（今と同じ）。形の誤りは `CANDIDATE_INPUT_INVALID` |
| 配信 | 受理のあとの公開（おもてにしたカード・にげた・トラッシュ）は既存の更新のとおり全員へ。拒否は全員への知らせにしない（`_submit` のまま） |
