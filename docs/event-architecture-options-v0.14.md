# イベント・効果の解決の設計案の比較（v0.14 Phase B）

[event-architecture-audit-v0.14.md](event-architecture-audit-v0.14.md)（現行の分析）を前提に、効果の解決の仕組みの 4 つの案を比べます。結論の採否は「確かめる前の候補」で、プロトタイプと検証の結果（[event-prototype-verification-v0.14.md](event-prototype-verification-v0.14.md)）で見直します。

## 2. 案

### 案A: 現行のアーキテクチャを維持（境界と専用の口を足していく）

- v0.9〜v0.13 と同じ。新しい効果ごとに、境界の関数（`deal_attack_damage`・`finish_damage_elements`・`_finish_attack` など）に探す処理と口を足し、ワザ 1 回の中の記録を `AttackUse` に足し、止める確認を `_use_attack` に足す。

### 案B: 型付きのイベントと共通の振り分け（ディスパッチャ）

- 出来事を型付きのイベント（`DamageApplied` など）にして発行し、効果を購読者として登録する。購読者が条件を見て処理する。順番は購読の順番か優先度で決まる。

### 案C: イベントにもとづく効果の解決のパイプライン（段階を明示する）

- 処理の段階（ダメージの適用の前・適用のとき・ダメージの要素のあと・効果の要素の前・きぜつの判定・きぜつの処理・勝ち負けのあと・番の終わり）を名前のある「窓」として明示する。各窓で、その窓ではたらく効果の候補を、状態（場のポケモンのいちばん上のカードの特殊能力・持続する効果）から集め、窓ごとの規則（原典で決まった順番、決まらなければ止める）で解決する。
- 窓の順番は原典の処理の順番（p.309・p.321・p.323〜p.325・p.89）で、仕組みが自由に決めない。

### 案D: 宣言的な効果のモデルとインタプリタ

- カードの効果をデータ（発動の契機・条件・対象・処理）で書き、共通のインタプリタが評価・実行する。

|---|---|---|---|---|

## 4. 実際のカードで見た必要性

- **「ダメージの処理のあと、効果の前」（p.89）**: 案A では、効果のあるワザの実装 10 種類がそれぞれ `finish_damage_elements` を呼ぶ。案C では、ワザの要素を「ダメージの要素」「効果の要素」に分類しておけば、仕組みが最初の効果の要素の前に窓を開く（呼び忘れが構造的に起こらない）。ピカチュウの「でんげき」（相手へのダメージ → コイン → 自分へのダメージ）は、コインが自分へのダメージの要素の一部なので、窓はワザの最後に開く。ビードルの「どくばり」（ダメージ → コイン → どく）は、コインがどくの要素の一部なので、窓はコインの前に開く（v0.13 の順番と同じ。乱数の割り当ても同じ）。
- **「はんげき」と「こうらがえし」の違い**: どちらも同じ窓ではたらくが、与えるダメージの分類（特殊能力・ワザ）が違う。案B のように「ダメージを受けた」イベントを発行し直すと、「はんげき」のダメージでも「はんげき」がはたらく誤りを、購読者の条件で毎回防ぐ必要がある。案C では、ダメージの分類（ワザ・特殊能力）を枠が持ち、「ワザのダメージを受けたとき」の効果は、ワザの分類の枠のダメージだけで候補になる（v0.10 の C13・C14 と同じ考え方を仕組みが持つ）。
- **「こんじょう」「ふしちょう」**: どちらも任意で、決定で止まる。案C では、きぜつの判定の窓・勝ち負けのあとの窓が、候補を集めて決定を出し、続きの情報（窓と残りの段階）を決定の `context` に書く。v0.13 の決定と同じ形にできれば、保存の形式（形式 9）を変えずに済む。
- **「だつりょくえき」（※）**: ダメージの処理のあとの窓で決定が要る。案A では `finish_damage_elements` を中断できる形にする設計変更が要る（`AttackUse` の記録が決定をまたげない）。案C では、窓の中の残りの候補を続きの情報として持てば表せる（v0.14 では実装しない。カードと裁定を確かめていない）。
- **「ファイナルビーム」「みちづれ」（※）**: きぜつの段階で新しいダメージ・きぜつが起こる。案C では、きぜつの原因の枠を記録しておけば、「別の枠のダメージによるきぜつが同時になる」場合（C18・W24 と同じ問い。p.324）を同じ検出で見つけられる。
- **「かがくへんかガス」**: どの案でも、今の状態から求める（v0.8 の `continuous.suppressors_of`）。案C では、特殊能力から来る候補をすべて同じ 1 か所で抑止の確認に通す（v0.13 は 5 か所で聞いている）。

## 5. 組み合わせと採用の候補

採用の候補は **案C を骨格にし、案B の「型付きのイベント」と案D の「ワザの要素の宣言」を限られた範囲で使う組み合わせ** です。

| 部分 | 採る | 採らない |
|---|---|---|
| 案C | 名前のある窓（段階）と、原典の順番の固定。窓ごとの候補の集め方・候補が 2 つ以上のときの規則（決まった順番がなければ止める）。処理の枠（フレーム）とダメージの分類による連鎖の制御 | 窓の順番を設定で変えられる形（順番は原典で決まる） |
| 案B | 型付きの内部のイベント（ダメージの提案・適用・きぜつなど）。公開のログとは別の、内部の解決の記録（トレース） | 汎用の購読・発行（グローバルなイベントバス）と、購読の順番・優先度で決まる処理の順番 |
| 案D | ワザを「要素」の並び（ダメージの要素・効果の要素・コイン・決定）として書き、仕組みが要素の分類から窓の位置を決める。効果の発動の契機・条件・処理を対応表（効果の定義）で書く | 任意のルールを書ける DSL。効果の中身（コインの扱い・量・特殊状態）はふつうの Python のまま |

採らない理由:

- 案A だけ: 動きは正しいが、4.4 節（[event-architecture-audit-v0.14.md](event-architecture-audit-v0.14.md)）のとおり、効果の種類を足すたびに共通の関数が変わってきた。これを減らせるかを確かめるのが v0.14 の目的なので、比べる基準として残す。
- 案B だけ: 順番が購読の順番という原典にない基準で決まる。v0.10・v0.11・v0.12 の設計（それぞれの architecture の 2 章）で不採用にした理由（C34・C35・T27・G40・P32 の順番を仕組みが決めてしまう）は変わっていない。
- 案D だけ: 今の 24 種類のワザの実装にも、語彙にしにくい規定（p.309 の「処理の対象がなくなってしまっている場合」・コインがどの要素に属するか・回復の条件）がある。v0.14 の非目標（完全な効果の DSL）でもある。
