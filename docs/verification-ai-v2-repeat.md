# 検証用 AI の V2 の補完: 反復を抑えるルールの方策 rules-v2

[V2](verification-ai-v2.md) の補完です。V2 の rules-s13 は、フシギバナのエナジートランスを同じ番の中で繰り返し、受理の上限（1,000）で止まりました（V2 の 7.2 節）。この補完は、
同じ番に同じ意味の操作が繰り返し受理されたら、その操作の優先順位を下げる**戦略上の選好**を、新しい方策の版 rules-v2 として加えます。合法性はエンジンに置き、候補を消さず、
処理可能性を書き換えません。V3（`boundary`・`negative`・双子・広い対象・最小化）・広いデッキと規約集合・きぜつの計測・探索の AI は扱いません。

1 章〜4 章は実装の前に書きました（仕様）。5 章以降は実装と実行のあとに書きます。

## 2. 同じ意味の操作

**操作の鍵**（`policies.action_key`）は、受理された（または送ろうとする）完成した入力の次の値の正準な JSON です。

- 主体（プレイヤーの番号）と操作の種類（`kind`）
- 候補の中身から、評価の値と応答ごとの番号を除いたもの。除く項目: `id`・`processability`・`reasons`・`guarantees`・`choices_format`・`input_stages`・`input_disclosure`。
  残る項目は、使うポケモン（場のポケモンの番号・カード・場所）・特殊能力・トレーナーのカードなどの対象
- 入力の意味（V0 の `meaning_of`。選んだ番号をその選べるものの中身に置きかえたもの）から、評価の値（`processability`・`reasons`・`eligible`）と番号（`id`・`after`）を除いたもの。
  段の順を保ち、段の中の並びは、その段の `order` が `significant`・`unconfirmed`（と `order` のない 2 個以上の段）なら選んだ順のまま、`not_significant`・`not_applicable` なら
  正準な順に並べかえる（並びに意味がないものを別の操作と数えない）

取っ手・候補の番号・選ぶものの番号・`operation_id` は鍵に入りません。完全な状態・相手の秘密は使いません（候補と段は本人の応答の値）。同じ種類でも、対象（場のポケモン・
エネルギーカード）や入力が違えば別の鍵です。エナジートランスの「A → B」と「B → A」は別の鍵で、それぞれが閾値に届けば抑えます（盤面全体の循環の検出はしない）。

## 3. 反復の抑制（rules-v2）

### 3.1 規則

| 項目 | 値 |
|---|---|
| 閾値 | 同じ番・同じ主体で、同じ鍵の操作が **2 回受理された**ら、その鍵の操作を以後その番では「抑えた操作」にする |
| 数える受理 | 受理（`accepted`）だけ。check の invalid・`refused`・`rejected`・入力を作れない・抑えて送らなかった試みは数えない。ランダムで選んで受理された操作も数える（混合の履歴） |
| 番 | 本人の観測の（区間の番号, 番の番号）。変われば履歴を空にする |
| 候補の順位 | rules-v1 と同じ（ベンチ 1 → 進化 2 → エネルギー 3 → ワザ 4 → ほか 5 → 番を終える 6）。下げた候補は順位 7（`end_turn` より後ろ） |
| 抑える場所 | 候補を選んで入力を作ったあと、送る前（完成した入力を評価する接点 `review`）。候補の種類や候補そのものを入力の前に一律に外さない |
| 抑えたとき | その入力を送らない（試みの記録の `build` は `suppressed_by_policy`）。同じエピソード（同じ状態）でもう一度、候補の選択からやり直す（入力の組み立ては uniform-stage のまま） |
| 候補を下げる | 同じエピソードで同じ候補（中身から評価の値と番号を除いたもの）の入力を **2 回**抑えたら、そのエピソードのあいだ、その候補を順位 7 にする（その候補の未抑制の入力が残っていても下げる。全部の入力を列挙しない） |
| 代わりがない | 選んだ候補がすでに順位 7（範囲の中に順位 1〜6 の下げていない候補がない）なら、抑えた操作でも送る（理由 `rule2:no_alternative`）。戦略の選好で対戦を止めない |
| 選び直しの上限 | 既存のまま（同じ状態の拒否 16・選び直し 64）。抑えた試みは選び直し（64）に数え、拒否（16）には数えない。候補を 2 回で下げるので、範囲の中の候補の数 × 2 を超えて抑えることはない |

- 抑えたのは戦略の選好で、「API が入力を返さない」「check で断られた」「合法でない」とは別の記録にする（`build: suppressed_by_policy`・カウンタ `policy_suppressed`・理由のコード）
- `end_turn` と、表にない種類（準備・決定の回答・ホストの係）は抑えない
- 乱数: 抑えて選び直すぶん、ルールの側の候補・入力の選択の乱数の消費は rules-v1 と変わる。rules-v1 と同じ操作の列になるとは言わない

### 3.2 混合

- `mixed` のルールの側の版を `rules_version`（1 か 2）で指定する。既定は 1（V2 と同じ）
- 混合の単位は V2 のまま（選択のエピソードごとに混合の乱数で 1 回だけ方式を決め、入力を作れない・拒否・抑えた選び直しで引き直さない）。ε は 0.25
- 抑制を当てるのはルールのエピソードだけ。ランダムのエピソードは抑えない（`review` はいつも送る）
- 履歴（同じ鍵の受理の回数）は、ランダムのエピソードで受理された操作も含めて更新する
- ゲームの乱数・混合の判定の乱数・候補と入力の選択の乱数の分け方は V2 のまま

### 3.3 記録と計測

- 方策の記録: 名前 `rules`・版 2・分布 `rules-v2-candidate+uniform-stage`・閾値・候補を下げる回数。混合は `rules_version`
- 試みの記録: `action_key`（鍵の sha256 の先頭 16 桁）、送る前の評価 `policy_review`（送るか・理由・その番の同じ鍵の受理の回数）、選んだ理由のコード（下げた候補を選んだときは
  `rule2:demoted:...`）
- 番ごとの反復（どの方策でも数える。ランナーの側）: 主体・番ごとの同じ鍵の受理の回数の最大と、2 回以上受理された鍵の数。保存した V2 の記録からも同じ関数で数え直す
- 計測の関係の追加: `check_valid + check_invalid = build_ok − already_tried − policy_suppressed`（rules-v2 でだけ `policy_suppressed` が 0 でない。ほかの方策では V1 の関係のまま）
- 方策の中の比べ（鍵の計算・履歴の照合）はエンジンへの操作として数えない（送信・受理のカウンタは変わらない）
