### 3.1 各件のエンジンの条件と、文面・裁定との対応

**R1（にげる）**
- エンジンは、うらのバトル場のポケモンのにげるで、先にカードをおもてにします（`engine._reveal_for_action`）。
- 本人の観測では、本当のカードはたねポケモンで、にげるエネルギーは 2、ついているエネルギーは 0 でした。トラッシュ 0 枚では費用に合わないので拒否されました。
- 候補の契約（`GUARANTEE_FACE_DOWN_RETREAT`）は「費用を評価しない。足りるかはエンジンがおもてにしてから確かめる」です。
  - この経路で作れる入力はトラッシュ 0 枚だけです（段 2 の数が 0〜0）。
- 同じ番の 2 回目のにげるでしたが、回数の制限はありません。p.311「「にげる」の宣言は、1回の自分の番の中で、何度でもすることができます」（[trainers-v0.2b.md](trainers-v0.2b.md)）のとおりです。

**R2（ワザ）**
- エンジンはカードをおもてにし（たねポケモン）、ワザの確かめでエネルギー不足と判定して拒否しました。
- 候補（`legal_actions._face_down_attack_candidate`）は、本当のカードの印刷のワザをすべて unverified で出し、確かめを呼びません（[legal-actions-u7-4.md](legal-actions-u7-4.md)）。
- judge には、この経路の拒否を分ける専用の規則（P6 の規則 4、U-R3a の規則 5 に当たるもの）がありません。一般の規則（停止系でない分類の拒否は normal_rejection）で判定されました。

**R3・R4（本人のうらのカードを指定した特殊能力）**
- エンジンは、特殊能力の source・target と、energy がついているポケモンのうち、うらのものを指定として扱い、おもてにしようとします（`designate_face_down(can_lose=False)`）。
- 本当のカードがたねポケモンでなければ、状態を変える前にこのコードで拒否します。理由の文に本当のカードは書きません。
- 本人の観測では、指定したうらのカードは 2 件とも、たねポケモンではありませんでした。
- このコードはエンジンの未対応として記録済みです（[secret-plan-preflight-v0.67.md](secret-plan-preflight-v0.67.md) 4 章・5 章、[legal-actions-r3-audit.md](legal-actions-r3-audit.md)、停止の分類は A・P2）。
- 候補の契約は「指定するうらのカードを含む組は確かめない（unverified）」です。
- 選んだエネルギーも、カードの条件のタイプではありませんでした。それでもこのコードになったのは、エンジンが指定を先に処理する順番だからです。

**R5〜R8（うらの使い手の特殊能力）**
- エンジンは使い手（うらのカード。本当はたねポケモン）をおもてにしたあと、特殊能力の確かめで拒否しました。選んだエネルギーカードが「炎」でなかったためです（カードの文面「「炎」エネルギーカードを1枚はがし、このカードにつけてよい」）。
- 状態はもどり、おもてにしたことも公開されません（候補の契約の acceptance）。
- 候補の段は、受け付けるかどうかでは絞りません（構造だけ）。

## 4. undetermined 2 件（R3・R4）

**判定の内容**
- どちらも送信の判定（judge の rows、source submit）です。受理の中身の判定でも、終わり方の判定でもありません。
- 理由は `stop_condition_not_evidenced:UNSUPPORTED_SECRET_PLAN_LOST_TARGET` です。
- judge が known_stop にしなかった理由:
  - コード表にあり、分類も同じです。経路の理由（`face_down_reveal_not_evaluated`）もあります。
  - しかし、代表の条件の根拠（`KNOWN_STOP_EVIDENCE` と記録の側の evidence）が登録されていません。
  - 規則 3 で、コード名だけでは known_stop にしないので、undetermined になりました。
- 停止方針の分類は `evidence_missing_stop` です（理由の先頭による）。計画の方針は continue です。
  - 2 局とも続けて game_over で終わり、完了マーカーの stop は空でした。計画と実際の継続は一致しています。

**過去に同じコードを調べた記録**
- r1 の 1 件は、決定への回答の経路（`engine._designate_answer`）でした（[verification-ai-reach-policy.md](verification-ai-reach-policy.md) 13.2 節・13.10 節）。
- 今回の 2 件は、コマンドの入口（`_reveal_for_action`）の経路です。
- エンジンの既存の試験は、相手の特殊能力の対象に相手のうらのカードを選ぶ場合（本当のカードによらず同じコード）だけです。本人のうらのカードを source にする経路の試験は見つかりませんでした。

**known_stop にするのに足りないもの**（別の変更案。この単位では実装していません。証跡 `judge_proposal_lost_target.md`）
- 経路ごとの代表の条件を登録する必要があります。経路は 3 つで、受け付ける条件も本当のカードの読み方も違うので、コード名で一括して当てません。
  - 本人のうらのカードを指定する
  - 相手のうらのカードを指定する
  - 決定への回答で指定する
- 条件の案（記録した API の値で確かめる）:
  - 本人の場の、うらで理由つきのカードを、source・target・energy の段で選んだ。
  - 生・診断・公開のコードがそろい、分類が unsupported。
  - 拒否のあとも同じ主体の turn_action が続き、取り直しが要らない。
- 判断が要る点: 本当のカードがたねでないことは、送信の値にはありません。本人の観測を判定に渡すかを決める必要があります。
- 負のテストの例:
  - うらのカードを選んでいない
  - 相手のうらのカード
  - 決定への回答の経路
  - コードや分類の食い違い
  - 拒否のあとの next や status が違う
  - 別のコードの拒否
- エンジン側の試験: 本人のたねでないうらのカードを指定したとき、このコードで状態が変わらないこと。たねなら続くこと。
- 規則の版への影響:
  - 判定の規則を 6 から 7 に上げると、道具の識別が変わり、既存の計画は再開しません。
  - 保存済みの判定は書き換えません。新しい規則を当て直すなら、別の単位で旧規則の結果と並べます。

## 5. 再送回避 5 件

- 5 件とも、runner の拒否済み入力の回避（`tried`）です。
  - 鍵は「候補の中身（応答ごとの id を除く）と入力の意味」です。
  - 方策の反復抑制（rules-v2 の review、`suppressed_by_policy`）とは別のものです。boundary の方策に review はありません。
- 対応:
  - R3 のあとに同じエピソードで 3 回、R6 のあとに 2 回、同じ入力を選んでいます。どちらも check も submit もしていません。
  - 確認スクリプトで同じ材料の鍵を比べ、先行する拒否と一致しました。
- 回避のあと:
  - R3 の局は、にげる（入力を作れない）のあと、たねを出して受理されました。
  - R6 の局は、たねを出して受理されました。
  - どちらも位置が進んでいます。
- `tried` はエピソードごとで、受理で位置が進むと空になります。
  - 状態の更新のあとまで回避を続けた例はありません。
  - 逆に、状態の更新と関係しない理由（エネルギーのタイプ）の拒否は、位置が変わると同じ入力がもう一度送られます（R7・R8）。今の設計の性質で、不具合とはしていません。
- 記録だけで対応を確定できないものはありませんでした。

## 6. 保存済みの記録の限界

- 拒否の前後の確認値は、保存されていません。
  - 実行時の確かめは「異常がない」という結果だけが残ります。
  - replay による確かめは、別の実行での再現です。
- 枠 A には観測の記録がありません。相手・観戦者の観測と、公開ログの中身による不変の確認はしていません。
- 本人の観測は位置ごとの行だけです。拒否の直後の view はありません。
- 「たねでない」ことは、本人の観測の real で確かめました（検証者の記録）。送信の API の値にはありません。
