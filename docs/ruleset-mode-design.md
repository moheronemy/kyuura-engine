## 2. 合意済みの定義（**[合意]**。2026-11-03）

| ID | 合意の文（利用者の指示のまま） | 台帳での読み方 |
|---|---|---|
| `AGR-MODE-SHARED-ENGINE` | 同じ処理基盤に、採用する規約集合を渡す。 | モードごとに別のエンジン・別の分岐を持たない。モードの違いは、渡す規約集合の中身の違いとして表す |
| `AGR-MODE-STRICT` | 厳密モードは、未決の裁定に当たったら停止する検証用モード。 | 未決の裁定（研究の停止コード UNRESOLVED_*・コードのない問いのうち止めている場面）に当たったら、今のエンジンと同じく止める（拒否・HALTED・途中停止の区別も今のまま） |
| `AGR-MODE-PLAY` | プレイ用モードは、未決の裁定を事前に定めた続行規約で処理し、実際の対戦を進めるモード。 | 続行規約は対戦の前に集合に入れておくもの（対戦の途中で決めない）。どの未決の裁定にどの規約を当てるかは未決（個々の続行規約は 1 つも採っていない） |
| `AGR-MODE-BASELINE-USER` | 既存の承認済み利用者指定は、両モードに共通する基礎集合に含める。 | 台帳の conventions のうち、利用者が明示的に指定した記録（baseline_category が user_specified）だけ。指定の対象・範囲は記録のまま（広げない・無効化しない）。エンジンの簡略化・実装上の仮定・データの訂正は、この合意に含まれない（DEC-BASELINE-NONUSER・DEC-CARD-DATA-CORRECTIONS） |
| `AGR-MODE-SAFETY` | 情報漏れ、状態破損、不正入力、実装不足、計算上限は、プレイ用だから無視してよいものではない。 | 両モードで同じ安全境界（safety_boundaries の SB-*）を保つ。プレイ用の規約で漏れ・破損・未実装・上限の超過を解消したことにしない |
| `AGR-MODE-PRIORITY` | 続行規約の整備は、対戦全体を終端にする項目から優先する。 | 準備の HALTED・ポケモンチェックの HALTED・途中停止（5 章の 14 コード）を、選択肢を 1 つ減らすだけの拒否より先に扱う。どの規約を採るかは決めていない |

- **根拠**: 本会話の利用者の指示（作業ブランチ `claude/ruleset-mode-design` の依頼）。**公式の裁定・最新の説明・エラッタ・kyuura の研究上の解決としては記録しません**（UQ- の論点は

- **過去の検討案**: 分類の時点（基点 `3e25ac5`）の STRICT-A（公式の根拠だけ）は、**厳密モードの定義としては採用しません**。STRICT-B（承認済みの利用者指定・簡略化・仮定を含む固定の
  ルールセット）は、上の定義に置きかえました（台帳の `mode_definitions.history`。[stop-policy-decisions.md](stop-policy-decisions.md) の DEC-STRICT-DEFINITION）。公式の根拠だけの
  集合を、研究・照合の用途で別に作るかは決めていません。
- **合意に含まれないこと**（[ruleset-mode-decisions.md](ruleset-mode-decisions.md)）: 規約集合の ID・版・内容の識別方法、プレイ用の規約を採る単位、対戦の途中の変更、旧保存状態の移行、

  実装上の仮定・データの訂正を基礎集合に入れるか。

### 2.1 合意の読み方（**[合意]** をそのまま当てはめたもの）

- 「未決の裁定」は、研究の停止コード（`UNRESOLVED_*`。固定研究基準の対応表の 316 件）と、コードのない問いのうちエンジンが止めている場面です。表外の `UNSUPPORTED_*`（実装不足）・
  内部ガード（`RuntimeError` など）・`IllegalActionError`（不正入力）・`StateIntegrityError`（状態破損）・探索の上限（`UNSUPPORTED_*_LIMIT`）は未決の裁定ではなく、AGR-MODE-SAFETY の
  対象です（台帳の `safety_boundaries` の SB-*。7 章）。
- 「厳密モードで停止する」は、今のエンジンの止め方そのものです（コマンドの拒否・答えの一部の拒否・準備とポケモンチェックの HALTED・途中停止。台帳の `axes.stop_mechanisms`）。厳密モードを
  導入しても、今の止め方を変える必要はありません。
- 「同じ処理基盤」は、モードの名前で分かれた別のエンジン・別の処理の経路を作らないことです。`engine.py`・`resolution/` にモード名・カード ID の分岐を加えません（CLAUDE.md の約束）。

## 3. 層の構成（**[案]**。合意の範囲は印のとおり）

規約集合は、次の層に分けて考えます。層ごとに、識別・変更の扱いが違います。

| 層 | 中身 | 今の記録 | 識別 | 変わるとき |
|---|---|---|---|---|
| 0 公式ルールと採用している資料 | 公式ルール 2000.02.14 版（`RuleSet`・`RULE_REFERENCES`）、kyuura の記録の採用（最新の説明 LD-・確定した裁定 CR-・規定 GR-・照合 CC-）、印刷の文面の採用 | `rules.py`・`research_links.json`・`card_sources.json` | ルールの組の id と研究の基準のコミット（`71d1728`） | 研究の基準を上げる作業（差分を調べる別の作業。CLAUDE.md） |
| 1 基礎集合（両モード共通） | **[合意]** 利用者指定（4 章の 12 件）。**[未決 DEC-BASELINE-NONUSER]** エンジンの簡略化 2 件・実装上の仮定 3 件 | 台帳の `conventions`・エンジンの登録の記録 | 4・5 章（案） | 利用者の新しい指定・指定の範囲の変更 |
| 2 続行規約（プレイ用だけ） | 未決の裁定ごとの続行の方法。**今は 1 つも採っていない** | なし（族の候補 `families.*.play_candidates` は案） | 5・6 章（案） | 利用者が規約を採る・版を上げる |
| 別の層: カードデータ | kyuura の写し（固定コミット）とエンジンが当てはめる訂正（`ENGINE_USER_CORRECTIONS`・kyuura のデータに入った訂正 `KYUURA_CORRECTIONS`） | `kyuura_cards.json`・`scripts/extract_kyuura_cards.py` | 写しの元のコミットと訂正の一覧（**[未決 DEC-CARD-DATA-CORRECTIONS]**） | 写しの作り直し |
| 別の層: エンジンの版 | 不具合の修正・同じ結果を保つ最適化・新しいカードの登録 | `kyuura_engine.__version__`・版の文書 | エンジンの版 | 版ごと |
| 両モードの安全境界 | 情報漏れ・状態破損・不正入力・実装不足・計算上限の保護（**[合意]** AGR-MODE-SAFETY） | 台帳の `safety_boundaries` | 規約ではない（集合に入れない。外せない） | 不具合の修正（エンジンの版） |

- 厳密モードの集合 = 0 層 + 1 層。プレイ用の集合 = 0 層 + 1 層 + 2 層。**[合意]** AGR-MODE-SHARED-ENGINE により、どちらも同じエンジンに渡します。
- 安全境界は規約集合の要素にしません（集合から外せると、プレイ用で漏れを許す構成が作れてしまう）。

## 5. 識別と版の管理（**[案]**）

### 5.1 3 つの版を分ける

| 版 | 意味 | 今 | 変わるとき |
|---|---|---|---|
| エンジンの版 | 処理の実装（`kyuura_engine.__version__`） | 0.138.0 | 不具合の修正・最適化・新しいカード・新しい規約の実装 |
| 保存形式の版 | 書き出しの形（`state_to_dict` の `format_version`） | 1〜34 | 表す項目が増える・意味が変わる |
| 規約集合の版 | 採る規約と各規約の意味・範囲 | なし（今のエンジンが暗に 1 つの集合） | 規約を加える・除く・規約の意味や範囲を変える |

原則（**[案]**。[ruleset-mode-decisions.md](ruleset-mode-decisions.md) の DEC-RULESET-VERSIONING）:

- 不具合の修正と、同じ結果を保つ最適化は、それだけでは規約集合の変更にしません（エンジンの版の変更として、版の文書に意図した差を書く）。
- 新しい続行規約、既存の規約の意味・適用範囲の変更は、規約集合の変更として追跡します（規約の版を上げ、集合の版を上げる）。
- 同じ規約集合でも、エンジンの版によって、不具合の修正の前後の差があり得ます（v0.137・v0.138 の情報漏れの修正は、規約を変えずに受理・拒否が変わった例）。比べるときは、エンジンの版と規約集合の
  版の両方をそろえるか、差を意図した差として列挙します。
- 過去の規約集合の意味を、あとから書き換えません。間違いが見つかったら、新しい版を作り、古い版は「この版は誤り」と記録して残します。
- 不具合の修正が規約の文面に書いた範囲を変えてしまう場合（例: 規約が「山札に目的のカードがないとき」と書いていて、修正で判定の情報が変わる）は、規約集合の変更として扱う必要があるかを、
  修正の版の文書で判断します。

### 5.2 識別の方法の比較

| 案 | 中身 | 利点 | 危険 |
|---|---|---|---|
| A. 集合の ID だけ | 例 `kyuura-strict` | 簡単 | 中身が変わっても同じ ID（今の `EffectRegistry.id` が `kyuura-engine-0.13` のままなのと同じ問題）。比べ・再生で別の集合を同じと読む |
| B. 集合の ID と版 | 例 `kyuura-strict@3` | 版で区別できる | 版の付け忘れ・同じ版で中身を変える誤りを見つけられない |
| C. B ＋ 含む規約の ID と各規約の版 | 例 `{set: kyuura-play@2, members: [USER-SWAP-OWNERSHIP-RECEIVER@1, PLAY-…@1]}` | 保存から中身が分かる。未知の規約を見つけられる | 規約の版の付け忘れは見つけられない |
| D. C ＋ 内容の照合値（ハッシュ） | 規約ごとの意味の記録（対象・条件・効果・範囲）を正規化した JSON の sha256 と、集合の照合値 | ID・版と中身の食い違いを機械的に見つけられる | 照合値の対象（何を正規化するか）を決める必要。コードの実装のハッシュではない（実装はエンジンの版で識別） |

**推奨（案）は D** です。照合値は「規約の意味の記録」に付け、エンジンのコードには付けません（同じ規約の実装の不具合の修正で照合値が変わらないようにする）。識別子の例はどれも案です。

規約 1 つの記録の形（**[案]**。今の `UserSpecifiedRule` などの記録を一般にした形）:

```text
{ "id": "PLAY-…（案）", "version": 1, "layer": "baseline | continuation",
  "targets": [{"code": "UNRESOLVED_…", "case": "…（台帳の事例）", "cards": ["…"], "key": "<カード id>/attack/0"}],
  "applies_when": "当てはまる条件（公開・本人が知っている情報だけで書く）", "excludes": ["隣の場面"],
  "effect": "続行の方法", "requires": ["ほかの規約 ID@版"], "conflicts": ["…"],
  "approved_by": "user", "approved_on": "YYYY-MM-DD", "source": "根拠の文書の節", "unresolved_issues": ["UQ-…"],
  "digest": "上の項目を正規化した sha256" }
```

### 5.3 受け取ったときの扱い（**[案]**）

| 場面 | 扱い |
|---|---|
| 未知の集合 ID・版、未知の規約 ID・版 | 対戦を始めない（構成の誤り。推測で近い版を当てはめない） |
| エンジンが実装していない規約（記録はあるが、この版のエンジンに処理がない） | 対戦を始めない。どの規約が足りないかを返す |

| 保存データの ID・版と中身（照合値）が一致しない | 読まない（ID を信じて中身を推測しない） |
| 規約集合の情報のない旧保存状態 | 8.4 節 |

### 5.4 再生・lockstep・監査で必要な情報（**[案]**）

エンジンの版・保存形式の版・規約集合の ID と版と照合値・含む規約の ID と版・カードデータの識別（写しの元のコミットと訂正の一覧）・効果の登録表の識別（名前だけの id ではなく中身で）・
最初の seed・送ったコマンドの列。規約を当てはめた場面ごとのログ（規約の ID と版・当てはめた停止コードと事例）。

## 6. 規約を採用する単位（**[案]**）

### 6.1 比較

| 単位 | 利点 | 危険 |
|---|---|---|
| 停止コード単位 | 数が決まっている（研究コード 316）。台帳・研究の対応表と 1 対 1 | **1 つのコードに性質の違う場面が混ざる**。例: ST1（`UNRESOLVED_SEARCH_TRAINER_WITHOUT_TARGET`）は、公開のトラッシュに対象がない場面（`#discard`）と、秘密の山札に対象がない場面（`#deck`。持ち主が知っている集合で決める。v0.137）を同じコードで止める。UPZ2 も増幅装置の山札（`#amplifier-deck`）と公開の領域（`#public-zones`）が混ざる（v0.138）。コードで一括にすると、片方に安全な規約をもう片方へ当ててしまう |
| 事例（場面）単位 | 情報の条件（公開・持ち主が知る・秘密）・時点・対象を分けられる。台帳の `cases` がある | 事例の分割は 7 コードしか確かめていない（分類の 14 章）。分けていないコードは、事例を作る作業が先 |
| カード単位 | 文面の違い（「てよい」の有無など）を取りこぼさない。kyuura・エンジンの記録もカードごとに別の問い | 数が多い。同じ処理の規約が重複する |
| 問題の族単位 | 方針を書きやすい（23 族） | 族の中のコード・カードを一括にすると、文面が違うものを同じに扱う（族は記録の書式の単位で、採用の単位ではない） |

### 6.2 推奨（案）: 事例を単位とし、明示した対象の一覧で共有する

- **適用条件と対象**: 規約は (停止コード, 事例) の組に当てます。対象のカード（とワザ・特殊能力の位置）を一覧で明示し、「同じコードのすべて」とは書きません。適用条件は、公開の情報か、
  当てはめるプレイヤーが知っている情報だけで書きます（SB-SECRET-INDEPENDENCE）。
- **対象外の隣接場面**: 規約ごとに `excludes` に書きます（例: ST1 の `#deck` の規約は `#discard` を含まない。逆も同じ）。同じコードで事例が 1 つしかないコードも、隣の場面を確かめてから
  規約を作ります（分けていないことを「同じでよい」とは読まない）。
- **同じ規約を共有する条件**: 印刷の文面の該当部分が同じ型、情報の条件（`secret_dependency`）が同じ、時点（使う前・解決の途中・ポケモンチェック）が同じ、のすべてを満たし、かつ対象の
  一覧に明示したときだけ。kyuura・エンジンの記録が別の問いとして扱うカードは共有しません。
- **同時に当たる場合**: 1 つの場面に当たる規約は 1 つだけにします。2 つ以上が当たりうる構成は、構成の検査で拒否します（暗黙の優先順位を作らない）。意図して重ねる場合は、後から採る規約が
  `overrides` で相手の ID と版を明示し、承認を受けます（**[未決 DEC-CONVENTION-CONFLICTS]**）。安全境界は、どの規約よりも先にはたらきます（規約で外せない）。
- **必要な共通実装**: 止める箇所（今 `UnsupportedError(code, …)` を投げる箇所）に、事例の識別を加えること（今は理由の文で区別しているだけの事例がある）。規約の照会は、効果の登録と同じく
  登録の側（`effects` の登録表や規約の登録の記録）に置き、`engine.py`・`resolution/` にはモード名・カード ID の分岐を加えない。規約を当てはめたことのログ。
- **承認と検証の単位**: 承認は規約 1 つ（ID と版）ごと。検証も規約ごとに、(1) 規約が当たる盤面の結果（状態・乱数・ログ・観測）、(2) 隣の場面が変わらないこと、(3) 秘密への非依存
  （両方の集合で `twin_command_problems`）、(4) 厳密の集合との差が規約の当たった場面から始まること（9 章）を確かめる。

同じ停止コードを、すべて同じ方法で処理するとは決めません。

### 6.3 例（**[案]**。採用していない）

- ST1 `#discard`（リサイクルなど。公開のトラッシュに対象がない）と ST1 `#deck`（エネルギー転送など。持ち主が知っている集合の下限で止める）は、別の規約の対象。
- UPZ2 `#amplifier-deck`（エネルギー増幅装置の山札。v0.138 の下限）と `#public-zones` は、別の規約の対象。

### 6.4 構成の検査（静的）

対戦を始める前に、集合の中で次を確かめます: 規約 ID の重複、同じ (コード, 事例, 対象) に当たる 2 つの規約、`requires` の不足、`conflicts` の同居、エンジンが実装していない規約、
照合値の食い違い。

## 7. モードと安全境界（**[案]**。AGR-MODE-SAFETY は **[合意]**）

モードの名前を見て例外を一括で無視する設計にはしません。各処理が必要とする規約（その場面の (コード, 事例)）と、集合の中身の対応で決めます。

| 場面 | 厳密モードの集合 | プレイ用の集合 |
|---|---|---|
| 未決の裁定に当たった | 今と同じく止める（拒否・HALTED・途中停止。コードは今のまま） | 規約があり、エンジンが実装していれば、その規約で続ける（ログに規約の ID と版）。規約がなければ 7.2 節 |
| 規約が設定されている | （厳密の集合は続行規約を持たない） | 規約の適用条件に当たる場面だけ続ける。隣の場面は止める |
| 規約が未整備（集合にない） | 止める | **止める**（未決の裁定のまま。黙って続けない）。止めた理由に「この集合にこの場面の規約がない」ことを区別して残す（7.2 節） |
| 規約はあるが、実装・保存の情報が足りない | — | 止める（`UNSUPPORTED_*` と同じ扱い。規約のあることを、実装があることと読まない） |
| 情報漏れ・不変条件の違反・不正入力・計算上限 | 両モードで同じ保護（SB-*）。規約で外さない | 同じ |

### 7.1 開始の前に見つける不足

- 構成の検査（6.4 節）に加えて、**準備の度合いの検査**: デッキのカードから、そのカードに結び付いた停止の場面（台帳の `related_cards`・事例の対象）を引き、集合に規約がない場面の一覧を返す。
- この検査は静的な結び付きだけで、カードの組み合わせ・相手のカード・旧状態の記録で初めて起こる場面は見つけきれません。一覧が空でも「止まらない」とは表示しません。

### 7.2 実行中に初めて分かる不足

- その場で止めます（未決の裁定の止め方のまま）。止めた記録に、規約の不足であること（集合の ID と版・場面の (コード, 事例)）を残します。プレイ用の集合で止まったことを、利用者に区別して
  見せます。
- 「プレイ用なので止まらない」と表示しながら規約の不足を黙って残す設計にはしません。完成したプレイ用の集合は、到達しうる未決の裁定に続行規約が用意されていることを目標にしますが、
  未整備の規約を推測で補いません。
- 規約がそろっていない構成で対戦を始められるか（**[未決 DEC-PLAY-CONFIG-INCOMPLETE-START]**）、デバッグ用の部分的な構成を設けるか（**[未決 DEC-PLAY-DEBUG-PARTIAL]**）は決めていません。

## 8. 対戦中・保存・区間（**[案]**）

| 項目 | 推奨（案） | 理由 |
|---|---|---|
| 対戦の開始時に規約集合を固定する | `new_game` の入力で集合を受け取り、状態に持つ。同じ対戦の中では変えない | 乱数・ログ・決定の意味が途中で変わると、再生・比べ・監査ができない |
| サドン・デスへ同じ集合を引き継ぐ | `SEGMENT_FIELD_POLICY` で keep（`rules`・`effects` と同じ） | 延長戦は同じ対戦の続き（p.324「延長戦として、もう一度初めから対戦をやり直します」）。区間ごとに集合が違うと、対戦全体の結果を 1 つの集合で説明できない |
| 途中の変更を原則禁止する | 変更の操作を作らない（**[未決 DEC-MODE-CHANGE-DURING-GAME]**） | 同上 |
| 規約の情報のない旧保存状態 | その状態を作った版の挙動（その版のエンジンが暗に採っていた集合）に対応付ける。作った版が分かる場合だけ（**[未決 DEC-LEGACY-STATES]**） | 今の保存（pickle）と書き出しは、エンジンの版も規約集合も持たない。推測で別の集合を当てはめると、再生の意味が変わる |
| 作成版・規約を特定できない旧状態 | 推測で読まない（規約集合を扱う読み込みでは拒否する） | 同上 |

- 今の pickle の復元は、今のコードのクラスで読みます。規約集合を導入する版より前の pickle を、その版のコードで読んだときの扱い（既定の値を入れるか・拒否するか）は、
  DEC-LEGACY-STATES で決めます。今の読み方は変えていません。
- 停止した対戦を別の規約集合で再開する機能は、通常のモード切替とは別の将来の機能として扱います（**[未決 DEC-RESUME-WITH-OTHER-RULESET]**。新しい対戦の記録として、もとの対戦の
  識別と再開の理由を残す形を案にする）。今回は実装しません。

## 9. 再生・lockstep・監査（**[案]**）

- 保存・書き出し: 規約集合の ID・版・照合値と、含む規約の ID・版を書く（新しい保存形式の版。今回は保存形式を変えない）。エンジンの版も書く。
- ログ: `game_created` に規約集合の識別を加える。規約を当てはめた場面ごとに、規約の ID と版・停止コードと事例のイベントを書く。延長戦の `sudden_death_started` は同じ集合の続き
  （区間の記録で集合が変わらないことを不変条件で確かめる）。
- 観測: 規約集合は公開の情報にする案（両方のプレイヤーが同じ規則で対戦していることを確かめられる）。規約を当てはめたイベントは、そのイベントのもとの場面の公開の範囲にしたがう
  （規約の当てはめが秘密を示さないこと）。
- lockstep・前の版の組: 同じ規約集合（照合値）どうしでだけ比べる。エンジンの版が違えば、不具合の修正の差を意図した差として列挙する（今のやり方のまま）。
- 厳密とプレイ用の比べ: 同じ seed・同じコマンドで 2 つの集合を走らせ、違いが出た最初の段を記録する。違いは、規約を当てはめたイベントのある段から始まる場合だけ許す。
- 秘密への非依存: `twin_command_problems` を、どちらの集合でも走らせる（続行規約が新しい漏れを作らないこと）。

## 10. 今の不具合との分離

**[事実]** v0.138 の修正範囲と残る性質（[oracle-leak-fixes-v0.138.md](oracle-leak-fixes-v0.138.md)）:

- 直したのは、遺跡の石版（neo2-054・neo2-057）のガスのもとの使う前の拒否の**理由の文**（受理・拒否・コードは修正の前も配分によらなかった）と、エネルギー増幅装置（neo4-102）の使う宣言と
  段階 2 の答えの UPZ2（`PSP-RUIN-WALL-BLOCKED-REASON-ORACLE`・`PSP-UPZ2-ENERGY-AMPLIFIER-ORACLE`。台帳の status は `fixed`）。
- 残る情報の伝わり方: 受理（公開）が相手・観戦者に、使ったプレイヤーの見えないカードの構成の 1 ビットを伝えること（v0.137 4.4 節・v0.138 5.4 節）。持ち主のデッキリストが観測にないこと
  （v0.137 4.3 節）。どちらも解消していません。
- 研究の停止コード（GG1・MG1・DW1・UPZ2・ST1・FC1）は未解決のまま（`active`）。増幅装置の特殊エネルギーをもどす使い方は、保守的な制限で止めます。

**[事実]** 新しく報告された次の 2 件は、**両モード共通の不具合**として別の作業に残します（台帳の status は `active`。修正していない）:

- `PSP-INCREASE-ENTRY-PW3-ORACLE`: アンノーンI（neo2-023）の［INCREASE］の使う機会で「使う」を答えると、山札に「アンノーン」がないときだけ PW3 で拒否される。
- `PSP-COCOON-DV2-ORACLE`: キョウのコクーン（PMCG6-011）の［うか］の DV2 が、キョウのスピアーが山札とサイドのどちらにあるかで変わる。

`PSP-DECK-CONTENT-PRECHECKS` の残り（GV1・`UNRESOLVED_EVOLUTION_HP` の経路）は、比較プローブをしていない未確認の候補で、安全とも到達不能とも断定しません。

これらをプレイ用の規約で解消したことにはしません（続行規約は未決の裁定の処理で、漏れを塞ぐものではない。AGR-MODE-SAFETY）。この設計の作業に修正を混ぜていません。新しい不具合が
あることを理由に、モードの定義（2 章）を未決にもどしません。

## 11. 推奨する実装の順序（**[案]**）

1. 両モード共通の不具合（10 章の 2 件と未確認の候補）の扱いを決め、修正する（モードの導入と別の版）。
2. 基礎集合の確定: DEC-BASELINE-CENSUS（実装上の仮定の数え上げ）→ DEC-BASELINE-NONUSER・DEC-CARD-DATA-CORRECTIONS。
3. 識別と版: DEC-RULESET-IDENTITY・DEC-RULESET-VERSIONING を決め、規約 1 つの記録の形と照合値を決める（文書と台帳だけで先に作れる）。
4. 状態・保存・ログの土台: 規約集合を `GameState` に持ち（keep）、保存形式・`game_created` に書く。この段では集合は厳密（今の挙動）の 1 つだけで、結果が変わらないことを lockstep で確かめる。
   DEC-LEGACY-STATES・DEC-MODE-CHANGE-DURING-GAME を先に決める。
5. 止める箇所への事例の識別と、構成の検査・準備の度合いの検査（6.4 節・7.1 節）。止め方は変えない。
6. 最初の続行規約: 対戦全体を終端にする項目から（**[合意]** AGR-MODE-PRIORITY）。切り直しの補償（DEC-MULLIGAN-COMPENSATION）・両側ねむり（DEC-SLEEP-COIN-ORDER）などの規約の内容は、
   利用者が決めてから。DEC-PLAY-CONFIG-INCOMPLETE-START・DEC-PLAY-DEBUG-PARTIAL もここまでに決める。
7. 厳密とプレイ用の比べの道具（9 章）と、規約ごとの検証。

## 12. 既存のデータとの役割分担

- **唯一の元**: 合意（`mode_agreements`）・基礎集合の区分と 18 件の記録（`conventions`）・判断事項の置き場所と状態（`decision_status`）は、作成スクリプト
  `scripts/build_stop_policy_classification.py` に書き、台帳 JSON に書き出します。この文書の 2 章・4.2 節の表は、同じスクリプトが `--write` で台帳から書きます（印の間を手で直さない）。
  `--check` は、表が台帳と同じこと、判断事項の見出しがそれぞれの置き場所の文書にちょうど 1 つあることを確かめます。
- **挙動の元**: 利用者指定の処理は、エンジンの登録の記録（4.2 節の `registry`）です。台帳はそれを写さず、対象の鍵と規則の ID だけを照らします。
- **研究の元**: kyuura の論点・裁定は研究の対応表（`research_links.json`）です。台帳・この文書は、論点を解決済みにしません。
- 同じ規約の一覧を、ほかのファイルに手で書き写しません。版の文書（v0.127〜v0.134）の指定の章は、指定を受けた時点の記録として残します。
