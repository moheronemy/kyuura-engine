## 2. F: 化石の発掘

### 2.1 処理と、今届いている情報（0.184.0）

| 段 | 処理 | 出来事・観測 | 相手・観戦者・ホスト（観戦者の写し）に届くもの |
|---|---|---|---|
| 使う | 手札から出す | `play_trainer`（公開） | 化石の発掘を使ったこと |
| 選ぶ | 決定 `search_deck_or_discard`（山札の「なにかの化石」→ トラッシュの「なにかの化石」。0〜1 枚） | 決定の観測 | 種類と決める人だけ（`HIDDEN_COUNT_KINDS`。選べるものの数・中身は見せない） |
| 山札から選んだ | `zones.reveal_deck_to_hand`（`identify` なし） | `reveal_from_deck`（`player`・`card`） | uid だけ。`card_id` はない |
| トラッシュから選んだ | `return_discard_to_hand` | `retrieve_trainer`（公開。`card`） | uid。トラッシュは公開の場所なので、動く前の観測の `discard` に uid と `card_id` の組がある |
| 選ばない・選べるものがない | `_trainer_take_none` | 理由は本人だけ | 何も加えなかったこと |
| 最後 | 山札を切る | `shuffle` | 切ったこと |

- 使った本人は、決定の選べるもの（`card_id` つき）で、選ぶ前から自分のカードを知っています。
- 足りないのは、山札の側の 1 つの出来事だけです。相手・観戦者は、見せられたカードを uid だけで受け取ります。

### 2.2 前回の分類 E（「名前が一意なので推論できる」）の根拠と限界

推論の中身: 公開の `play_trainer` が化石の発掘を示し、文面が名前の完全一致で「なにかの化石」にしぼり、写しでその名前の ID は 1 つです。なので、`reveal_from_deck` の uid は PMCG3-046 だと推論できます。

この推論を識別の根拠にしない理由:

1. **カードの集合しだい**: 「その名前の ID が 1 つ」は、今の写し（`71d1728`）の事実です。カードを足すと崩れます（再録・別の版の「なにかの化石」）。
2. **契約の外の知識**: 推論には、登録の中身（名前の完全一致・山札とトラッシュの分け方）と、`reveal_from_deck` がどのトレーナーのものかの対応が要ります。どちらも client_api の契約にありません。GUI は出来事の `card_id` だけで表示します（6 章）。
3. **前の監査の原則**: 「uid が見えるだけでは識別としない。既知のデッキ・完全な記録・後の公開からの推測も根拠にしない」（[静的な監査](reveal-call-sites-identification-audit.md) 3 章）。名前からの推論も、同じく出来事の外からの推測です。
4. **同じ文の効果との釣り合い**: 同じ「相手プレイヤーに見せてから、手札に加え」の 17 か所と交換おじさんは、0.184.0 で `card_id` を書きます。化石の発掘だけが推論に頼る理由は、文面にも裁定にもありません。

### 2.3 新しい裁定ではないことの確かめ

- 見せる対象（選んだ 1 枚）・見せる相手（相手プレイヤー）・時点（手札に加える前）は、v0.73 からすでに実装されています。`reveal_from_deck` は公開の出来事です。
- 変えるのは表し方だけです。公開した uid に、そのカード自身の `card_id` を添えます。見せる範囲・時点・相手は変わりません。
- 矛盾する根拠は見つかりませんでした。v0.73 の文書・登録の docstring・観測の規則は、どれも「山札のカードは見せて手札へ」です。なので保留にしません。

### 2.4 最小の修正仕様（F）

| 項目 | 仕様 |
|---|---|
| 変える箇所 | `effects.py` `SearchNamedFromDeckOrDiscard.resume` の `reveal_deck_to_hand(state, use.player, card)` を `reveal_deck_to_hand(state, use.player, card, identify=True)` にする（クラス名と呼び出しで探す。行番号に頼らない） |
| 変えない | `zones.py`（ヘルパーの既定は `False` のまま）・トラッシュの側（`retrieve_trainer`）・決定・候補・観測の `HIDDEN_COUNT_KINDS`・ポケモンタワーの分岐・切る処理 |
| 足りるか | 足ります。出来事 `reveal_from_deck` は公開で、`identify=True` は見せたカード自身の `card_id` を足すだけです（0.184.0 と同じ）。ほかの値は変わりません |
| 出来事の形 | 0.184.0 の 17 か所と同じ: `{"kind": "reveal_from_deck", "turn", "player", "card", "card_id"}`（`effect`・`power` はない） |
| トラッシュの側 | 変えない（推奨。採用判断 J-F2）。トラッシュは公開の場所で、受理の前の観測に、同じ uid と `card_id` の組がもうあります。`retrieve_trainer` はダウジングマシーンなど 4 か所の共通の出来事なので、化石の発掘のためだけに形を変えません |

### 2.5 受け入れ条件（F）

1. 山札から選んだとき、受理のあとの 4 つの入口（0・1・観戦者・ホスト）の `log` で、`reveal_from_deck` の `card_id` が、そのカードの本当の `card_id` です。
2. 選ぶ前（決定の時点）は、本人以外には uid と `card_id` の組が届きません（選べるものの数も見えない）。
3. トラッシュから選んだとき・選ばなかったとき・選べるものがなかったとき・ポケモンタワーの下では、出来事と観測が 0.184.0 と同じです。
4. 閲覧用記録の写しが `log` と同じです。前の出来事は、あとの受理で変わりません。
5. `identify=True` を渡す呼ぶ箇所は、交換おじさん 2・0.184.0 の 17・化石の発掘 1 の、ちょうど 20 になります。

## 3. S: スロットゲームの束全体

### 3.1 公開の要件（文面と処理順から確定したこと）

| 問い | 答え | 根拠 |
|---|---|---|
| 誰が見る・見せる | 使ったプレイヤーが見て、相手プレイヤーにも見せる（「見て、相手プレイヤーにも見せる」） | 文面 |
| 何枚 | 山札の上のちょうど 3 枚（`look=3`） | 文面・登録 |
| いつ | 1 回目に切ったあと、手札に加える前。決定はなく、使う受理の 1 つの中で終わる | 文面の順・`resolve` |
| 山札が 3 枚より少ない | 使えない（TOP1。手札から出す前に止める）。束の出来事は生成されない。空の束・短い束は今は起こらない | `_check_deck_top`・TOP1 |
| 束の順を相手・観戦者に示すか | 文面は順を求めていない（見せたあとで、残りを山札にもどして切る）。ただし `cards` は v0.80 から上からの順で公開している。新しい項目は `cards` と同じ順にするだけで、順に新しい意味を持たせない | 文面・`deck[:3]` |
| 選ぶカード・もどすカード | 選ぶ決定はない。「同じ名前のカード」（`same_name_groups`。`deck.same_name`）が 2 枚以上なら、そのすべてを手札へ。ほかは山札にもどして切る | 文面・実装 |
| 束の公開と、手札へ加えたカードの公開 | 別のもの。束（3 枚すべて）は「相手プレイヤーにも見せる」の公開。手札へ加えたカードは、その束の一部が手札へ動いたこと（`reveal_from_deck`）。0.184.0 で、加えたカードだけ `card_id` が付いた | 文面・0.184.0 |

### 3.2 0.184.0 で直った範囲と残り

- 直った: 手札へ加えたカード（`reveal_from_deck` の `card_id`。加えたカードは 0・2・3 枚）。
- 残り: 束の出来事 `reveal_deck_top` は `cards`（uid）だけです。山札へもどした 1〜3 枚は、相手・観戦者には識別できないままです。
- 保存済みの dump（0.184.0 の比較用。`out/saved_event_shapes.json`）で、4 つの入口とも、束の出来事の項目は `cards`・`count`・`kind`・`player`・`trainer_card`・`turn` で、`card_id` はありませんでした。加えた 3 枚の `reveal_from_deck` は、修正後の dump で `card_id` を持っていました。
  - この dump は修正のコミット（版の更新の前）で作ったので、版の文字列は 0.183.0 です。

### 3.3 `reveal_deck_top` の生成・可視性・ほかの読み手

| 項目 | 内容 |
|---|---|
| 生成 | `effects.py` `RevealDeckTopTakeSameNamed.resolve` の `state.add_event("reveal_deck_top", ...)` の 1 か所だけ（ヘルパーはない） |
| 可視性 | `observation.PUBLIC_EVENTS`（全員に全部の項目）。`PRIVATE_FIELDS` にはない |
| うらのカードの伏せ | `_mask_face_down` は uid の項目（`UID_FIELDS`・`…_card`・`…_cards`）だけを伏せる。`card_ids` はどれにも当たらない（0.184.0 の `card_id` と同じ扱い） |
| エンジンのほかの読み手 | `faceup.py`（`LOOK_EVENTS`。`cards`・`player` だけを読む） |
| テスト・道具の読み手 | `tests/log_audit.py`（種類の集合と、加えたカードの種類の確かめ）・`tests/test_exeggutor_bilingual_names_v0_131.py`（`cards` の中身）・`tools/existing_effect_games.py`（数え上げ）。どれも項目を足しても読み方は同じ |
| 期待を変えるテスト | `tests/test_reveal_identify_v0_184.py` `test_a_slot_game_taken_cards_only` の「束に `card_id` がない」（新しい期待に直し、旧の期待は docstring に残す） |

- 共通の出来事を「全部の呼び出しで公開」にする案はとりません。生成は 1 か所だけなので、その 1 か所で書きます。今後ほかの効果が `reveal_deck_top` を生成するときは、文面の「見せる」を確かめてから、その箇所で決めます（範囲のテストで生成の 1 か所を固定する。7 章）。
- ほかの効果への影響はありません。マスターボール・ポケモンギア・みずかき・新ポケモン図鑑HANDY808 の束は、本人だけの `look_at_deck_top` で、別の出来事です。

## 4. S: 束の識別情報の形式

### 4.1 案の比べ

| 案 | 形 | 評価 |
|---|---|---|
| **A（推奨）並行の配列** | 既存の `reveal_deck_top` に `card_ids: [str, …]`（`cards` と同じ長さ・同じ順） | 既存の前例と同じ形（`serialize` の `set_aside` の `cards`・`card_ids`、`cards_exchanged` の `card_ids`）。`cards` はそのまま。読み手は項目を 1 つ足して読むだけ |
| B オブジェクトの列 | `revealed: [{"card": uid, "card_id": str}, …]` | uid を二重に書くので、`cards` との一致の条件が要る。伏せる処理（`_mask_face_down`）は入れ子の uid を見ないので、うらのカードの伏せと食い違う |
| C 別の出来事 | 新しい種類（例: 束の識別）を束のすぐあとに置く | 可視性の表・`faceup`・監査・GUI の検証にそれぞれ種類を足す必要がある。1 つの公開が 2 つの出来事に分かれる |

### 4.2 推奨の仕様（A）

| 項目 | 仕様 |
|---|---|
| 項目名と型 | `card_ids`: 文字列の並び（JSON の配列。内部は tuple） |
| 既存の項目 | `kind`・`turn`・`player`・`count`・`cards`・`trainer_card` は変えない（名前・値・順） |
| 長さ・順の一致 | `len(card_ids) == len(cards) == count`（今は 3）。`card_ids[i]` は `cards[i]` の uid のカードの `card_id`。順は `cards`（山札の上からの順）と同じ |
| uid の一意性 | 生成の時点で `cards` の uid はたがいに違う。同じ `card_id`・同じ名前の別の個体は、位置ごとに同じ値が並ぶ（まとめない・並べかえない） |
| 部分的な値 | 書かない。書くなら 3 つすべて、書かないなら項目ごとない（`null` の要素を作らない） |
| 空・短い束 | 今は起こらない（TOP1）。TOP1 を将来解いて短い束を作るときは、`card_ids` を同じ長さで書く（`count` の意味はそのとき決める）。空の束では出来事を作らない |
| 生成の時点 | `resolve` の中で、1 回目に切ったあと・手札に加える前に、`cards` と同時に書く |
| 値の固定 | 書くのは生成の時点の値だけ。あとの状態から補わない。古い出来事（0.80.0〜0.184.0）に足さない |
| うらのカードの伏せ | `card_ids` は uid の項目ではないので伏せない。`cards[i]` が見る人によって `null` に伏せられても、位置はそのまま（0.184.0 の `reveal_from_deck` の `card`・`card_id` と同じ扱い。uid の方式全体の安全性は対象外） |
| 加えたカードとの整合 | 同じ受理で束のあとに続く `reveal_from_deck` のそれぞれについて、`card` は束の `cards` にあり、`card_id` は同じ位置の `card_ids` と同じ |
| 書かないもの | 名前・画像・山札全体の一覧・uid とカードの対応表・選ばれなかった理由・同じ名前の判定の結果 |

推奨の出来事の例（値はたとえ）:

```json
{"kind": "reveal_deck_top", "turn": 5, "player": 0, "count": 3, "cards": [41, 17, 52], "card_ids": ["X-001", "X-002", "X-001"], "trainer_card": 9}
```

### 4.3 選ぶ前・選んだあとに取れる範囲

- スロットゲームには決定がありません。受理の前は、だれにも束は届きません。受理のあとは、束（`card_ids` つき）・加えたカード（`card_id` つき）・2 回の切ることが、同じ受理の出来事としてそろいます。
- 山札へもどしたカードの今の位置は、だれにも届きません（切ったあとなので）。束の公開は「その時点で見せたカード」で、今の山札の中身ではありません。

### 4.4 受け入れ条件（S）

1. 受理のあとの 4 つの入口の `log` で、`reveal_deck_top` が `card_ids` を持ち、長さ・順・値が 4.2 節のとおりです（加えたカード・もどしたカードの両方）。
2. 同じ名前の 2 枚・3 枚・同じ `card_id` の 3 枚・同じ名前のない 3 枚の、どれでも 1 が成り立ちます。
3. 加えたカードの `reveal_from_deck` が、同じ位置の `card_ids` と同じ値です。
4. 山札が 3 枚より少ないときは、0.184.0 と同じく使う前に止まり、出来事は作られません。
5. ほかの項目・ほかの出来事・閲覧用記録の写し・カードの移動・山札の順・乱数・候補・受理の判定は、`card_ids` を除けば 0.184.0 と同じです。

## 5. 公開の範囲と非公開の対照

| 主体 | F（山札の側） | S（束） |
|---|---|---|
| 使った本人 | 前から自分のカードを知っている（決定の選べるもの）。出来事に `card_id` が足される | 束の uid は前から見えている。`card_ids` が足される |
| 相手 | `card_id` が新しく届く（見せる相手） | `card_ids` が新しく届く（見せる相手） |
| 観戦者 | 公開の出来事の規則で、相手と同じ | 同じ |
| ホスト | 観戦者の写しを読む（0.183.0 の `log`）ので、観戦者と同じ | 同じ |

非公開のまま変えないもの（対照）:

- 本人だけが見る束: マスターボール・ポケモンギア・みずかきの `look_at_deck_top`、新ポケモン図鑑HANDY808 の `look_at_deck_top`・`arrange_deck_top`。選ばなかったカード（見せない効果）。
- `reveal=False` の山をさがすトレーナーの `search_deck`、パソコン通信の `search_deck`（`card` は本人だけ）。
- 化石の発掘の決定の選べるもの・選べるものの数（`HIDDEN_COUNT_KINDS`）と、選ばなかった理由。
- てじなの段階 1 のもどすカード（`hand_to_deck`）。
- 選ばなかったカードも見せる効果は、この論点ではスロットゲームの束だけです（文面が束全体を見せる）。

旧形式・保存の扱い:

- 旧形式（0.184.0 までの化石の発掘の `reveal_from_deck`、0.80.0〜0.184.0 の `reveal_deck_top`）は、識別の情報がないまま読みます。uid・後の状態・既知のデッキ・名前から補いません。
- 0.183.0 の `log` は受理の時点の写しを貯めて書きかえないので、出来事の値は生成の時点で固定されます。`baseline_end` より前の出来事は hub を作った時点の投影です（今までどおり）。
- 閲覧用記録は、その時点の `visible_log` から写すので、`log` と同じ値になります。
- 公開の uid が見えるだけでは識別としません。既知のデッキ・完全な記録を、公開の根拠にしません。
- uid の方式全体の安全性は、今回は証明も変更もしていません。今回足す情報は、文面で見せたカードの `card_id` だけです。
