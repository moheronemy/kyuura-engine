## 2. 「開始の照合」の区間に入る処理（コードの読み取り）

`tools/verification_ai/batch.py` の `run_batch` は、ロックを取った直後の `t0` から台帳の `elapsed` を数えます。

| 処理 | 区間の中か |
|---|---|
| Python の起動・`site` | 外 |
| CLI のモジュール `tools.verification_ai.batch` の読み込み（`kyuura_engine` を先頭で import しない。標準ライブラリと道具のパッケージの 62 モジュール） | 外 |
| ロックの取得 | 外（`t0` の直前） |
| 台帳の読み取り・`session_start` の追記 | 中 |
| `load_plan`: `plan.json` の sha256、`adapter.identity()`（`records` の読み込みで **`kyuura_engine` を初めて import**、実装識別のハッシュ、道具の digest）、局ごとの `check_entry`（設定・`runner` の読み込み・デッキの記録と `deck_problems`・規約集合・方策の生成） | 中 |
| `scan`: 完了局ごとの `verify_complete`（表の全ファイルの sha256、観測の記録のある計画では `observe` の読み込み） | 中 |
| 台帳の読み取り・累積時間・`tree_bytes`・最初の局の attempt のディレクトリ作成と `attempt_start` の追記 | 中 |

- エンジンのモジュールの読み込み（とコンパイル）は、遅延 import のため区間の中に入ります。
- 外側の実時間（呼び出しの実時間）と区間の差には、Python の起動・CLI のモジュールの読み込み・局のあとの集計（`aggregate_after`）が入ります。

## 3. 測定の方法

- **対戦をしない再現**（`scripts/measure_startup.py`）: `run_batch` と同じ順に、既存の関数を呼びます。
  - 呼ぶ関数: `Ledger.read` → `load_plan` → `scan` → `Ledger.read` → `accounted_seconds` → `tree_bytes`。
  - ロックの取得・台帳への追記・attempt の作成・対戦はしません。
  - 内訳は、同じプロセスの中だけで既存の関数を計時の包みで包んで取りました。包んだ関数は `EngineAdapter` の各メソッド、`tool_digest`・`verify_complete`・`sha256_file`（量を数える）などです。
  - 包みは戻り値・例外・呼ぶ順を変えません。ファイルは編集していません。包みの負荷は `perf_counter` の呼び出しだけで、区間の値（11.7 秒）に対して無視できる大きさです。
- **キャッシュの条件**（OS のファイルキャッシュは空にしていない。「pyc なし／あり」は pyc の有無だけを指す）:
  - **pyc なし**: `-B`、`PYTHONPYCACHEPREFIX` なし。lt11 に `__pycache__` がないので、t-run と同じ条件です。
  - **pyc あり**: 調査用の外部キャッシュ（`PYTHONPYCACHEPREFIX`＝証跡の `pycache_prefix/`）を使います。準備の 1 回だけ `-B` なしで pyc を書き（155 個・13 MB）、測定は `-B` で読むだけです。
- **`-B` の作用**（`raw/minitest_*`）: 小さなモジュールで確かめました。`-B` は既存の pyc を読みます（`-v` の出力が「matches … code object from …pyc」）。pyc のないモジュールはソースからコンパイルし、pyc を書きません。
- **回数**: まず各条件 1 回。そのあと主要条件（pyc なし／ありの再現区間を t1・t2 で、import を前に出した分割を t1 で）を 2 回足して、合計 3 回にしました。値の差は小さく、結論を変えないので追加はしていません。
- 対象: t1（完了 6 局・66.9 MB をハッシュ）と t2（完了 8 局・219.0 MB）。量の参考として s1・s2 に `scan` だけを当てました（旧道具の計画は今の識別と違うので `load_plan` を通らない）。

## 4. 結果

### 4.1 主要な時間（秒。3 回の最小〜最大、1 回のものはその値）

| 条件 | t1 の区間 | t2 の区間 | 外側の実時間（t1） |
|---|---|---|---|
| Python の最小の起動（`-B -c pass`） | — | — | 0.023 |
| 再現の区間・pyc なし（t-run と同じ条件） | 11.67〜11.76 | 11.81〜11.84 | 11.89〜11.97 |
| 再現の区間・pyc あり | 1.69〜1.71 | 1.82〜1.84 | 1.88〜1.90 |
| import を区間の前に出したときの残り・pyc なし | 0.267〜0.270 | — | 11.87〜11.95 |
| import を区間の前に出したときの残り・pyc あり | 0.257〜0.264 | — | 1.89〜1.90 |

- 記録された t-run の開始の照合（11.60〜11.85 秒）は、pyc なしの再現の区間と合います。
- pyc ありの区間（1.69〜1.84 秒）は、s-run の記録（1.59〜1.96 秒）と同じ程度です。ただし、s-run の環境を再現したとは言えません（2 章）。

### 4.2 区間の内訳（pyc なし・t1。3 回の中央値）

| 処理 | 呼ばれた回数 | 時間 |
|---|---|---|
| `adapter.identity()`（最初の呼び出しで `kyuura_engine` の 51 モジュールと `tools` の一部を読み込む） | 2 | 11.41 |
| 　うち import を除いた実装識別のハッシュ（`implementation_identity`。分割の測定） | 1 | 0.04 |
| 　うち道具の digest（`tool_digest`。26 ファイル） | 2 | 0.03 |
| `check_entry`（局ごと。デッキの記録・`deck_problems`・規約集合・方策） | 6 | 0.17（import を前に出すと 0.10） |
| 　うち `deck_problems` | 12 | 0.06 |
| `scan`（`verify_complete` 6 局・90 ファイル・66.9 MB の sha256） | 1 | 0.11 |
| 台帳の読み取り・累積時間・`tree_bytes` | — | 0.004 |

- `-X importtime`（計測の負荷がある。1 回）では、区間の import の self 時間の合計 11.48 秒のうち、`kyuura_engine` が 11.30 秒でした。そのうち `effects.py`（ソース 4.4 MB）が 9.91 秒、`resolution/programs.py`（1.2 MB）が 0.71 秒、`engine.py` が 0.37 秒です。
- pyc ありでは、`kyuura_engine` の self 時間の合計は 1.42 秒（`effects` 1.21 秒）でした。pyc の読み込みとモジュールの初期化の時間が残っています。
- 同じ処理の繰り返し: `identity` と `tool_digest` は 1 セッションで 2 回ずつ呼ばれます（`load_plan` と、デッキの合法性の記録の最初の 1 回）。実装識別のハッシュは `lru_cache` で 1 回だけです。重複の時間は約 0.03 秒で、原因ではありません。

### 4.3 ハッシュの照合の時間と量（モジュールの読み込みを除いた `verify_complete` の値）

| 対象 | 完了局 | ファイル | 量 | `verify_complete` の時間 |
|---|---|---|---|---|
| s1（観測の記録なし） | 30 | 300 | 262.4 MB | 0.38 |
| t1 | 6 | 90 | 66.9 MB | 0.10（分割の測定） |
| t2 | 8 | 120 | 219.0 MB | 0.24（pyc なしの再現の中の値） |

- `scan` だけを単独で測ると、t1・t2・s2 では 1.5〜1.8 秒（pyc あり）、11.5〜11.7 秒（pyc なし）でした。観測の記録のある計画では `verify_complete` が `observe` を読み込み、そこからエンジンのモジュールも読み込むので、その読み込みの時間がふくまれます。
- ハッシュそのものは、数百 MB で 1 秒未満でした（OS のファイルキャッシュに載っている可能性があり、ディスクから読む時間の保証ではない）。

## 5. 結論

| 確定度 | 内容 |
|---|---|
| **測定で確認した原因** | 開始の照合の約 11.7 秒のうち約 10 秒は、区間の中の遅延 import で、エンジンのソース（特に `effects.py`）をコンパイルする時間です。pyc が使えないと、毎セッションこれが起こります。pyc を読める条件では区間は 1.7〜1.8 秒になりました |
| 原因の一部と考えられるもの | t-run が pyc なしになったのは、新しい worktree に `__pycache__` がなく、道具が `-B`（pyc を書かない）で動くからです。`-B` は既存の pyc の読み込みを禁止しません。「`-B` が原因」ではなく、「pyc がない worktree で `-B` を使い、毎回コンパイルして捨てた」ことの組み合わせが原因です |
| 原因でないもの（測定） | 実装識別のハッシュ（0.04 秒）、道具の digest（0.03 秒）、デッキの検証（0.10〜0.17 秒）、完了局のハッシュの照合（t1 0.10 秒・t2 0.24 秒）、台帳・`tree_bytes`（0.004 秒） |
| 未確認の仮説 | s-run が 1.6〜2.0 秒だったのは、up5td に当時のソースに合う pyc があったから、という説明（今の up5td の pyc は記録の時点の状態を示さない）。OS のファイルキャッシュの効果（空にしていない） |

- **pycache の仮説の評価**: 結果の文書 10.8 節の推測（「`__pycache__` がなく、`-B` で毎回ソースを読み込む」）は、t-run の区間については測定で確かめられました。正確には「`-B` で書けないため、毎回コンパイルする」です。s-run との差の説明としては未確認のままです。
