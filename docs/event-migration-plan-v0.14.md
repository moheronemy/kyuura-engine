# v0.15 以降の移行計画（v0.14 Phase F）

[event-prototype-verification-v0.14.md](event-prototype-verification-v0.14.md)（検証の結果）をもとに、汎用のイベント・効果の解決の仕組みを本番（`kyuura_engine/`）に入れるかを判断し、入れる範囲と順番を決めます。

- 「確認した事実」は v0.14 で実際に動かして得た結果、「評価」はその解釈、「予測」はまだ確かめていない見込みです。予測を測った数として扱いません。
- v0.14 では本番のコード（`kyuura_engine/`）を変えていません。この計画は v0.15 以降の作業の提案です。

## 1. 結論: PARTIAL

**ワザの解決（ダメージの要素・効果の要素・ダメージを受けたときの効果・きぜつの判定ときぜつの処理・番の終わりの期限）だけを、窓と枠の共通の仕組みに段階的に移し、それ以外（コマンドの受付、トレーナー、宣言して使う特殊能力、進化、にげる、状態の形、保存の形式）は既存の方式を維持します。**

MIGRATE（汎用の基盤を全体に入れる）にしない理由:

- 問題が集まっているのはワザの解決の経路だけです。v0.9〜v0.13 で共通の関数が変わったのは、どれもダメージ・きぜつの経路でした（[event-architecture-audit-v0.14.md](event-architecture-audit-v0.14.md) 4.4）。トレーナー・宣言して使う特殊能力・進化・にげるは、効果を加えても共通の関数が同じようには変わってこなかったので、移しても得るものが小さい（評価）。
- プロトタイプは、ワザ・番の終わり・きぜつのあとの決定だけを処理し、ほかのコマンドは v0.13 のエンジンに渡しています。それ以外を移せるかは確かめていません（確認した事実）。

DEFER（入れない）にしない理由:

- 同じ種類の効果を加える実際の変更（E4）で、旧方式は共通の関数 5 つを変え、新方式は 0 でした。関係のない効果の確認（2 つ以上はたらいたときに止める・決定の前に送る効果が残っていないこと）を、旧方式は手で広げる必要があり、広げ忘れても既存のテストでは見つかりませんでした（確認した事実。検証 6 章）。
- 原典で決められない場合の宣言の前の確認を、効果の組み合わせごとの 5 つの関数と補助の宣言（`damage_profile`・`opponent_effect_elements`）を使わずに、共通の先読みで同じ答えにできました（延べ 727,681 歩の比較で食い違いなし。確認した事実）。旧方式では補助の宣言を忘れると G37 を見落とすことも、実際の変更で確かめました（検証 6 章）。

## 4. 段階

### v0.15: 解決の核を本番に入れ、v0.13 と並べて確かめる

- `experiments/event_kernel/` を本番の内部の部品（例: `kyuura_engine/resolution/`）に移す。公開の API・状態・ログ・乱数・形式は変えない。
- プロトタイプが直接呼んでいる本番の非公開の関数 14（`_require_turn`・`_confusion_check`・`_knock_out`・`_finish`・`_halt` など）を、内部の部品として名前と説明を整え、両方の経路から呼ぶ（中身は変えない）。
- `apply_command` のうち、ワザ（`UseAttack`）・番の終わり（`EndTurn`）・再開先 `attack`・`knock_out`・`post_knockout`・`take_prize`・`promote_active` の決定を、新しい核で処理する。v0.13 の経路は消さずに残し、テストの基準（参照の実装）にする。
- 先読みは `derived`（共通の検出）を使い、v0.13 の止める関数（`legacy`）とテストで常に比べる。
- 新しいカードは加えない（移す作業と、ルールの意味を変えないことの確認だけ）。
- 確かめること（すべて満たすまで v0.15 を終えない）:
  - 既存のテスト（v0.13 の 1,685 件と v0.14 で加えた 46 件）が 3 つの Python で通る。
  - `tools/event_kernel_compare.py`（C 段階）で、新しい核と v0.13 の経路の食い違いが 0（対戦のテストの方針 23 × 100 seed・ストレス実行 26 組 × 10 seed 以上、2 つの先読み、交互の状態）。
  - `tools/compare_engine_versions.py --base 8facf3a` で、v0.13 と同じ。
  - 書き出しの形式が 9 のまま（参照データ・固定値を作り直さない）。
  - 時間: プロトタイプが受け持つコマンドの平均で v0.13 の経路の 1.5 倍以内、受け付けたワザ 1 回あたり 2 倍以内（v0.14 の測定は 1.30 倍・1.82 倍。どちらの上限も v0.14 の測定のあとに決めた値で、ワザの費用は余裕が小さい）。そのため v0.15 で、乱数を使わず決定も出さないワザ（v0.14 の測定で 58%）は先読みを省く（本処理は状態の複製の上で行うので、問いに当たれば複製を捨てれば済む）ことを試し、省いても v0.13 と食い違わないことを 1 歩ごとの比較で確かめる。

### v0.16: v0.13 の重複した経路を外す

- v0.15 の比較が続けて 0 なら、v0.13 の境界の関数（`deal_attack_damage` の効果を探すコード・`finish_damage_elements`・`_apply_counterattack`・`_apply_retaliation`）、`AttackUse` のワザ 1 回の中の記録 4 項目、24 のワザの実装の `resolve` を外す。ワザの実装のクラスは、データの形の確認（`check`）と数値だけを持つ。
- 止める関数 5 つと補助の宣言（`damage_profile`・`opponent_effect_elements`・`DamageProfile.outcomes`）は、テストの照合の基準として 1 版残し、共通の先読みとの比較を続ける（外すのは v0.17 以降）。
- ワザの経路の内部の関数を使っているテストのモジュール 14 と helpers.py を、公開の API か新しい核の入口で書き直す。確かめる内容（裁定の番号・誌面のページ）を減らさない。書き直す前後で、同じ盤面の結果を比べる。
- CLAUDE.md の規則を書きかえる（「汎用のイベントの仕組み（購読・発行）にしない」は、「購読・発行にしない。窓の順番は原典の順番で固定し、表（枠の表・問いの表・対応表）にない連鎖・問い・効果は止める」に置きかえる）。
- ログの監査（tests/log_audit.py）は公開のログを読むので、変えない。

### v0.17 以降: 新しい効果を核の上で加える

- 同じ窓に入るカード（ダメージを受けたとき・きぜつするとき・きぜつしたとき・受ける前の置きかえ・ワザの効果の持続）を、対応表の定義と処理で加える。カードごとの裁定の確認（誌面との照合・`card_verification.json`）は今までどおり。
- 新しい窓・新しい枠が要るカード（ベンチへのダメージ、ダメージの要素のあとの窓の中の決定（だつりょくえき など）、きぜつの処理の中のダメージ（みちづれ など））は、先に原典で順番を確かめ、確かめるまでは宣言の前に止める問い（新しい `UNRESOLVED_…`）を問いの表に加える。窓の中の候補の順番を、仕組みが決めないこと。
- トレーナー・宣言して使う特殊能力は、ワザの経路と同じ問題（共通の関数が効果ごとに変わる）が実際に起きたときに、改めて判断する。

## 5. 中止・延期の条件

次のどれかが起きたら、その段階を止め、原因を記録してから続けるかを決め直します。

1. 新しい核と v0.13 の経路の 1 歩ごとの比較で食い違いが出て、本番の不具合（裁定の番号と誌面で確かめたもの）が原因だと示せない。
2. 続きの情報を、v0.13 の決定の形（書き出しの形式 9）で表せなくなる（形式を変える必要が出る）。形式を変えるなら、別の計画にする。
3. 窓の中の候補の順番を、原典ではなく仕組みが決めないと先に進めない（C34/C35・G40・P32・T27 と同じ種類の問い）。問いの表に加えて止めることができないなら、その効果は移さない。
4. 共通の先読みの試す結果の数が、ワザ 1 回で 4,096 を超える、または 1 歩の時間が v0.13 の経路の 2 倍を超える。そのときは、そのワザだけ v0.13 の止める関数（`legacy`）を使う。
5. 既存のテストを弱めないと移せない（確かめる内容を減らす・期待値を作り直す必要がある）。
6. 1 つの版の作業が、移す作業と新しいカードの追加を同時に必要とする。分けられないなら延期する。
7. v0.17 で次の実際のカードを加えたときに、共通の処理の変更が旧方式より減らない（E4 の測定と同じ方法で測る）。その場合は、移した範囲を保ち、さらに広げない。

## 6. v0.14 で確かめていないこと（予測のまま）

- ベンチへのダメージ・複数のポケモンへのダメージを与えるワザで、窓と枠の形が足りるか。
- 窓の中で決定を出す効果（ダメージの要素のあとの窓の中の決定）を、v0.13 の決定の形で表せるか。
- トレーナー・宣言して使う特殊能力を同じ仕組みに入れたときの利点。
- 本番に入れたときの、テストの書き直しの実際の量（14 のモジュールという数は、内部の関数の名前を使っているかを数えただけ）。
