## 2. 方法（`scripts/repro_d17.py`）

- 盤面は既存のテストの盤面の関数と補助関数です（3 章の表）。`ClientHub.from_state`（不変条件の確かめ）で包み、プレイヤーのセッション（候補 → 入力 → 検査 → 送信）で進めました。どの段も検査は valid・受理で、不変条件の問題は 0 でした。
- 構築盤面です。new_game からの到達の実績には数えません。
- **呼ぶ箇所の通過の確かめ**: `effects`・`programs` のモジュールの名前 `reveal_deck_to_hand`・`return_hand_to_deck` を、呼び元の行・引数を記録するだけの包みに置きかえました（同じ引数で元の関数を呼び、戻り値・例外・順序は同じ。製品のファイルは変えていない）。
  - 包みは、候補・検査の先読み（状態の複製の上の試し）の呼び出しも記録します。受理した状態そのものへの呼び出しだけを対象にしました（複製の上の呼び出しは 75 回で、数だけ残した）。
- **各段のあとに取った値**: 4 つの入口（プレイヤー 0・1・観戦者・ホスト）の `log` の新しい出来事・更新・view と、3 閲覧者の `ViewRecorder` の項目。
  - どの段でも、`log` の新しい出来事は閲覧用記録と同じで、ホストは観戦者と同じでした。
- **判定**（閲覧者ごと: 山札の持ち主・その相手・観戦者・ホスト）:
  - 選ぶ前: その段の前までに届いた値に、対象の uid・組があるか
  - 受理の直後: 出来事の uid・`card_id`、その時点までに届いた値の組
  - 同じ `card_id` の別個体だけが見えているか（識別に数えない）
  - 事例の終わりまでに初めて組が届いたか（後の公開。当時の識別に数えない）
- 相手・観戦者の判定に、完全な記録・既知のデッキ・後の公開は使っていません。本当の `card_id` は監査の照合にだけ使いました。

**修正**: 次の 17 か所で、既存のヘルパーの呼び出しに `identify=True` を足します（0.182.0 の交換おじさんと同じ引数。ヘルパーは変えない）。
